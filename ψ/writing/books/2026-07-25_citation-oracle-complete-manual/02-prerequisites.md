# บทที่ 2: เตรียมของ — ต้องมีอะไรบ้าง (จริงๆ แค่ 2 อย่าง)

  "comment": "No runtime dependencies on purpose. …",

Citation Oracle ไม่เดินตามทางนั้น เปิด repo นี้มาแล้วถามคำถามเดียว — เครื่องคุณมี bun ไหม มีก็เริ่มงานได้เลย ไม่มีขั้นตอนที่สอง

ของที่เกี่ยวข้องในเล่มนี้แยกเป็นสามกองชัดเจน กองแรกต้องมี ขาดไม่ได้เลย กองที่สองควรมี ขาดได้แต่ทำงานได้ไม่เต็ม กองที่สามไม่ต้องมี เพราะตัดทิ้งไปตั้งแต่ก่อนจะมาถึงมือคุณ แยกให้ชัดตั้งแต่บทนี้ เพราะถ้าไม่แยก คุณจะไปลงของที่ไม่จำเป็นแล้วเสียเวลาฟรี หรือแย่กว่านั้นคือไปเชื่อว่าของที่ตัดทิ้งไปแล้วยังต้องมีอยู่

เรื่องนี้ไม่ได้เกิดโดยบังเอิญ มันคือการตัดสินใจที่ต้องลงมือตัดของออกจริง — จากสถานะที่เคยหนักถึง 487 MB (เล่าละเอียดในหัวข้อถัดไป) ของที่ไม่ต้องลง คือของที่ไม่มีวันพังแบบที่ dependency ตัวอื่นเคยพังมาให้เห็น

| กอง | ของ | สถานะ |
|---|---|---|
| ต้องมี | bun (runtime) | ขาดไม่ได้ — ทุกคำสั่งวิ่งผ่านตัวนี้ |
| ควรมี | ollama + bge-m3 | จำเป็นเฉพาะ `search` / `index` |
| ไม่ต้องมี | node_modules, database, API key, Docker | ตัดออกจาก repo ไปแล้ว |

## กองแรก — ต้องมี: bun เท่านั้น

ของที่ต้องมีจริงๆ ในเล่มนี้มีตัวเดียว คือ [bun](https://bun.sh) — runtime ที่รัน TypeScript ตรงๆ ไม่ต้อง compile แยก ไม่ต้องมี `tsc` คั่นกลาง ไม่ต้องตั้งค่า bundler ไม่ต้องเลือกว่าจะใช้ CommonJS หรือ ESM เปิด terminal มา bun ตัวเดียวก็รันไฟล์ `.ts` ได้ทันที

เช็คว่ามีหรือยังด้วยคำสั่งเดียว

```bash
bun --version
```

ถ้าเห็นเลขเวอร์ชันกลับมา แปลว่าพร้อม ถ้ายังไม่มีก็ลงตามทางการของ bun.sh — ขั้นตอนเดียวจบ ไม่มีอะไรซับซ้อนกว่านั้น ไม่ต้องเลือกเวอร์ชัน Node ผ่าน nvm ไม่ต้องตั้งค่า `tsconfig.json` ก่อนไฟล์แรกจะรันได้ เพราะ bun อ่าน `.ts` เป็นภาษาแม่ของมันเองอยู่แล้ว

ทำไมถึงพูดว่า "เท่านั้น" ได้เต็มปาก ลองเปิด `ψ/lab/citation/package.json` ดู

```json
{
  "name": "citation",
  "private": true,
  "comment": "No runtime dependencies on purpose. The vector store is plain files + brute-force cosine, embeddings come from ollama (local, GPU) or a Cloudflare worker over HTTP, and figures are SVG. `sharp` is an OPTIONAL peer: install it only if you also want PNG output.",
  "dependencies": {},
  "optionalDependencies": {
    "sharp": "^0.33.5"
  },
  "devDependencies": {
    "@types/bun": "^1.3.0"
  }
}
```

`"dependencies": {}` ว่างจริง ไม่ใช่ตัวเลขน้อยแล้วบอกว่า "พยายามลดแล้ว" — ว่างสนิท ไม่มี key ไหนอยู่ข้างในเลยสักตัว field `comment` ข้างบนไม่ใช่ metadata มาตรฐานของ npm แต่เป็นข้อความที่คนเขียนใส่ไว้ให้คนอ่าน package.json เจอเหตุผลตรงนั้นเลย ไม่ต้องไปงมหาใน README แยกไฟล์

ส่วน `optionalDependencies` มีอยู่ตัวเดียวคือ `sharp` ซึ่งเป็นของกองที่สาม (เสริม) เก็บไว้เล่าเต็มๆ ในบทหน้า `devDependencies` ก็มีแค่ type ของ bun เอง ไม่ใช่ของที่ต้องมีตอนรัน มีไว้ให้ editor ช่วย autocomplete เท่านั้น

พอ dependencies ว่างแบบนี้ คำสั่ง `bun install` ก็ไม่มีอะไรให้ทำ ข้ามได้เลยด้วยซ้ำ — clone repo มาแล้วรันคำสั่งได้ทันที ไม่ต้องรอ progress bar โหลด package สักตัวเดียว

ไม่ต้องเจอ lockfile ที่ conflict กับเครื่องอื่น ไม่ต้องเจอปัญหา "รันบนเครื่องฉันได้ แต่เครื่องเธอไม่ได้" ที่มักมาจากเวอร์ชัน package ที่ resolve ไม่ตรงกัน — เพราะไม่มี package ให้ resolve ตั้งแต่ต้น

ลองจริงดู clone repo มาที่ไหนก็ได้ในเครื่อง แล้วสั่งเลย

```bash
git clone https://github.com/Soul-Brews-Studio/phd-citation-oracle
cd phd-citation-oracle
./bin/citation status
```

สามบรรทัด ไม่มีบรรทัดที่สี่ ไม่มีขั้นตอนเตรียมเครื่องแทรกกลาง — นี่คือความหมายของ "ต้องมีแค่ bun" ในทางปฏิบัติ ไม่ใช่แค่คำโฆษณาบนหน้า README

## กองที่สอง — ควรมี: ollama + bge-m3

`status`, `cards`, `doi`, `bib` — สี่คำสั่งนี้ทำงานได้ด้วย bun ล้วนๆ ไม่แตะ embedding เลย แต่พอถึง `search` กับ `index` ต้องมีตัวช่วยแปลงข้อความเป็นเวกเตอร์ตัวเลข 1024 มิติ นั่นคือหน้าที่ของ [ollama](https://ollama.com) รันโมเดล `bge-m3`

เห็นได้ว่าครึ่งหนึ่งของ 8 คำสั่งทำงานได้โดยไม่ต้องมี ollama เลยสักคำสั่งเดียว นี่ไม่ใช่ความบังเอิญ แต่เป็นการแยกชั้นตั้งใจ

งานที่แค่อ่าน/เขียนไฟล์ (การ์ด, `.bib`, เช็คสถานะ) ไม่ควรต้องพึ่งโมเดลภาษาที่ต้องโหลดขึ้น GPU ก่อนถึงจะเริ่มได้ ส่วนงานที่ต้อง "เข้าใจความหมาย" อย่าง `search` กับ `index` ต่างหากที่จำเป็นต้องมี

ลงสองอย่างนี้เพิ่ม

```bash
brew install ollama
ollama pull bge-m3
```

ไม่มีก็ไม่ถึงกับใช้งานไม่ได้เลย เพียงแต่ครึ่งหนึ่งของคำสั่งทั้งหมดจะหายไป — เหมือนได้เครื่องมือมาแล้วขาดใบมีดสำคัญไปหนึ่งอัน ยังจับด้ามได้ ยังเปิดดูการ์ดได้ ยังทำ `.bib` ได้ แต่ค้นหาด้วยความหมาย (ไม่ใช่ค้นหาด้วยคำ) ทำไม่ได้

วิธีติดตั้งแบบละเอียด พร้อมตัวเลขจริงว่าเร็วช้าแค่ไหนบน CPU กับ GPU จะอยู่ในภาค 2 ทั้งภาค (บทที่ 6–11)

ตัวเลข 1024 มิตินั้นคืออะไรกันแน่ ยังไม่ต้องรู้ตอนนี้ก็ได้ — บทที่ 6 จะอธิบายแบบไม่ใช้สมการสักตัว ตอนนี้รู้แค่ว่ามันคือ "ลายนิ้วมือทางความหมาย" ของข้อความหนึ่งชิ้น ก็พอ

จุดที่ควรรู้ไว้ตั้งแต่ตอนนี้คือทุกอย่างรันบนเครื่องคุณเอง ollama ไม่ใช่ API ที่ต้องขอ key ไม่ใช่ service ที่ต้อง sign up ไม่มี token ไม่มี rate limit จาก third party — corpus วิทยานิพนธ์ที่ยังไม่ตีพิมพ์ไม่ต้องออกจากเครื่องเลยสักไบต์เดียว

โมเดล `bge-m3` ตัวเดียวกันนี้ก็เป็นตัวที่ cloud worker สำรอง (บทที่ 10) ใช้ด้วย — สลับไปมาระหว่าง local กับ cloud จึงยังได้เวกเตอร์ที่เทียบกันได้ ไม่ใช่คนละภาษากัน

## กองที่สาม — ไม่ต้องมี

ส่วนที่เหลือ — `node_modules`, database, API key, Docker — ไม่ต้องแตะเลย ไม่ใช่เพราะ "ยังไม่ได้ทำ" แต่เพราะตัดทิ้งออกจาก repo ไปแล้วโดยตั้งใจ

- **`node_modules`** — ไม่มีเพราะไม่มี dependency ให้ install ตั้งแต่แรก ไม่มีโฟลเดอร์ร้อย MB นอนรอในเครื่อง ไม่มีอะไรให้ `.gitignore` ต้องกันไว้ตรงจุดนี้
- **database** — ไม่มีเซิร์ฟเวอร์ไหนต้องรัน ไม่มี connection string ให้ตั้งค่า ไม่มี migration ให้ลืมรัน vector store ทั้งชุดเป็นไฟล์ธรรมดาสามไฟล์ในโฟลเดอร์ เปิดดูด้วย text editor ได้ตรงๆ (รายละเอียดสามไฟล์นี้อยู่บทที่ 4)
- **API key** — เส้นทาง default ทั้งหมดรันในเครื่อง ollama ไม่ขอ key ไม่มีบัญชีให้สมัคร ไม่มี `.env` ที่ต้องระวังไม่ให้หลุดขึ้น git (cloud เป็นทางเลือกเสริมที่จะเล่าในบทที่ 10 — สำหรับตอนนี้ยังไม่ต้องแตะ)
- **Docker** — ไม่มี container ให้ build ไม่มี image ให้ pull เพราะไม่มี service ตัวไหนต้องแยก process ออกไปรันข้างนอก bun ไม่มี `docker-compose.yml` ให้ต้องดูแลคู่ขนานกับ code

พอกองนี้หายไปทั้งกอง เวลาที่เหลือทั้งหมดก็ไปอยู่ที่งานจริง ไม่ใช่การดูแลโครงสร้างพื้นฐาน — นี่คือใจความของบทนี้เลย เครื่องมือที่ดีไม่ใช่เครื่องมือที่ทำได้ทุกอย่าง แต่เป็นเครื่องมือที่รู้ว่าตัวเองไม่ต้องทำอะไรบ้าง

## จาก 487 MB เหลือ 140 KB

repo นี้ไม่ได้เริ่มมาแบบนี้ ช่วงแรกมี [`@lancedb/lancedb`](https://lancedb.com) เป็น vector database เต็มรูปแบบ บวกกับ `sharp` เป็น hard dependency สำหรับแปลง SVG เป็น PNG — สองตัวนี้รวมกันดันขนาดติดตั้งไปถึง 487 MB ก่อนจะรันคำสั่งแรกได้สักคำสั่งเดียว ต้องรอ native binary compile เสร็จก่อน

commit `5475615` (25 กรกฎาคม 2569) ตัดทั้งสองออกในคราวเดียว ข้อความ commit เขียนไว้ตรงๆ ว่า

> "487 MB of native dependencies → 140 KB installed, nothing to `bun install`."

`@lancedb/lancedb` หลุดออกไปทั้งตัว เพราะ corpus แค่ 62 ใบ ไม่ใช่ 6.2 ล้านใบ — ค้นแบบ brute-force cosine ในไฟล์ TypeScript ล้วนๆ ก็เร็วพอแล้ว ไม่ต้องแบก native binary ของ database มาแลกกับความเร็วที่ไม่มีใครสัมผัสได้

vector store เลยกลายเป็นไฟล์แบนสามไฟล์แทน (`vectors.f32`, `meta.jsonl`, `manifest.json`) ลบโฟลเดอร์ทิ้งแล้ว index ใหม่ได้เสมอ เพราะมันคือ derived data ไม่ใช่ของต้นฉบับ ข้อความ commit สรุปเหตุผลไว้แบบนี้

> "Search is brute-force cosine in pure TS — 73 rows in ~0.2 s including the query embed, and even 100k rows stays sub-second, which is well short of where an ANN index earns a native dependency."

พูดง่ายๆ คือ database เต็มรูปแบบเอาไว้แก้ปัญหาระดับแสนระดับล้านแถว แต่ corpus นี้อยู่ระดับหลักสิบ ใช้ของหนักเกินขนาดไปก็มีแต่จะเพิ่มความเสี่ยงโดยไม่ได้อะไรกลับมาเลย

`sharp` ไม่ได้หายไปเสียทีเดียว แค่ถอยจาก hard dependency มาเป็น `optionalDependencies` แล้วเรียกผ่าน dynamic import ใน try/catch แทน — มีก็ได้ PNG ไม่มีก็ยังได้ SVG ซึ่งเป็น vector อยู่แล้ว คมกว่าด้วยซ้ำ ไม่มีคำสั่งไหนพังเพราะขาด `sharp` ไปสักคำสั่งเดียว

(รายละเอียดวิธีทำ optional ให้ "optional จริง" — พร้อมบทเรียนที่เกือบทำให้ลบ `sharp` ทิ้งไปทั้งที่ยังใช้อยู่ — เก็บไว้เล่าเต็มๆ บทหน้า)

commit เดียวกันนี้ยังบอกวิธีเลือก embedding backend ไว้ด้วย เรียงลำดับอัตโนมัติ

> "Embedding backends, auto-detected in order: ollama (local, GPU — default when running), the shared Cloudflare worker, then Cloudflare REST with a token."

ตอนที่ commit นี้เพิ่งเข้า ข้อความวัดผลจริงบนเครื่อง m5 ไว้ว่า "62 cards + 11 vault notes embedded in 6.2 s warm, 292 KB store, search 0.21 s"

ตัวเลขวันนี้ (ในบล็อก `status` ท้ายบทนี้) ขยับเป็น 62 การ์ด + 13 vault note รวม 300 KB เพราะมี note เพิ่มเข้ามาอีกสองชิ้นระหว่างทาง แต่รูปแบบเดิมยังเหมือนเดิมทุกอย่าง ไฟล์แบนสามไฟล์ ค้นแบบ brute-force ไม่มี database คั่นกลาง

487 MB กับ 140 KB ต่างกันสามพันกว่าเท่า แต่ตัวเลขไม่ใช่ประเด็นหลัก ประเด็นคือของทุกชิ้นที่ลงเพิ่มคือความเสี่ยงที่พังเพิ่มหนึ่งจุด — native dependency ที่ compile ไม่ผ่านบนเครื่องใหม่ database ที่ลืม migrate schema container ที่ image เวอร์ชันไม่ตรงกับที่ทีมอื่นใช้ ของที่ไม่ต้องลง คือของที่ไม่มีวันพังแบบนั้นได้เลย

## สองทางเข้า หนึ่ง implementation

repo นี้เรียกใช้ได้สองทาง

```bash
./bin/citation status      # ต้องมีแค่ bun — ไม่ต้องมี maw
maw citation status        # เหมือนกันทุกอย่าง สำหรับคนที่มี maw
```

`maw` คือ federation engine ของตระกูล oracle เอาไว้ให้ oracle หลายตัวคุยกันข้ามเครื่อง — ถ้าไม่รู้จักก็ไม่ต้องไปหาข้อมูลเพิ่ม ไม่จำเป็นสำหรับเล่มนี้เลยสักบรรทัด ทุกคำสั่งที่เล่าในเล่มนี้ใช้ `./bin/citation` ล้วนๆ พอ

สองทางนี้ไม่ได้เป็นสองระบบที่บังเอิญให้ผลลัพธ์เหมือนกัน แต่เรียก handler ตัวเดียวกันที่ export ออกมาจาก `ψ/lab/citation/src/index.ts` — ไม่มี dispatch สองชุดให้ดูแลคู่ขนาน แก้ logic ที่เดียว ทั้งสองทางได้ผลตรงกันเสมอ

ไฟล์ `bin/citation` เองก็บอกไว้ตรงๆ ในคอมเมนต์หัวไฟล์

> "The plugin and this shim share one implementation ... so there is no second dispatch path to keep in sync."

คำถามที่ตามมาคือ แล้วมันรู้ได้ยังไงว่า repo อยู่ตรงไหน ในเมื่อรันจากไดเรกทอรีไหนก็ได้ คำตอบคือมันไล่หาตามลำดับนี้

1. `CITATION_ROOT` — ถ้าตั้ง env นี้ไว้ ใช้ตามนั้นเลย ไม่ไล่หาต่อ
2. `MAW_HOME` — ถ้ารันผ่าน maw ตัวนี้จะมีอยู่แล้วเสมอ
3. ไล่ขึ้นจากตำแหน่งของ **สคริปต์เอง** หา `CLAUDE.md` + `ψ/`
4. ไล่ขึ้นจาก working directory ปัจจุบัน ด้วยกฎเดียวกัน
5. `git rev-parse --show-toplevel`
6. working directory ปัจจุบัน (fallback สุดท้าย)

ขั้นที่ 3 คือจุดที่น่าสนใจที่สุด เพราะ `bin/citation` เป็นไฟล์ที่นอนอยู่ *ข้างใน* repo เสมอ ไม่ว่าคุณจะ `cd` ไปอยู่ที่ไหนก็ตาม ไล่ขึ้นจากตำแหน่งไฟล์นั้นก็เจอ root ทุกครั้ง — นี่คือเหตุผลที่ `./bin/citation status` รันจาก `/tmp` ก็ยังได้ผลถูกต้อง (commit `051014b`)

ก่อนจะแก้ตรงนี้ รันจากนอก repo แล้วมันจะเงียบๆ รายงานว่า "0 paper cards" กลับมา — ไม่ error ไม่เตือนอะไรเลย แค่ดูเหมือนข้อมูลหายไปทั้งชุด ข้อความ commit เล่าจุดพลาดเดิมไว้ตรงๆ

> "Only two lines actually coupled the plugin to maw — repoRoot() and STORE_DIR both fell back to process.cwd(), so running from /tmp reported '0 paper cards' and put the store wherever you happened to be standing."

เพราะบั๊กแบบนั้นเคยเกิดขึ้นจริงมาแล้ว `status` เลยพิมพ์บอกตรงๆ ทุกครั้งว่าเจอ root ด้วยกฎข้อไหน — จะได้รู้ทันทีถ้ามันไปหลงทาง ไม่ต้องเดา ไม่ต้องไปนั่งไล่ log เอง

## เช็คว่าพร้อมหรือยัง: `./bin/citation status`

ทุกอย่างข้างบนเช็คได้ด้วยคำสั่งเดียว `status` เป็น 1 ใน 8 คำสั่งของเล่มนี้ (อีก 7 ตัวคือ `cards` `doi` `bib` `index` `search` `serve` และ `graph` — เล่าเต็มในบทที่ 5)

แต่เป็นตัวที่ควรรันก่อนเสมอ เพราะมันไม่ได้แค่บอกว่า "พร้อม" หรือ "ไม่พร้อม" — มันบอกด้วยว่า *ทำไม*

```bash
./bin/citation status
```

นี่คือ output จริงจากเครื่อง m5 (Apple M5 Max) วันที่เขียนบทนี้

```
── citation status ──
  ✓ repo root: /opt/Code/github.com/Soul-Brews-Studio/phd-citation-oracle (walk up from the script)
  ✓ 62 paper card(s) in ψ/papers — 61 with a DOI, all citable
  ✓ corpus present (artifacts/literature_corpus.jsonl) — 23814 bytes
  ✓ store ready (…/.citation/store) — 62 paper(s) + 13 vault note(s) · 1024-dim · 300 KB · model ollama:bge-m3
  ✓ hardware: Apple M5 Max · arm64 · 18 cores · 128 GB unified memory — Metal GPU available to ollama
  ✓ embeddings: ollama bge-m3 @ http://localhost:11434 — local, no token, no egress — 1024-dim
      └ bge-m3:latest · 634 MB · 100% GPU (fully resident — no CPU fallback) · 8192 ctx
  ✓ arra-oracle-v3 reachable (http://localhost:47778) — ok [optional]
```

ไล่ทีละบรรทัดว่าแต่ละบรรทัดบอกอะไรจริงๆ

| บรรทัด | บอกอะไร |
|---|---|
| `repo root: ... (walk up from the script)` | เจอ repo ตรงไหน ด้วยกฎข้อไหนในหกข้อของหัวข้อก่อนหน้า — ผิดข้อนี้เมื่อไหร่ ทุกบรรทัดถัดไปก็ผิดตามกันหมด |
| `62 paper card(s) ... 61 with a DOI` | จำนวนการ์ดจริงใน `ψ/papers/` กับจำนวนที่มี DOI ยืนยันแล้ว |
| `corpus present ... 23814 bytes` | ไฟล์ `artifacts/literature_corpus.jsonl` ต้นทางยังอยู่ครบ — เป็นแค่ทาง *import* เข้าสู่การ์ด ไม่ใช่ของจริงที่ใช้งานประจำวัน |
| `store ready ... 300 KB ... model ollama:bge-m3` | vector store พร้อมค้นแล้ว มีกี่แถว ขนาดเท่าไหร่ ทำจาก model ไหน |
| `hardware: Apple M5 Max ...` | สเปกเครื่องที่กำลังรันอยู่ตอนนี้ บอกว่ามี GPU ให้ ollama ใช้หรือเปล่า |
| `embeddings: ollama bge-m3 @ localhost:11434` | backend ที่กำลังใช้อยู่จริง ยืนยันว่า local ไม่มี token ไม่มีอะไรออกเน็ต |
| `└ bge-m3:latest · 634 MB · 100% GPU ...` | บรรทัดย่อยขยายบรรทัดบน — โมเดลตกไปอยู่ CPU หรือยังอยู่ GPU เต็มๆ |
| `arra-oracle-v3 reachable ... [optional]` | ระบบค้นความรู้เสริมของทีม — ไม่มีก็ไม่กระทบ verb ไหนของ citation เลย |

บรรทัดที่มี DOI คุ้มค่าจะขยายอีกนิด "61 with a DOI" ไม่ใช่ 62 เต็ม เพราะใบที่เหลืออย่าง `jarernwong2021` (ตีพิมพ์ใน Chemical Engineering Transactions) หา DOI จาก Crossref ไม่เจอจริงๆ — เก็บช่องว่างไว้ดีกว่าเดาเอาเองแล้วใส่เลขผิด

ตัวเลข 61/62 นี้ไม่ใช่จุดเริ่มต้น มันคือผลจากงานตรวจสอบทั้งบทที่เล่าไว้ในบทที่ 1 (เริ่มจาก 8/62) — `status` แค่รายงานสถานะปัจจุบัน ไม่ได้เล่าเรื่องราวว่ากว่าจะมาถึงตรงนี้ผ่านอะไรมาบ้าง

บรรทัด `corpus present` ก็มีรายละเอียดที่ควรรู้ไว้ก่อนบทที่ 4 — `artifacts/literature_corpus.jsonl` คือไฟล์ต้นทางที่ *เคย* เป็นของจริงตอนเริ่มโครงการ แต่ตอนนี้กลายเป็นแค่ทาง import เข้าสู่การ์ดใน `ψ/papers/` เท่านั้น

การ์ดต่างหากที่เป็น source of truth วันไหนที่ JSONL กับการ์ดขัดกัน ให้เชื่อการ์ด เพราะการ์ดคือของที่ถูกแก้ไขและตรวจทานต่อเนื่องมาเรื่อยๆ ส่วน JSONL หยุดนิ่งอยู่กับที่มันเคยถูก import มาจากตอนแรก

ส่วน `arra-oracle-v3 reachable ... [optional]` คือระบบค้นความรู้ของทั้งตระกูล oracle ที่ Nat ดูแลอยู่ — ไม่เกี่ยวกับ corpus paper 62 ใบนี้โดยตรง วงเล็บ `[optional]` ท้ายบรรทัดบอกไว้ตรงๆ ว่าเช็คไว้เฉยๆ ไม่มีก็ไม่กระทบ verb ไหนของ citation เลยสักตัว ต่างจากบรรทัด embedding ที่ถ้าขาดจะกระทบ `search` กับ `index` ทันที

อีกบรรทัดที่ควรจำไว้คือ `store ready` เพราะตำแหน่งไฟล์จริงของ store ขึ้นกับว่าเรียกผ่านทางไหน — ถ้ารันผ่าน `maw` จะไปอยู่ที่ `$MAW_HOME/citation-data/store` ถ้ารันแบบ standalone ด้วย `./bin/citation` จะไปอยู่ที่ `<repo>/.citation/store` แทน

ทั้งสองที่เก็บไฟล์หน้าตาเดียวกันทั้งชุด ต่างกันแค่ตำแหน่ง เพราะยึดกฎ root-resolution เดียวกับหัวข้อก่อนหน้า

สังเกตว่าทุกบรรทัดขึ้นต้นด้วย `✓` — ถ้าของชิ้นไหนขาด เครื่องหมายจะเปลี่ยนและบอกตรงๆ ว่าขาดอะไร ไม่ใช่แค่ error ทั่วไปที่ต้องไปไล่ log เอาเอง

บรรทัดที่ควรมองก่อนบรรทัดอื่นเสมอคือบรรทัดแรก — `repo root` เพราะถ้าตรงนี้ผิด บรรทัดถัดๆ ไปจะดูเหมือนพังหมดทั้งที่จริงๆ แค่หา repo ไม่เจอ กด `status` ทีเดียวรู้ทันทีว่าปัญหาอยู่ตรงไหนในสี่จุดนี้ — root, corpus, store, หรือ embedding backend

ของที่ต้องมีจริงๆ ก็แค่นี้ bun หนึ่งตัว ollama กับ bge-m3 อีกหนึ่งคู่ ส่วนที่เหลือคือของเสริมที่มีไว้ก็ดี ไม่มีก็ไม่ตาย — แล้วของเสริมพวกนั้นจริงๆ แล้วมีอะไรบ้าง แต่ละตัวถ้าขาดไปจะเกิดอะไรขึ้น บทหน้าไล่ให้ดูทีละตัว
