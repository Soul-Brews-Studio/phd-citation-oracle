# บทที่ 11: Cafe Mode — เน็ตไม่มี แบตไม่เยอะ ทำงานยังไง

นั่งร้านกาแฟ แบตเหลือ 40% wifi ร้านช้าจนต้อง login วนไปวนมา
แล้ว thesis deadline ก็ยังนับถอยหลังอยู่เหมือนเดิม — สถานการณ์นี้
เกิดกับคนทำ thesis บ่อยกว่าที่คิด บางทีก็ไม่ใช่ร้านกาแฟด้วยซ้ำ
เป็นรถไฟ เป็นเครื่องบิน เป็นบ้านต่างจังหวัดที่ wifi ไม่เสถียร
คำถามที่ตามมาก็ตรงไปตรงมา: ใช้ Citation Oracle ต่อได้ไหม
ถ้าไม่มีเน็ต แล้วถ้ามีแค่ tethering จากมือถือ ควรระวังอะไรบ้าง

คำตอบคือได้ เกือบทั้งหมด เพราะเราออกแบบมันให้ **ออฟไลน์เป็นค่าเริ่มต้น**
ไม่ใช่ออฟไลน์แบบ "เผื่อไว้" — model รันในเครื่อง store เป็นไฟล์ธรรมดา
บนดิสก์ ไม่มี database ต้องต่อ ไม่มี service กลางที่ต้อง ping ตลอดเวลา
สิ่งที่ต้องมีเน็ตจริงๆ เหลือแค่คำสั่งเดียว และบทนี้จะบอกว่าคำสั่งไหน
พร้อมวิธีเตรียมตัวก่อนออกจากบ้าน และวิธีประหยัดแบตระหว่างนั่งข้างนอก

## ตารางเดียวจบ: verb ไหนออนไลน์ verb ไหนไม่ใช่

เริ่มจากตารางก่อน เพราะนี่คือสิ่งที่ต้องรู้ก่อนออกจากบ้านที่สุด

| verb | ต้องมีเน็ตไหม | ทำไม |
|---|---|---|
| `status` | ไม่ต้อง | อ่าน sysctl + เช็ค process ในเครื่องล้วนๆ |
| `cards` | ไม่ต้อง | อ่าน/เขียน markdown ในโฟลเดอร์ `ψ/papers/` |
| `index` (รวม `--vault`) | ไม่ต้อง* | ยิง embedding ไป ollama ที่ localhost |
| `search` | ไม่ต้อง* | เดียวกัน — embed query ผ่าน ollama local |
| `serve` (= `visualize`) | ไม่ต้อง | เสิร์ฟ HTML จาก store ในเครื่อง ผ่าน localhost |
| `graph` | ไม่ต้อง | render จาก store ในเครื่อง → PNG |
| `bib` | ไม่ต้อง | อ่าน card ในเครื่อง → เขียน `.bib` |
| `doi` | **ต้อง** | ยิงตรงไปที่ `api.crossref.org` |

7 ใน 8 คำสั่งไม่แตะเน็ตเลย มีแค่ `doi` ตัวเดียวที่ต้อง — เพราะมันทำ
สิ่งที่ทำในเครื่องไม่ได้จริงๆ (อธิบายต่อด้านล่าง) ส่วนเครื่องหมาย `*`
ที่ `index` กับ `search` คือเงื่อนไขเดียว: ต้องเลือก backend เป็น
ollama (ค่า default) ไม่ใช่ `cf-rest` — ถ้าสลับไป Cloudflare REST
ตามบทที่ 10 นั่นแหละที่ทำให้ทั้งสอง verb นี้กลายเป็นต้องมีเน็ตจริง
เพราะยิงออกไปหา Cloudflare ตรงๆ

## เลือก backend ให้ชัดก่อนออกจากบ้าน กันหลุดไปโดนเน็ต

`index` กับ `search` เลือก backend เอง 3 ทางเรียงลำดับ: ลองยิงหา
ollama (local) ก่อน — ถ้า pull `bge-m3` ไว้แล้วและ ollama รันอยู่
ก็จบตรงนั้น ไม่มีอะไรออกนอกเครื่อง ถ้าไม่เจอ ollama มันจะลองต่อไป
หา Cloudflare worker ที่ `:18787` (ต้องมี `wrangler dev` รันอยู่ใน
เครื่องเหมือนกัน) แล้วสุดท้ายถึงจะไปที่ Cloudflare REST จริงๆ ซึ่ง
ต้องมี `CF_ACCOUNT_ID` กับ `CF_API_TOKEN` และต้องมีเน็ตจริง

ลำดับนี้ปกติไม่มีปัญหา เพราะขั้นแรกมักจะเจอ ollama อยู่แล้ว แต่
ถ้าลืม `ollama pull bge-m3` มาจากบ้าน แล้วก็ไม่ได้เปิด `wrangler
dev` ไว้ด้วย — มันจะไหลไปจบที่ REST ซึ่งพังทันทีถ้าไม่มีเน็ต (หรือ
แย่กว่านั้นคือมีเน็ต tethering นิดหน่อยแล้วมันดันใช้ไปจริงๆ โดยไม่
รู้ตัว) วิธีกันเหตุนี้ตรงไปตรงมา — บังคับ backend ไว้เลยด้วย env
ก่อนออกจากบ้าน จะได้ไม่มีทางหลุดไปทางอื่น:

```bash
export CITATION_EMBED=ollama
```

ตั้งไว้ครั้งเดียวใน shell profile ก็ได้ ถ้า ollama ไม่พร้อมมันจะ
error ตรงๆ ทันที ดีกว่าเงียบๆ แล้วไปโดนบิล tethering ทีหลัง

## ทำไม 7 verb ไม่แตะเน็ตเลย — เพราะ store เป็นไฟล์ ไม่ใช่ service

หัวใจของ cafe mode ไม่ได้อยู่ที่ "ปิด wifi แล้วลองดู" แต่อยู่ที่
สถาปัตยกรรม store เอง store ของ Citation Oracle ไม่มี database
ไม่มี server ต้อง connect — มีแค่ 3 ไฟล์ธรรมดา:

```
vectors.f32    N × 1024 Float32 เรียงต่อกัน
meta.jsonl     เมทาดาต้าต่อรายการ หนึ่งบรรทัดต่อหนึ่ง paper/note
manifest.json  ชื่อ embedding model ที่ใช้สร้าง store นี้
```

ทั้งโฟลเดอร์รวมกัน **452 KB** — เฉพาะ `vectors.f32` เอง **300 KB**
(วัดจริงบนชุด 75 รายการ: 62 paper + 13 note) เล็กพอจะ zip
ใส่ USB ติดกระเป๋าไปได้เลย ไม่ต้องพึ่ง cloud sync ไหนทั้งนั้น
และเพราะเป็นไฟล์ธรรมดา ไม่ใช่ database ที่ล็อกฟอร์แมต — ลบโฟลเดอร์
ทิ้งแล้ว `index` ใหม่ได้เสมอ มันคือ derived data จาก card ที่เป็น
source of truth ไม่ใช่ตัวข้อมูลจริง เสียก็ไม่เสียอะไร

`search` เองก็ทำใน TypeScript ล้วน — brute-force cosine ไล่เทียบ
ทีละแถว ไม่มี ANN index ไม่มี native dependency ที่ต้อง compile
วัดจริงบนชุด 75 รายการ (embed query + cosine ครบ 75 แถว): **0.221
วินาที** ต่อการค้นหาหนึ่งครั้ง เร็วพอจะรู้สึกเหมือน local grep
ไม่ใช่รอ network round-trip เลย

หน้าตา output จริงของ `search` — สังเกตว่าผลลัพธ์แยก 📄 paper
กับ 📝 note ให้เห็นชัด (ใบหลังมาจาก `--vault` ที่อธิบายต่อไป):

```
$ maw citation search "sensor calibration drift"
[0.7913] 📄 paper \cite{mahajan2025}
  (low-cost-sensor-calibration) Mahajan & Helbing (2025)
[0.8702] 📝 note (ψ/writing/research)
  Environmental prediction models for PM2.5
```

`serve` กับ `graph` ก็เดินตามหลักเดียวกัน — อ่านจาก store ที่ index
ไว้แล้ว render เป็น HTML หรือ PNG ในเครื่อง `serve` เปิด
`Bun.serve()` บน `localhost` ไม่มีการยิงออกนอกเครื่องสักครั้งเดียว
เปิดในโหมด airplane mode ก็ยังใช้ได้ — เพราะ localhost ไม่ต้องพึ่ง
wifi หรือ network adapter ใดๆ เลยด้วยซ้ำ

## งานที่ทำได้เต็มที่ตอนไม่มีเน็ต ไม่ใช่แค่ `search`

ตัวที่มักถูกมองข้ามคือ `cards` กับ `bib` — สองคำสั่งนี้ไม่แตะ
network เลยสักครั้ง เพราะทำงานกับ markdown ในโฟลเดอร์ `ψ/papers/`
ล้วนๆ อ่านอย่างเดียวก็ทำได้ แก้ก็ทำได้ นั่งร้านกาแฟแล้วอ่าน paper
ที่โหลดมาไว้ในเครื่องแล้ว จดสรุปลงใน `## Notes` ของ card ได้เต็มที่
— ส่วนนี้เป็น section ที่ `citation cards` รับประกันว่าจะเก็บไว้
ทุกครั้งที่ build การ์ดใหม่จาก JSONL ไม่มีการเขียนทับความคิดที่
จดไว้เอง

พอกลับมาทำ `bib` มันก็แค่อ่าน card ที่มีอยู่แล้วประกอบเป็น
`.bib` — ไม่ได้ไปคำนวณอะไรหนักหรือติดต่อใครข้างนอก สรุปคือ
ระหว่างนั่งร้านกาแฟ งานที่ทำได้จริงไม่ใช่แค่ "ค้นของเดิม" แต่
รวมถึง "เขียนงานใหม่" เข้าไปในคลังด้วย แค่ DOI ของ paper ใหม่
ที่เพิ่งเจอจะยังยืนยันไม่ได้จนกว่าจะมีเน็ตเท่านั้นเอง

## `doi` ตัวเดียวที่ต้องมีเน็ต — เพราะมันยิง Crossref จริง

`doi` ทำสิ่งที่ verb อื่นทำไม่ได้: ยืนยันว่า author, ปี, DOI ที่
เขียนใน card ตรงกับสิ่งที่ Crossref บันทึกไว้จริง ไม่ใช่แค่สิ่งที่
เราพิมพ์เอาไว้เอง งานนี้ต้องมีแหล่งข้อมูลภายนอกที่เชื่อถือได้ —
จะให้ AI เดา DOI เองในเครื่องก็ได้ แต่นั่นคือการแกล้งทำเป็นยืนยันได้
ทั้งที่จริงไม่ได้ยืนยันอะไร Citation Oracle เลือกไม่โกหกแบบนั้น
เลยยอมให้ `doi` เป็น verb เดียวที่ "ต้องพึ่งข้างนอก" อย่างเปิดเผย
ดีกว่าให้ verb อื่นแอบยิงเน็ตโดยไม่บอก

ถ้าลอง `doi` ตอนไม่มีเน็ต มันจะไม่ crash เงียบๆ — request ไป
`api.crossref.org` จะ timeout แล้วรายงาน error ตรงๆ ว่า resolve
ไม่ได้ ไม่ใช่ค้างเฉยๆ ให้เดา ก็เป็นความซื่อสัตย์แบบเดียวกับที่
คู่มือเล่มนี้ยึดถือมาตลอด: บอกตรงว่าทำไม่ได้ ดีกว่าเงียบแล้วให้เดา

## เตรียมตัวก่อนออกจากบ้าน — 2 คำสั่งจบ

Cafe mode ไม่ใช่ mode ที่ต้อง "เปิด" ตอนถึงร้าน — มันคืองานเตรียม
ที่ทำตอนยังอยู่บ้าน มีเน็ตเต็มแรง แล้วปล่อยให้เครื่องพร้อมเอง สอง
คำสั่งพอ:

```bash
ollama pull bge-m3
maw citation index --vault
```

บรรทัดแรกโหลด model ลงเครื่อง ครั้งแรกที่ pull ใช้เน็ตดาวน์โหลด
ประมาณ **1.2 GB** — ทำครั้งเดียวพอ ครั้งต่อไป ollama มี model
อยู่แล้วในเครื่อง ไม่โหลดซ้ำ บรรทัดที่สอง index ทุกอย่างเข้า store —
ทั้ง 62 paper และ 13 vault note (จาก `ψ/memory/{learnings,
retrospectives,resonance}` กับ `ψ/writing/research`) รวม 75
รายการ วัดจริงตอน model warm อยู่ใน GPU แล้ว: **8.4 วินาที**
เท่านั้น ไม่ใช่งานที่ต้องรอนาน แค่ต้องมีเน็ตตอนดาวน์โหลด model
ก่อนหนึ่งรอบ

สิ่งที่ต้อง embed ต่อ 1 paper คือ title + summary + thesis_relevance
ต่อกัน — ไม่ใช่ทั้งไฟล์ ส่วน `doi`, `volume`, `pages` ไม่ถูก embed
เลย นี่คือเหตุผลที่เติม DOI เข้า card ทีหลังแล้ว**ไม่ต้อง index
ใหม่** — เติมได้แม้ตอนไม่มีเน็ตพอกลับมาแล้วค่อยยืนยันด้วย `doi`
ทีหลังก็ยังทัน

ก่อนปิดเครื่องออกจากบ้าน คำสั่งเดียวที่พิสูจน์ว่าพร้อมจริงคือ
`maw citation status` — มันไม่ได้แค่บอก "พร้อม" ลอยๆ แต่โชว์ให้
เห็นเลยว่า backend ที่จะใช้คือตัวไหน model resident อยู่บน GPU
กี่เปอร์เซ็นต์ หน้าตาประมาณนี้บนเครื่อง m5 (Apple M5 Max):

```
── citation status ──
  ✓ store ready — 62 paper(s) + 13 vault note(s) · 1024-dim
      · 300 KB · model bge-m3
  ✓ hardware: Apple M5 Max · arm64 · 18 cores · 128 GB unified
      memory — Metal GPU available to ollama
  ✓ embeddings: ollama bge-m3 @ http://localhost:11434 — local,
      no token, no egress — 1024-dim
      └ bge-m3:latest · 634 MB · 100% GPU
        (fully resident — no CPU fallback) · 8192 ctx
```

บรรทัด `hardware` กับตัวเลข `size_vram` ใน `/api/ps` คือสิ่งที่
พิสูจน์คำว่า "GPU-backed" จริงๆ — คำนี้เคยอยู่แค่ในเอกสารมาก่อน
ไม่เคยโชว์ใน output ไหนเลย ซึ่งเป็นแบบนั้นได้ง่ายที่โฆษณาที่ไม่มี
ใครวัดจะค่อยๆ เลิกเป็นความจริงโดยไม่มีใครรู้ตัว ตอนนี้ `status`
วัดให้ทุกครั้งที่รัน — เห็น `100% GPU` แปลว่า model โหลดเต็มก้อน
บน GPU ไม่มีตกไป CPU จริง เช็คก่อนออกเดินทางครั้งเดียว อุ่นใจได้
ทั้งวัน

เช็คก่อนออกจากบ้านด้วย checklist สั้นๆ:

```
[ ] ollama pull bge-m3 เสร็จแล้ว — เช็คด้วย `ollama list`
[ ] maw citation index --vault รันผ่าน ไม่มี error
[ ] maw citation status เห็น backend: ollama (ไม่ใช่ cf-rest)
[ ] ถ้ามี card ที่ยังไม่มี DOI — resolve ให้ครบตอนนี้
    (เพราะ doi ต้องมีเน็ตเท่านั้นที่ทำได้จริง)
```

ข้อสุดท้ายสำคัญที่สุด — ถ้ารู้ตัวว่าจะออกไปทำงานยาวๆ โดยไม่มีเน็ต
ให้ล้าง backlog ของ `doi --write` ให้เกลี้ยงก่อน จะได้ไม่ต้องมานั่ง
เสียดายตอนถึงร้านแล้วเจอ card ที่ยังไม่มี DOI ค้างอยู่

ถ้าลืมข้อแรกล่ะ — ถึงร้านแล้วค่อยนึกได้ว่ายังไม่ได้ `ollama pull`
มา จะเกิดอะไรขึ้น คำตอบตรงๆ คือ `index` กับ `search` จะ error ทันที
เพราะ ollama หา model ไม่เจอในเครื่อง แล้วพอไม่มีเน็ตก็ pull ให้
ไม่ได้เหมือนกัน กลายเป็นทางตันทั้งสองทาง — นี่คือเหตุผลที่ prep
ต้องทำที่บ้านจริงๆ ไม่ใช่ "เดี๋ยวค่อยทำที่ร้านก็ได้" เพราะร้าน
กาแฟไม่มีเน็ตพอให้ pull 1.2 GB แบบสบายใจแน่นอน

## ประหยัดแบต: ปิด `serve` เอง ollama ปิดตัวเอง

`serve` เปิด `Bun.serve()` ซึ่งกินการ์ด event loop ค้างไว้ตลอด —
ตราบใดที่ terminal ยังเปิดอยู่ process ก็ยังรันอยู่ ไม่ได้จบเองแม้
ปิดแท็บเบราว์เซอร์ที่เข้าไปดูแล้ว วิธีปิดคือ Ctrl+C ตรงๆ ตอนดูจบ
แล้ว — ไม่มีเหตุผลต้องเปิดค้างไว้ทั้งวันถ้าไม่ได้ดูซ้ำ

ส่วน ollama เองมีพฤติกรรม unload model ออกจากหน่วยความจำเองหลัง
ไม่มีการเรียกใช้ประมาณ **5 นาที** — เป็นค่า default ของ ollama เอง
ไม่ใช่โค้ดของเรา เช็คได้ตรงๆ ว่า model กำลังโหลดอยู่หรือ unload
ไปแล้วด้วย:

```bash
curl -s http://localhost:11434/api/ps | jq
```

ดูที่ฟิลด์ `expires_at` — ถ้าเวลาผ่านไปแล้ว model จะหายไปจากลิสต์
คือ unload แล้วจริง ระหว่างที่ยังโหลดอยู่ วัดจริงบน m5: bge-m3 กิน
**634 MB** ใน VRAM ที่ context 8192 และ resident แบบ **100% GPU**
(ยืนยันด้วย `size_vram == size` ในผลลัพธ์ `/api/ps` — ถ้าเท่ากัน
แปลว่าอยู่บน GPU ทั้งก้อน ไม่มีตกไป CPU) ตราบใดที่ model ยังโหลดค้าง
อยู่ GPU ก็ยังทำงานอยู่เบาๆ — ปล่อยให้มัน unload เองหลัง 5 นาที
ดีกว่าไปยิง request ปลอมๆ กันไม่ให้มัน idle จะกลายเป็นทำให้กิน
พลังงานนานกว่าที่ต้องใช้จริง

พูดง่ายๆ: ไม่ต้องทำอะไรพิเศษเพื่อประหยัดแบตฝั่ง ollama — แค่อย่า
ไปแทรกแซงพฤติกรรม auto-unload ของมัน ส่วนฝั่งเรา หน้าที่เดียวคือ
ปิด `serve` เองตอนดูเสร็จ

## tethering น้อยๆ: `doi` ทีละใบ ไม่ใช่ `--all`

เมื่อจำเป็นต้อง resolve DOI จริงๆ ระหว่างนั่งร้านกาแฟ (สมมติเจอ
paper ใหม่ต้องใส่ card ทันที) อย่ายิง `--all` ที่ resolve ทุก card
ที่ยังขาด DOI หรือ author รอบเดียว — เลือกทีละ citekey แทน:

```bash
maw citation doi mahajan2025
# dry run — ดูผลก่อน ยังไม่บันทึก

maw citation doi mahajan2025 --write
# พอใจแล้วค่อยเขียนทับ card จริง
```

รูปแบบเต็มของคำสั่งคือ
`maw citation doi [--write] [--rekey] [--all] [citekey…]` —
ใส่ citekey ต่อท้ายได้หลายตัว มันจะกรองเฉพาะ card ที่ชื่อ
ตรงกับ citekey ที่ระบุเท่านั้น ไม่แตะ card อื่นเลย ถ้าไม่ระบุ
citekey และไม่ใส่ `--all` มันจะเดา — เลือกทุก card ที่ยังไม่มี DOI
หรือยังไม่มี author ให้เองอัตโนมัติ ซึ่งบนเครือข่ายจำกัดแบบ
tethering คือสิ่งที่อยากเลี่ยง เพราะควบคุมจำนวน request ไม่ได้
เท่าระบุ citekey เอง

ข้อสังเกต: dry run กับ `--write` ยิง request ไป Crossref เท่ากัน
ต่างกันแค่ตอนท้ายว่าจะเขียนทับ card หรือไม่ — ตัวที่ประหยัด
tethering จริงๆ คือ "ระบุ citekey ให้แคบ" ไม่ใช่ "ไม่ใส่ --write"
ฉะนั้นถ้ารู้อยู่แล้วว่าอยากบันทึกแน่ ใส่ `--write` ไปเลยตั้งแต่
รอบแรกยังประหยัดกว่า — ไม่ต้องยิงซ้ำสองรอบ

## `serve` บน port 5556 — ถ้าไม่ว่าง มันขยับเองให้

`serve` (นามแฝง `visualize`) ผูก port default ไว้ที่ **5556**
เปลี่ยนได้ด้วย `--port` หรือ env `CITATION_VISUALIZE_PORT` แต่
กรณีทั่วไปไม่ต้องยุ่งอะไรเลย:

```bash
maw citation serve
```

ถ้าเคยเปิด `serve` ค้างไว้จากรอบก่อนแล้วลืมปิด (Ctrl+C ไม่ทัน)
พอเปิดรอบใหม่มันจะเจอ port 5556 ไม่ว่าง แล้วขยับไปหา port ถัดไป
เองอัตโนมัติ พร้อมบอกตรงๆ ว่าขยับไปที่ไหน:

```
⚠ port 5556 busy (an earlier serve is still running) — using 5557
✦ citation constellation (2D) — http://localhost:5557
```

ไม่ crash ไม่ค้างรอ EADDRINUSE เงียบๆ — บอกเลขที่ใช้จริงตรงๆ ให้
copy URL ไปเปิดต่อได้ทันที นี่คือเหตุผลอีกข้อที่ควรปิด `serve`
ด้วยมือทุกครั้งที่ดูเสร็จ — ไม่ใช่เพราะมันพัง แต่เพราะปล่อยไว้
เรื่อยๆ จะมี process ค้างสะสม กิน port ไปเรื่อยๆ โดยไม่จำเป็น

## กลับบ้านแล้วค่อย sync — ไม่มีอะไรค้างอยู่ในเมฆ

จบวันที่ร้านกาแฟแล้วกลับบ้าน ไม่มีขั้นตอน "sync" พิเศษต้องทำ
เพราะตลอดเวลาที่ใช้ backend ollama ไม่มีอะไรถูกส่งขึ้น cloud เลย
สักบรรทัด — card ที่แก้ก็เขียนลงดิสก์ทันทีตอนแก้ ไม่ใช่ queue
รอ sync ทีหลัง store ก็ update ทันทีตอน `index` รันเสร็จ ไม่มี
state ไหนแขวนคอยอยู่ที่ไหนทั้งนั้น

ข้อยกเว้นเดียวคือถ้าระหว่างวันสลับ backend ไปใช้ Cloudflare REST
ตามบทที่ 10 (ต้องมี `CF_ACCOUNT_ID` + `CF_API_TOKEN` จริง) — กรณี
นั้นข้อมูลออกไปนอกเครื่องแล้วจริง ต้องดูข้อควรระวังเรื่อง corpus
ที่ยังไม่ตีพิมพ์ตามบทนั้น แต่สำหรับ cafe mode ที่แนะนำในบทนี้
ทางเลือกที่ดีที่สุดคือปล่อยให้ ollama เป็น backend ตลอด — ไม่ต้อง
ตัดสินใจอะไรเพิ่ม ไม่ต้องกังวลเรื่องข้อมูลรั่วไหลระหว่างทาง เพราะ
มันไม่เคยออกจากเครื่องตั้งแต่แรก
