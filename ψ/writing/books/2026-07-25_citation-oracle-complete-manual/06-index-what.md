# บทที่ 6: Index คืออะไร ทำไมต้องทำ

พิมพ์คำว่า "tmux mouse paste" ลงไปในช่อง search แล้วมันเจอ
เอกสารเรื่อง clipboard handling — ทั้งที่ไม่มีคำว่า "paste"
ในเอกสารนั้นสักคำ นี่ไม่ใช่เวทมนตร์ นี่คือสิ่งที่บทนี้จะอธิบาย
ทีละขั้น ไม่มีสมการ แต่ต้องถูก

## 6.1 embed คืออะไร — ข้อความหนึ่งก้อนกลายเป็นตัวเลข 1024 ตัว

คำว่า "index" ในความหมายของ Citation Oracle ไม่ใช่การสร้าง
สารบัญตามตัวอักษร A-Z แบบพจนานุกรม มันคือการเอาข้อความของ
แต่ละ paper ไปแปลงเป็น**เวกเตอร์** — ตัวเลขทศนิยม 1024 ตัวเรียง
กันเป็นแถวเดียว แล้วเก็บแถวนั้นไว้แทนตัวเอกสาร

กระบวนการแปลงนี้เรียกว่า embed โมเดลที่เราใช้คือ bge-m3 —
รับข้อความเข้าไป คายตัวเลข 1024 มิติออกมา ทุกครั้ง ทุก paper
ได้ขนาดเท่ากันเป๊ะ ไม่ว่า paper นั้นจะยาวกี่บรรทัด

ทำไมต้อง 1024 ตัวเลข ไม่ใช่ 10 หรือ 10,000 — เพราะนี่คือ
ขนาดที่โมเดล bge-m3 ถูกฝึกมาให้ใช้ แต่ละมิติไม่มีชื่อ ไม่มีป้าย
กำกับว่า "มิตินี้แทนคำว่า sensor" มันไม่ได้ทำงานแบบนั้น สิ่งที่
สำคัญไม่ใช่มิติแต่ละอันเดี่ยวๆ แต่คือ**ตำแหน่งรวมของทั้งแถว**
ในพื้นที่ 1024 มิตินั้น — paper สองใบที่พูดเรื่องใกล้กัน ตำแหน่ง
ของมันในพื้นที่นั้นก็จะอยู่ใกล้กันตาม

จุดที่ทำให้ bge-m3 ใช้งานได้จริงกับ corpus ของเรา คือมันเป็น
multilingual — ไทยกับอังกฤษตกอยู่ใน vector space เดียวกัน
พิมพ์ค้นเป็นไทยก็เจอ paper ภาษาอังกฤษได้ ไม่ต้องแปลก่อนค้น
ไม่ต้องมีสองระบบแยกกันสำหรับสองภาษา

## 6.2 อะไรถูก embed — ไม่ใช่ทั้งไฟล์

ตรงนี้คือจุดที่คนเข้าใจผิดกันบ่อย คิดว่า index แล้วคือทั้งการ์ด
ทั้งไฟล์ .md ถูกดูดเข้าไปเป็นตัวเลขหมด — ไม่ใช่

สิ่งที่ถูก embed ต่อ 1 paper คือสามฟิลด์นี้ต่อกัน:

```
title + summary + thesis_relevance
```

แค่นั้น ในโค้ดจริงมันคือฟังก์ชันชื่อ `paperText()`:

```typescript
// The text we embed per paper: title carries the topic,
// summary + relevance carry the semantic meat that makes
// similarity meaningful.
function paperText(p: Paper): string {
  return [p.title, p.summary, p.thesis_relevance]
    .filter(Boolean)
    .join("\n\n");
}
```

comment ในโค้ดบอกเหตุผลตรงๆ — title บอกว่า paper นี้เรื่อง
อะไร ส่วน summary กับ thesis_relevance คือ "เนื้อความหมาย"
จริงๆ ที่ทำให้ similarity มีความหมาย สามฟิลด์นี้พอแล้ว

**ฟิลด์ที่ไม่ถูก embed**: doi, volume, pages, journal —
พวกนี้เป็น metadata ล้วนๆ ไม่มีเนื้อความให้ตีความ เอาไปแปลง
เป็นเวกเตอร์ก็ไม่มีประโยชน์ มีแต่จะทำให้ similarity เพี้ยน

ผลที่ตามมาโดยตรง — **เติม doi เข้าการ์ดเฉยๆ ไม่ต้อง index
ใหม่** เพราะ doi ไม่ได้อยู่ในข้อความที่ถูก embed ตั้งแต่แรก
เวกเตอร์เดิมยังถูกต้อง 100% ไม่มีอะไรเปลี่ยน แก้ title หรือ
summary ต่างหากที่ต้อง index ใหม่ เพราะนั่นคือฟิลด์ที่ไปเข้า
`paperText()` จริงๆ

ฝั่ง vault note ก็ถูก embed ด้วยถ้าเรียก `index --vault` — ดึง
มาจาก `ψ/memory/{learnings,retrospectives,resonance}` และ
`ψ/writing/research` ติด tag `kind: note` เอาไว้ ทำให้ search
ครั้งเดียวเจอทั้ง paper และความคิดของเราเองปนกันในผลลัพธ์
เดียว แยกด้วยไอคอน 📄 กับ 📝 — ผลลัพธ์จริงหน้าตาแบบนี้:

```
  [0.7913] 📄 paper \cite{mahajan2025}
           (low-cost-sensor-calibration)
           Mahajan & Helbing (2025)
  [0.8702] 📝 note (ψ/writing/research)
           Environmental prediction models for PM2.5
```

## 6.3 cosine similarity — ไม่มีสมการ แต่ต้องถูก

พอมี paper 75 ใบ (62 paper + 13 note) แต่ละใบเป็นแถวตัวเลข
1024 ตัว คำถามคือ paper A กับ paper B "ใกล้กัน" แค่ไหน — วัด
ยังไง

ลองนึกภาพแบบนี้ — เวกเตอร์แต่ละแถวไม่ใช่แค่จุด มันคือ**ลูกศร**
ที่ชี้ออกไปในทิศทางหนึ่งจากจุดศูนย์กลาง ลูกศรของ paper A กับ
ลูกศรของ paper B ชี้ไปทางเดียวกันมากแค่ไหน — นั่นคือสิ่งที่
cosine similarity วัด ไม่ใช่ระยะห่างของปลายลูกศร แต่เป็น
**มุม**ระหว่างสองลูกศรนั้น

ชี้ไปทางเดียวกันเป๊ะ ค่าออกมาเต็ม 1.0 — paper สองใบพูดเรื่อง
เดียวกันแทบทุกมิติ ตั้งฉากกัน ค่าออกมา 0 — ไม่มีความเกี่ยวข้อง
กันเลยในมุมมองของโมเดล ชี้ไปคนละทางสุดขั้ว ค่าติดลบ — แต่ใน
ทางปฏิบัติของ text embedding แทบไม่เจอค่าติดลบมากนัก ส่วนใหญ่
ผลลัพธ์ที่เห็นจะอยู่แถว 0 ถึง 1

ทำไมใช้มุม ไม่ใช้ระยะห่างตรงๆ (เหมือนวัดด้วยไม้บรรทัด) — เพราะ
เอกสารยาวกับเอกสารสั้นให้เวกเตอร์ที่ "ยาว" ไม่เท่ากันได้ (ความยาว
ของลูกศร) แต่เนื้อหาอาจจะพูดเรื่องเดียวกันทุกประการ วัดด้วยมุม
ตัดปัญหาความยาวลูกศรออกไปเลย เหลือแต่ทิศทาง — นี่คือเหตุผลที่
วงการ embedding เกือบทั้งหมดเลือก cosine ไม่ใช่ Euclidean
distance

ในโค้ดจริง ก่อนเทียบมุม เราทำ normalise เวกเตอร์ทั้งสองฝั่งก่อน
(หารด้วยความยาวของตัวมันเอง) เพราะทั้งสอง backend ที่เราใช้ไม่
ได้ normalise เวกเตอร์มาให้ตั้งแต่ต้น ถ้าไม่ normalise เอง ตัวเลข
ที่ได้จะปนกันระหว่าง "ทิศทางใกล้กัน" กับ "ความยาวเวกเตอร์ต่างกัน"
— สองเรื่องที่ไม่ควรปนกัน

## 6.4 ทำไม brute force พอ — ไม่ต้องมี ANN index

คำว่า brute force ในที่นี้หมายถึง —ตอน search เราไม่มี index
พิเศษอะไรช่วยข้ามแถวที่ไม่เกี่ยวข้องเลย เอา query มา embed
เป็นเวกเตอร์หนึ่งแถว แล้ววน**ทุกแถว**ใน store คำนวณ cosine
กับทุกแถวนั้นตรงๆ เรียงจากมากไปน้อย จบ

ฟังดูโง่ เพราะระบบค้นเวกเตอร์ระดับโปรดักชันจริง (เช่น Pinecone,
FAISS, LanceDB) มักมี ANN index — Approximate Nearest
Neighbor — โครงสร้างพิเศษที่ทำให้ไม่ต้องวนทุกแถว ข้ามได้เร็ว
กว่า brute force มาก แต่ต้องแลกกับความแม่นยำ (approximate
แปลว่าอาจพลาด neighbor จริงๆ ไปบ้าง) แล้วก็ต้องมี native
dependency ผูกติดมาด้วย

คำถามคือ — เราต้อง ANN ไหม ตอบด้วยตัวเลขที่วัดจริง corpus
เรามี 75 แถว ค้น 1 ครั้ง (embed query + brute-force cosine
ทั้ง 75 แถว) ใช้เวลา **0.221 วินาที** — เร็วกว่าที่คนกดปุ่มจะรู้สึก
ได้ด้วยซ้ำ

ตารางเดียวเข้าใจ:

| ขนาด corpus | brute force | ต้อง ANN ไหม |
|---|---|---|
| 75 แถว (เราตอนนี้) | 0.221 วิ | ไม่ต้อง |
| หลักพัน | ยังคาดว่าเร็วพอ (ยังไม่ได้วัด) | ยังไม่ต้อง |
| หลักล้าน | ช้าลงชัดเจน | ต้องคิดเรื่อง ANN |

corpus วิจัยระดับ PhD ไม่มีทางโตถึงหลักล้าน paper — 56 ใบ
ตอนนี้ บวก note ที่เราเขียนเอง รวม 75 แถว ต่อให้โตขึ้นอีก 10
เท่าก็ยังอยู่ในระดับที่ brute force รับมือได้สบายๆ แลกกับสิ่งที่
ได้กลับมา — ไม่ต้องมี native dependency ผูกกับเครื่อง ไม่ต้อง
compile อะไรพิเศษ ผลลัพธ์แม่นยำ 100% ไม่มีคำว่า approximate
มาปน

นี่คือหลักการที่ควรจำ — เลือกความซับซ้อนให้พอดีกับขนาดงานจริง
ไม่ใช่ขนาดงานในจินตนาการ ระบบ enterprise ต้อง ANN เพราะมี
เอกสารเป็นล้าน เรามี 75 ไม่มีเหตุผลอะไรให้แบกความซับซ้อนนั้น
มาด้วย

## 6.5 store คือไฟล์ธรรมดา ไม่มี database

ผล index ทั้งชุดไม่ได้เก็บใน SQLite ไม่ได้เก็บใน Postgres ไม่มี
database engine ไหนเข้ามาเกี่ยวข้องเลย เก็บเป็นไฟล์ธรรมดาสาม
ไฟล์ในโฟลเดอร์เดียว:

```
vectors.f32     # N × 1024 Float32 เรียงต่อกันเป็นแถวดิบ
meta.jsonl      # 1 บรรทัด = 1 paper/note — citekey, title, kind, ...
manifest.json   # { model, dim, count, updated }
```

`vectors.f32` คือก้อนตัวเลขล้วนๆ ไม่มี label ไม่มีชื่อ paper
ปนอยู่ในไฟล์นั้นเลย — รู้ว่าแถวที่ 5 คือ paper ไหนได้จาก
`meta.jsonl` บรรทัดที่ 5 ที่ตำแหน่งตรงกัน สองไฟล์นี้ผูกกันด้วย
ลำดับ ไม่ใช่ key ที่ต้อง join

`manifest.json` คือตัวที่ทำหน้าที่**จำ**ว่าชุดนี้ index ด้วย model
ตัวไหน จำ dimension เท่าไหร่ จำจำนวนแถว และวันที่ update
ล่าสุด นี่คือกลไกป้องกันความผิดพลาดที่สำคัญที่สุดของทั้งระบบ —
เพราะเวกเตอร์จากคนละ model เทียบกันไม่ได้เลย แม้จะมีมิติ 1024
เท่ากันก็ตาม พื้นที่ 1024 มิติของ bge-m3 กับพื้นที่ 1024 มิติของ
โมเดลอื่นไม่ใช่พื้นที่เดียวกัน ตัวเลขหน้าตาคล้ายกันแต่ความหมาย
คนละเรื่อง — สลับ model แล้วเทียบแถวเก่ากับแถวใหม่ปนกัน จะได้
ผลลัพธ์ที่ผิดแบบเงียบๆ ไม่มี error โผล่มาเตือน

ขนาดจริงบนดิสก์ทั้งโฟลเดอร์ **452 KB** สำหรับ 75 รายการ — ใน
นั้น `vectors.f32` เองกิน **300 KB** (75 × 1024 × 4 byte ต่อ
float) ส่วนที่เหลือคือ meta กับ manifest ซึ่งเป็น text ล้วน เบา
มาก

จุดที่น่าชอบใจของการเป็นไฟล์ธรรมดา — **ลบโฟลเดอร์ทิ้งได้เลย
แล้ว index ใหม่** ไม่มีอะไรพัง มันคือ derived data ล้วนๆ
สร้างจาก JSONL/card เดิมได้เสมอ ไม่ใช่ source of truth ไม่ต้อง
กลัวว่าลบผิดแล้วข้อมูลหาย เพราะของจริงอยู่ที่การ์ด `.md` กับ
JSONL อยู่แล้ว

## 6.6 ตารางตัดสินใจ — ตอนไหนต้อง index ใหม่ ตอนไหนไม่ต้อง

นี่คือตารางที่ควรแปะไว้ข้างจอ ตอบคำถามที่เจอบ่อยที่สุด — "ทำ
สิ่งนี้แล้ว ต้อง index ใหม่ไหม"

| ทำอะไร | ต้อง index ใหม่ไหม | เพราะอะไร |
|---|---|---|
| เติม `doi` ในการ์ด | **ไม่ต้อง** | doi ไม่ถูก embed |
| เติม `volume`, `pages` | **ไม่ต้อง** | metadata ล้วน ไม่ถูก embed |
| แก้ `title` | **ต้อง** | อยู่ใน `paperText()` โดยตรง |
| แก้ `summary` | **ต้อง** | อยู่ใน `paperText()` โดยตรง |
| แก้ `thesis_relevance` | **ต้อง** | อยู่ใน `paperText()` โดยตรง |
| เพิ่ม paper ใหม่เข้า corpus | **ต้อง** | ยังไม่มีแถวของมันใน store |
| เขียน vault note ใหม่ | ต้อง ถ้าอยาก search เจอ | ใช้ `index --vault` |
| สลับ embedding model | **ต้อง index ใหม่ทั้งชุด** | vector คนละ space เทียบกันไม่ได้ |
| ลบโฟลเดอร์ store ทิ้ง | ต้อง (แต่ไม่มีอะไรพัง) | derived data สร้างใหม่ได้เสมอ |

กฎง่ายๆ ที่สรุปจากตารางนี้ — ถ้าแก้ฟิลด์ที่**อยู่ใน** title /
summary / thesis_relevance ต้อง index ใหม่ ถ้าแก้ฟิลด์อื่นที่
เหลือทั้งหมด ไม่ต้อง เก็บกฎนี้ไว้ในหัว จะไม่ต้องเปิดโค้ดมาเช็คอีก

## ความซื่อสัตย์ที่ต้องพูดตรงๆ — bge-m3 ไม่บอก keyword

ตอนที่ search คืนผลลัพธ์มาว่า paper A ใกล้กับ query ของเรา
0.7913 — คำถามต่อมาที่ทุกคนอยากรู้คือ "ใกล้กันเพราะคำไหน"

bge-m3 ตอบคำถามนั้นไม่ได้ มันเป็น black box ในความหมายที่
จริงจัง — เราป้อนข้อความเข้าไป มันคายตัวเลข 1024 ตัวออกมา
แต่ไม่มีมิติไหนสักมิติที่แปลว่า "คำว่า calibration" หรือ "คำว่า
satellite" โดยตรง ความหมายกระจายอยู่ทั่วทั้ง 1024 มิติแบบที่
มนุษย์แกะย้อนกลับไม่ได้

ตรงนี้เป็นจุดที่ง่ายมากที่จะโกหกตัวเอง — เขียนหน้า serve ให้ดู
ฉลาด สร้างคำอธิบายที่ฟังดูมั่นใจว่า "ใกล้กันเพราะคำนี้ คำนั้น"
ทั้งที่จริงๆ โมเดลไม่ได้บอกแบบนั้นเลย เราเลือกไม่ทำแบบนั้น

สิ่งที่หน้า serve โชว์แทนคือ **term overlap ถ่วงน้ำหนักด้วย
IDF** — คำที่ปรากฏร่วมกันระหว่าง query กับผลลัพธ์ ถ่วงน้ำหนัก
ตามความหายากของคำนั้นในทั้ง corpus แล้วติดป้ายชัดเจนว่านี่คือ
**หลักฐานประกอบ ไม่ใช่สาเหตุ** — มันไม่ได้บอกว่า "โมเดลจับคู่
เพราะคำนี้" มันแค่บอกว่า "คำเหล่านี้ปรากฏร่วมกันด้วย ลองดูเป็น
