# บทที่ 3: เตรียมลงอุปกรณ์เพิ่มเติม — ของเสริมที่ลงเมื่อจำเป็น

บทที่แล้วบอกไปแล้วว่า ต้องมีจริงๆ มีแค่ `bun` ตัวเดียว ควรมีอีกตัวคือ
`ollama` สำหรับ search กับ index — นอกนั้นไม่ต้องมี ไม่ต้อง `bun install`
ไม่ต้อง database ไม่ต้อง API key

แต่ "ไม่ต้องมี" กับ "ใช้ไม่ได้เลย" เป็นคนละเรื่องกัน ของสี่ตัวในบทนี้ —
`sharp` `maw` `wrangler` `bibtex` — ไม่มีก็รันได้ปกติ มีก็ได้เพิ่มความสะดวก
บทนี้จะบอกทีละตัวว่า มีไว้ทำอะไร แล้วถ้าไม่มี จะเกิดอะไรขึ้นจริงๆ ไม่ใช่
เกิดอะไรขึ้น "ในทางทฤษฎี"

ปิดท้ายด้วยเรื่องที่ไม่อยากเล่าเท่าไหร่ แต่ต้องเล่า — วันที่เราเกือบลบ
`sharp` ออกจาก `package.json` ทั้งที่มันถูกใช้งานอยู่จริง เพราะ `ripgrep`
มองไฟล์ที่เราเขียนเองว่าเป็น binary


## ของเสริมสี่ตัว ภาพรวมก่อน

| เครื่องมือ | ใช้ทำอะไร | ไม่มีแล้วเป็นยังไง |
|---|---|---|
| `sharp` | แปลง SVG เป็น PNG ตอน `graph` | ได้ SVG อย่างเดียว (คมกว่าด้วยซ้ำ) |
| `maw` | เรียกผ่าน `maw citation <verb>` | ใช้ `./bin/citation <verb>` แทนได้ทุกอัน |

| `bibtex` | ตรวจว่า `.bib` compile ผ่านจริง | ได้ `.bib` ไฟล์ปกติ แค่ไม่มีคนยืนยัน syntax ให้ |

สี่ตัวนี้ไม่มีตัวไหนอยู่ใน `dependencies` เลยสักตัว — มีแค่ `sharp` ที่ขึ้น

`maw` `wrangler` `bibtex` เป็นโปรแกรมนอกระบบ ไม่ใช่ package ของ Node เลย
เรียกผ่าน path หรือ `import()` แบบ dynamic ทั้งหมด


## `sharp` — แปลง SVG เป็น PNG เท่านั้น

คำสั่ง `graph` วาดกราฟความคล้ายของ 62 paper ออกมาเป็น SVG ก่อนเสมอ —
ไม่มีเงื่อนไข ไม่ต้องมี `sharp` ก็ได้ไฟล์นี้ แล้วถ้า `sharp` ติดตั้งอยู่
ก็แปลง SVG ตัวนั้นเป็น PNG เพิ่มให้อีกไฟล์ เพื่อคนที่อยากได้ไฟล์แปะลง
Google Docs หรือ PowerPoint ที่ SVG ใช้ไม่สะดวก

โค้ดจริงอยู่ที่ `ψ/lab/citation/src/index.ts:1551` หน้าตาแบบนี้ (จัดบรรทัด
ใหม่เพื่อให้อ่านง่าย ของจริงเขียนบรรทัดเดียว):

```typescript
await Bun.write(svgPath, svg);   // SVG เขียนไปแล้วเสมอ

try {
  const { default: sharp } = await import("sharp");
  await sharp(Buffer.from(svg)).png().toFile(outPath);
  pngNote = `\n✦ png → ${outPath}`;
} catch {
  pngNote = `\n  (png skipped — 'sharp' not installed;` +
    ` the SVG above is the figure)`;
}
```

ไม่มี `sharp` ก็ไม่มี error ไม่มีอะไรค้าง — แค่ `pngNote` เปลี่ยนเป็น
ข้อความบอกว่า skip แล้วจบ คนรันคำสั่งเห็นข้อความนี้ต่อท้าย output ปกติ
ไม่ต้องไปเปิด log หาที่ไหน

แล้วเรื่อง "SVG คมกว่า" ไม่ใช่คำปลอบใจ — SVG เป็น vector จริง ซูมเข้าไป
เท่าไหร่เส้นก็คมเท่าเดิม ส่วน PNG ที่ `sharp` render ออกมาคือ raster ที่
ตรึงความละเอียดไว้ตาม pixel ที่กำหนดตอนนั้น จะเอาไปย่อ-ขยายทีหลังก็เสีย
รายละเอียด ใครไม่มี `sharp` เลยไม่ได้เสียของ ได้ไฟล์ที่ในหลายกรณีดีกว่าด้วย
ซ้ำ เว้นแต่ปลายทางรับได้แค่ raster เท่านั้น

`package.json` เขียนความตั้งใจนี้ไว้ในตัวเองเลย:

```json
"dependencies": {},
"optionalDependencies": {
  "sharp": "^0.33.5"
}
```

`optionalDependencies` คือ field มาตรฐานของ npm/bun — แปลว่า "ลองลงให้
ถ้าลงไม่ผ่าน (เช่นเครื่องไม่มี compiler ของ native module) ก็ข้ามไป ไม่ทำ
ให้ install ทั้งก้อนพัง" ต่างจาก `dependencies` ตรงที่ตัวนั้นพังปุ๊บคือ
`bun install` ทั้งคำสั่งพังตาม


## `maw` — ประตูที่สอง ไม่ใช่ทางเดียว

มีสองทางเรียกคำสั่งเดียวกัน:

```bash
./bin/citation status      # ต้องมีแค่ bun
maw citation status        # เหมือนกันทุกอย่าง สำหรับคนที่มี maw
```

ทั้งสองทางเรียก handler ตัวเดียวกันที่ export ออกมาจาก
`ψ/lab/citation/src/index.ts` — ไม่มี dispatch สองชุดให้ต้องดูแลคู่กัน
`bin/citation` เขียนไว้ตรงๆ ในคอมเมนต์ของตัวเองว่า:

```typescript
// The plugin and this shim share one implementation:
// ψ/lab/citation/src/index.ts exports the same `handler`
// that maw invokes, so there is no second dispatch path
// to keep in sync.
```

เขียนแค่ครั้งเดียว แก้ที่เดียว ทั้งสองทางได้ผลเหมือนกันเป๊ะ — verb ไหนใหม่
ก็ใหม่พร้อมกันทั้งคู่ ไม่มีเคสที่ `maw citation` ทำอะไรได้แต่ `./bin/citation`
ทำไม่ได้ หรือกลับกัน

ที่ต้องแยกสองทางเข้าเพราะ `maw` เป็น federation engine ของ oracle
family — ตัวที่ทำให้ oracle คุยกันข้าม repo ได้ (`maw hey`, `maw locate`)
ใครทำงานในระบบ oracle อยู่แล้วก็ใช้ `maw citation` ต่อเนื่องไปเลย แต่คนที่
โคลน repo นี้มาอ่านเฉยๆ ไม่มี oracle ecosystem ติดตั้งอยู่ ก็ยังใช้งานได้
เต็มรูปแบบผ่าน `./bin/citation` — ไม่ต้องไปหา `maw` มาลงก่อน

ส่วนที่ต่างกันจริงๆ มีแค่จุดเดียว คือวิธีหา **repo root** ตอนเริ่มทำงาน
ลำดับการหาคือ:

```text
CITATION_ROOT (ตั้งเองผ่าน env)
  → MAW_HOME (ถ้ามี maw)
  → ไล่ขึ้นจาก SCRIPT หา CLAUDE.md + ψ/
  → ไล่ขึ้นจาก cwd หา CLAUDE.md + ψ/
  → git rev-parse --show-toplevel
  → cwd (fallback สุดท้าย จริงๆ ไม่อยากมาถึงตรงนี้)
```

ขั้น "ไล่ขึ้นจาก SCRIPT" คือเหตุผลที่ `./bin/citation` เรียกจาก `/tmp`
หรือ directory ไหนก็ได้แล้วยังหา repo เจอ (commit `051014b`) — เพราะ
`bin/citation` เองอยู่ในไฟล์ระบบของ repo อยู่แล้ว ต่อให้ cwd ปัจจุบันไม่
เกี่ยวอะไรกับ repo เลยก็ตาม ส่วน `maw` ใช้ `MAW_HOME` เป็นหลัก เพราะ `maw`
มักจะ `cd` เข้า directory ของ plugin เองก่อนเรียก ทำให้ cwd ใช้ไม่ได้อยู่
แล้วในบริบทนั้น

ทำไมต้องแคร์เรื่องนี้ขนาดนี้ — เพราะ root ผิดคือความล้มเหลวแบบเงียบที่สุด
ที่มีในเครื่องมือนี้ ผิด root แล้วมันไม่ error ไม่ crash มันแค่รายงานว่า
"0 paper cards" เหมือนข้อมูลหายไปทั้งชุด ทั้งที่จริงๆ แค่มองผิด directory
เพราะงั้น `status` ถึงพิมพ์บอกไว้เสมอว่าใช้กฎไหนหา root มา — ให้เห็นทันที
ถ้ามันเดาผิด ไม่ต้องรอเจอ "0 cards" แล้วมานั่งงงทีหลัง


## `wrangler` — cloud embedder สำรอง เวลาไม่มี GPU local

`search` กับ `index` ต้องแปลงข้อความเป็น vector ก่อนเทียบกัน — งานนี้เรียก
ว่า embedding เครื่องมือนี้ลองสาม backend เรียงลำดับ ไม่ต้องตั้งอะไรเอง:

```text
ollama    → local, ใช้ GPU, ไม่มี token ไม่มี network
            (default เมื่อรันอยู่)
worker    → wrangler dev --port 18787
            (ใช้ wrangler login เดิม ไม่ต้องขอ token ใหม่)
cf-rest   → Cloudflare REST + CF_ACCOUNT_ID + CF_API_TOKEN
```

`wrangler` เข้ามาเกี่ยวตรงบรรทัดกลาง — มันคือ CLI ของ Cloudflare สำหรับรัน
Worker ตัวเดียวกับที่ deploy ขึ้น production ได้ให้รันบนเครื่องตัวเอง
(`wrangler dev`) worker ตัวนี้เปิดพอร์ต `18787` ทำหน้าที่แปลงข้อความเป็น
vector ผ่าน model เดียวกับที่ Cloudflare AI ให้บริการ (`@cf/baai/bge-m3`)
ข้อดีคือใช้ login ของ `wrangler` ที่มีอยู่แล้ว ไม่ต้องไปขอ API token ใหม่
มาตั้ง env ให้ยุ่งยาก

```bash
cd ~/.maw/plugins/cf-embed/worker
wrangler dev --port 18787
```

เครื่องที่รันจริงตอนเขียนหนังสือเล่มนี้ (m5 — Apple M5 Max) มี GPU ให้
`ollama` ใช้ผ่าน Metal อยู่แล้ว ทำให้ backend แรกสุดถูกเลือกเสมอ ไม่เคย
ต้องไปแตะ `wrangler` เลยในการทำงานจริง แต่เส้นทางนี้มีไว้เผื่อเครื่องที่ไม่มี
GPU แรงพอ หรือเผื่อทำงานจากเครื่องที่ไม่ได้ลง `ollama` ไว้ — ลด `ollama`
ในลิสต์ `ollama list` ให้ไม่มี `bge-m3` เมื่อไหร่ backend ก็ไหลลงไปหา
`wrangler` ให้เองอัตโนมัติ ไม่ต้องแก้โค้ด

ไม่มี `wrangler` เลยล่ะ — ก็แค่ backend ตัวกลางใช้ไม่ได้ ถ้า `ollama` ยัง
รันอยู่ก็ไม่มีผลอะไรเลยเพราะไม่เคยตกไปถึงตัวนั้น ถ้า `ollama` ก็ไม่มีด้วย
มันจะพยายามต่อ `http://localhost:18787/embed` แล้วเจอ connection refused
error message ที่ได้กลับมาบอกตรงๆ ว่าให้ไปรันคำสั่งไหนต่อ:

```text
Local embed worker unreachable at http://localhost:18787
— reuse the shared one:
cd ~/.maw/plugins/cf-embed/worker && wrangler dev --port 18787
```

ข้อความ error ชี้ทางแก้ให้เลย ไม่ต้องไปงมว่าต้องรันคำสั่งอะไร — นี่คือหลัก
เดียวกับ `sharp` : ของหายได้ แต่ต้องบอกให้ชัดว่าหายเพราะอะไร แก้ยังไง
ไม่ใช่ปล่อยให้ stack trace งงๆ โผล่มาเฉยๆ


## `bibtex` — ของที่ไม่ได้ "รัน" แต่ "ตรวจ"

สามตัวข้างบนเป็น dependency ที่โค้ดเรียกใช้ตรงๆ ตอนทำงาน ส่วน `bibtex`
(จาก TeX Live) ไม่ได้ถูกโค้ดเรียกเลยสักบรรทัด — มันคือเครื่องมือแยกที่ใช้
**หลังจาก** `citation bib` สร้างไฟล์ `.bib` เสร็จแล้ว เพื่อตอบคำถามที่
สำคัญกว่าที่คิด: ไฟล์ที่ generate มานี้ ใช้กับ `\cite{}` จริงในวิทยานิพนธ์
ได้ไหม

`.bib` เป็นแค่ข้อความธรรมดา เขียนผิด field เขียนวงเล็บไม่ครบ ก็ยังเป็น
ไฟล์ที่เปิดอ่านได้ปกติ ไม่มี error ตอนสร้าง ความผิดจะโผล่ตอน compile
LaTeX เท่านั้น — เพราะงั้นจะรู้ว่าไฟล์ใช้ได้จริง ต้องเอาไปให้ `bibtex`
ประมวลผลจริงสักครั้ง ไม่ใช่แค่เปิดอ่านด้วยตา

ผลที่ได้จริงบนเครื่องนี้ ผ่าน TeX Live 2026: 62 entry ใน `.bib` แปลงเป็น
62 `\bibitem` ครบทุกใบ warning ที่ `bibtex` รายงานกลับมา — ศูนย์

ไม่มี TeX Live ลงอยู่ล่ะ — `.bib` ก็ยังใช้งานได้ปกติ เปิดด้วย Overleaf
หรือ editor ที่รองรับ BibTeX เอง ระบบพวกนั้นจะ compile และรายงาน error
ให้เองตอนอัปโหลด แค่จะไม่มีการตรวจ local ก่อน push เท่านั้น ต่างจาก
`sharp` `maw` `wrangler` ตรงที่ `bibtex` ไม่เคยเป็นส่วนหนึ่งของ flow การ
ทำงานเลย มันเป็นขั้นตอน QA ที่แยกออกมาต่างหาก


## หลักการ: ทำ optional dependency ให้ optional จริง

สามตัวแรกสอนบทเรียนเดียวกันซ้ำสามครั้ง — วิธีทำให้ dependency "ไม่มีก็ได้"
จริงๆ ไม่ใช่แค่พูดไว้ใน README คือ **dynamic import ใน `try`/`catch`**
รูปแบบทั่วไปเขียนได้แบบนี้:

```typescript
let note: string;
try {
  const mod = await import("some-optional-package");
  // ใช้ mod ทำงานที่ต้องพึ่งมัน
  note = "ทำสำเร็จด้วย some-optional-package";
} catch {
  // import ไม่เจอ (ไม่ได้ลง) หรือ native module
  // build ไม่ผ่านบนเครื่องนี้ ก็ตกลงมาที่นี่เหมือนกัน
  note = "ข้ามขั้นนี้ไป — ตัวหลักยังทำงานต่อได้ปกติ";
}
```

จุดสำคัญสามจุด:

**หนึ่ง** — ใช้ `import()` แบบ dynamic ไม่ใช่ `import x from "x"` แบบ static
บนหัวไฟล์ เพราะ static import ถูก resolve ตอน bundle/parse ไฟล์ ถ้า
package ไม่มีอยู่จริง โปรแกรมทั้งตัวจะพังตั้งแต่ยังไม่ทันรัน — เหมือนที่
`sharp` เคยเป็นปัญหาให้ต้องถอดออกจาก `dependencies` ตอนแรก (commit
`5475615`, บทที่ 2 เล่าไว้แล้ว) `import()` แบบ dynamic คืนเป็น Promise
ทำให้ error (ถ้ามี) โผล่ตอน `await` เท่านั้น ดักด้วย `try`/`catch` ได้ตรงๆ

**สอง** — งานหลัก (เขียน SVG, เขียน `.bib`, ทำ search) ต้องเกิด **ก่อน**
เข้าบล็อก `try` เสมอ ไม่ใช่เขียนกลับด้าน จุดที่พึ่ง optional dependency
ต้องเป็นแค่ "ของแถม" ที่เพิ่มเข้ามาทีหลังงานจริงเสร็จแล้ว ไม่ใช่ตัวปิดท้าย
ที่ทั้งระบบรอ

**สาม** — ข้อความใน `catch` ต้องบอกให้ชัดว่า "ข้ามไปแล้วนะ" ไม่ใช่กลืน
error เงียบๆ คนใช้ต้องเห็นว่ามีขั้นตอนหนึ่งถูกข้าม ไม่ใช่เข้าใจผิดว่าทุก
อย่างเสร็จสมบูรณ์

สามข้อนี้เขียนซ้ำได้กับ dependency ตัวไหนก็ตามที่อยากให้ "มีก็ดี ไม่มีก็ไม่
เป็นไร" จริงๆ — ไม่ใช่แค่ประกาศไว้เฉยๆ ว่าเป็น optional


## เคส NUL byte — ตอนที่ ripgrep มองไฟล์เราเป็น binary

เรื่องนี้เกิดในเซสชันเดียวกับที่เขียนบทนี้พอดี เลยเล่าตรงๆ ไม่ปรุงแต่ง

คำสั่ง `bib` ต้องเรียงลำดับ entry สองแบบ — เรียงตาม citekey เฉยๆ หรือ
เรียงตาม topic ก่อนแล้วค่อยตาม citekey ในกลุ่ม สำหรับแบบหลัง ต้องสร้าง
compound sort key ขึ้นมาตัวเดียวจากสองค่า แล้วเลือกตัวคั่นที่ไม่มีทาง
ไปชนกับตัวอักษรจริงในชื่อ topic หรือ citekey — `\u0000` (NUL) เหมาะสุด
เพราะมันเรียงมาก่อนตัวอักษรพิมพ์ได้ทุกตัวเสมอ ความคิดตรงนี้ไม่ผิด ปัญหา
อยู่ที่ *วิธีเขียน*:

```typescript
// เขียนแบบนี้ — NUL เป็น byte จริงในไฟล์ ไม่ใช่ escape
const sortKey = (e) => `${e.topic} ${e.key}`;
```

บรรทัดข้างบนแค่ตัวอย่างรูปแบบปัญหา ของจริงมี NUL อยู่ตรงกลาง string
literal นั้นเป็น byte 0x00 ตัวจริง เขียนเองไม่ทันสังเกตเพราะ editor ไม่
แสดงตัวมันให้เห็น หน้าตาในไฟล์เลยดูปกติทุกอย่าง

พังตรงไหน — ripgrep เช็คว่าไฟล์เป็น text หรือ binary จาก content ของ
มันเอง เจอ byte 0x00 ตรงไหนก็ตัดสินว่าไฟล์นี้เป็น binary ทันที พอเป็น
binary การรายงาน match ที่กำลังไล่หาก็หยุดกลางทางแบบเงียบๆ ไม่มี error
ไม่มี warning บอกว่า "เตือนนะ ไฟล์นี้แปลกๆ" — แค่หยุดเฉยๆ

ตอนนั้นกำลังจะถอด `sharp` ออกจาก `optionalDependencies` เพราะคิดว่าไม่
ได้ใช้แล้ว (จำ `sharp` จากบทนี้ได้ไหม — ตัวที่แปลง SVG เป็น PNG) เลยรัน
`rg sharp` ในไฟล์นี้เพื่อเช็คก่อนลบ ผลที่ได้กลับมามีแค่สองบรรทัด — บรรทัด
22 ที่เป็นคอมเมนต์เรื่องฟอนต์ พูดถึงคำว่า "sharp/librsvg" ผ่านๆ (ไม่ใช่
จุดที่เรียกใช้งานจริง) กับข้อความปิดท้าย `binary file matches`

จากผลลัพธ์แค่นี้ เกือบสรุปผิดไปแล้วว่า `sharp` ไม่ได้ถูกเรียกใช้จริงที่ไหน
เลยในไฟล์ ทั้งที่จุดเรียกใช้งานจริง — `await import("sharp")` ในบล็อก
`try`/`catch` ที่อธิบายไปตอนต้นบทนี้เอง ที่บรรทัด 1551 — ไม่ถูกรายงานออก
มาให้เห็นเลยสักครั้ง เพราะ `rg` หยุดไปแล้วตั้งแต่เจอ NUL ระหว่างทาง เกือบ
ลบ `sharp` ออกจาก `package.json` ทั้งที่มันถูกใช้งานอยู่จริง

ทางแก้ตรงไปตรงมา — เขียน `\u0000` เป็น **escape ในซอร์สโค้ด** แทนที่จะ
เป็น byte จริงในไฟล์:

```typescript
// \u0000 เขียนเป็น ESCAPE เสมอ ห้ามเป็น byte จริง —
// byte จริงทำให้ ripgrep มองไฟล์นี้เป็น binary แล้ว
// หยุดรายงาน match แบบเงียบๆ มันเรียงก่อนอักษรพิมพ์
// ได้ทุกตัว จึงยังเป็นตัวคั่นที่ปลอดภัยเหมือนเดิม
const sortKey = (e) =>
  byTopic ? `${e.topic}\u0000${e.key}` : e.key;
```

ผลลัพธ์ตอนรันเหมือนเดิมทุกอย่าง — sort ได้ output เดียวกัน byte ที่เขียน
ลงไฟล์เดียวกัน ต่างกันแค่ *ในซอร์สโค้ด* ตอนนี้เป็นตัวอักษรหกตัวที่คนอ่าน
และเครื่องมืออ่านออก แทนที่จะเป็น byte เดียวที่มองไม่เห็นและทำให้เครื่องมือ
สับสน (commit `4204da2`)

บทเรียนที่เอาไปใช้ที่ไหนก็ได้ ไม่ใช่แค่กับ repo นี้ — เจอ **"binary file
matches"** จาก `rg` หรือ `grep` เมื่อไหร่ อ่านมันให้ถูกความหมาย มันไม่ได้
แปลว่า "ไม่มีอะไรตรงนั้น" มันแปลว่า **เครื่องมือยอมแพ้กับไฟล์นี้แล้ว** หยุด
ไล่หาไปเลยตั้งแต่จุดที่มันตัดสินใจว่าเป็น binary — จะเชื่อผล negative จาก
`rg` ได้เต็มที่ ต้องมั่นใจก่อนว่าไฟล์เป็น text ล้วนจริงๆ ไม่มี byte แปลกปลอม
ซ่อนอยู่สักตัว ถ้าไม่แน่ใจ เปิดไฟล์อ่านตรงๆ หรือใช้ `rg -a` (บังคับให้
ค้นแบบ text) ดีกว่าเชื่อผลเงียบๆ ที่อาจเป็นแค่การยอมแพ้กลางทาง
