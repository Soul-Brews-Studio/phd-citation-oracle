## 15.1 `bib` ทำงานยังไง — ทำไม "et al." ไม่ใช่ชื่อคน

คำสั่ง `maw citation bib` อ่านการ์ดทุกใบใน `ψ/papers/` ดึง
frontmatter ออกมาเป็น field เก้าตัว (author, title, journal,
year, volume, number, pages, doi, note) เรียงใส่ template
ของ `@article{}` แล้วเขียนทับ `artifacts/citation.bib` ใหม่
ทั้งไฟล์ทุกครั้งที่รัน — การ์ดคือความจริง ไฟล์ .bib เป็นแค่
ผลลัพธ์ที่ generate ซ้ำได้เสมอ

ปัญหาที่เจอตั้งแต่ต้นคือคำว่า "et al." เอง — ภาษาละติน แปลว่า
"และคนอื่นๆ" แต่ BibTeX ไม่รู้จักคำนี้ในฐานะคำพิเศษ มันรู้จัก
แค่ field `author` ที่คั่นด้วยคำว่า `and` แล้วสมมติว่าทุกก้อน
ที่คั่นด้วย `and` คือชื่อคนหนึ่งคน

พอเจอ string แบบ "Taneepanichskul, N., et al." ทั้งก้อน
BibTeX จะพยายามเดาว่านี่คือนามสกุลของคนหนึ่งคน — ผลคือ
ชื่อพิมพ์ผิดออกมาบนหน้ากระดาษจริง ทางแก้ที่ BibTeX เข้าใจ
คือคำว่า `others` เฉยๆ ใส่เป็นชื่อคนสุดท้ายในลิสต์ แล้ว
citation style ทั่วไป (unsrt, apalike ที่ใช้กันแพร่หลาย) จะรู้
เองว่าต้องพิมพ์ออกมาเป็น "et al." ให้ — ไม่ต้องเขียนคำว่า
et al. ลงในไฟล์ .bib เองเลย

ฟังก์ชันที่ทำเรื่องนี้อยู่ใน `bibAuthors()`:

```typescript
function bibAuthors(authors: string[]): string {
  const named: string[] = [];
  let truncated = false;
  for (const a of authors) {
    const cleaned = a
      .replace(/,?\s*\bet\s+al\.?\s*$/i, "")
      .trim();
    if (cleaned !== a.trim()) truncated = true;
    if (cleaned) named.push(bibEscape(cleaned));
  }
  return [...named, ...(truncated ? ["others"] : [])]
    .join(" and ");
}
```

ตัด "et al." ท้ายชื่อออกทุกตัวในลิสต์ ถ้าตัดแล้วต่างจาก
ของเดิม แปลว่าเคยมีการตัดจริง — ตั้ง flag `truncated` แล้ว
ค่อยเติมคำ `others` เข้าไปเป็นก้อนสุดท้ายก่อน join ด้วย
`and` ทั้งหมด ผลคือ style จะพิมพ์กลับมาเป็น "et al." ให้เอง
ตอน render บรรณานุกรมจริง — ไม่ใช่เราพิมพ์คำนี้ตรงๆ

ฟังก์ชันถัดมาที่ประกอบทุก field เข้าด้วยกันคือ `bibEntry()`
— หา field ที่ชื่อยาวสุดมาตั้ง width แล้ว pad ชื่อ field อื่น
ให้ column `=` ตรงกันทั้งก้อน field ไหนค่าว่าง (เช่นการ์ดไม่มี
`issue`) ถูก filter ทิ้งไปเงียบๆ ไม่เขียนเป็นบรรทัดเปล่าลงไฟล์
ผลคือทุก entry อ่านง่ายเท่ากันไม่ว่าการ์ดต้นทางจะมี field
ครบแค่ไหน — ความเรียบร้อยของ `.bib` ไม่ได้มาจากวินัยตอน
เขียนการ์ด แต่มาจากตัว formatter เอง

ไฟล์ที่ได้ขึ้นต้นด้วย header สี่บรรทัดเสมอ บอกที่มา จำนวน
entry และคำเตือนว่าอย่าแก้ไฟล์นี้ตรงๆ

```
% Citation Oracle ✦ — generated by "citation
% bib" from ψ/papers/
% 62 citable entries of 62 cards · 61 with a DOI
% The cards are the source of truth: edit those,
% not this file.
% Regenerate: citation bib
```

การประกอบแต่ละ entry เป็นข้อความจริงอยู่ใน `bibEntry()` —
รับ field เป็น array ของคู่ `[ชื่อ, ค่า]` กรองตัวที่ค่าว่างทิ้ง
ก่อน แล้วค่อยจัด indent

```typescript
function bibEntry(
  fields: Array<[string, string]>,
  key: string,
  type = "article",
): string {
  const width = Math.max(
    ...fields.map(([k]) => k.length),
  );
  const body = fields
    .filter(([, v]) => v)
    .map(([k, v]) => `  ${k.padEnd(width)} = {${v}}`)
    .join(",\n");
  return `@${type}{${key},\n${body}\n}`;
}
```

`type` เผื่อไว้เป็น `@article` เป็น default เสมอ เพราะ
corpus ทั้ง 62 ใบเป็นวารสารล้วน — วันไหนมี conference
paper หรือ report เข้ามา ค่อยขยาย field นี้ตอนนั้น ไม่ต้องรื้อ
โครงสร้างเดิม

field `note` ก็มีบทบาทเงียบๆ อยู่หนึ่งอย่าง — มันดึงมาจาก
`verified:` ใน frontmatter ของการ์ด กลายเป็น "verified via
crossref 2026-07-25" ต่อท้ายทุก entry ที่เคยผ่านการเทียบกับ
Crossref แล้ว การ์ดไหนไม่มีบรรทัดนี้ในไฟล์ผลลัพธ์ แปลว่ายัง
ไม่เคยถูกยืนยัน — เปิด `citation.bib` แล้วหา entry ที่ไม่มี
`note` เลย เจอแค่ใบเดียวคือ `jarernwong2021` (รายละเอียด
อยู่หัวข้อ 15.7) นี่คือวิธี grep หาการ์ดที่ยังไม่ verify แบบไม่
ต้องเปิดการ์ดทีละใบ

ยังมี flag `--by-topic` ให้เรียง entry ตาม 6 taproot ของ
corpus แทนเรียงตามตัวอักษร คั่นแต่ละกลุ่มด้วยบรรทัด
`% ── <topic> ──` — เอาไว้ตรวจว่าแต่ละ topic มีกี่ paper
รองรับได้จริง โดยไม่ต้องนับมือจากการ์ด

## 15.2 การ์ดที่ไม่ครบ = comment ไว้ ไม่ลบ

หลักการเดียวกับ Rule 1 — "Nothing is Deleted" — ถูกเขียนลง
ไปในโค้ดของ `cmdBib` ตรงๆ การ์ดไหนไม่มี author เลยสักคน
จะถูกตัดออกจากกลุ่ม "citable" แต่ไม่ได้หายไปจากไฟล์เฉยๆ

โค้ดเช็คห้าอย่างต่อการ์ด — authors, title, journal, year, doi
สี่อย่างแรกถ้าขาดไปอย่างใดอย่างหนึ่ง การ์ดใบนั้นเข้ากลุ่ม
"withheld" ส่วน doi อย่างเดียวไม่บังคับ เพราะการ์ดที่มี
ผู้เขียน ชื่อเรื่อง journal ปี ครบทุกอย่าง ก็ cite ได้จริงอยู่แล้ว
แม้ไม่มี DOI — `jarernwong2021` คือตัวอย่างจริงของกรณีนี้
(รายละเอียดอยู่หัวข้อ 15.7)

การ์ด withheld จะถูกเขียนลงท้ายไฟล์เป็น comment ทั้งก้อน
นำหน้าด้วยบรรทัดบอกว่าขาด field ไหน แล้วบอกวิธีแก้ต่อท้าย
ด้วย `citation doi --write` — ไม่ใช่แค่หายเงียบๆ จากไฟล์

```
% ── withheld: 2 card(s) not citable yet ──
% Kept here rather than dropped — the gap
% is part of the record. Fill them with:
% citation doi --write
%
% <citekey> — missing: authors
% % @article{...}
```

ตอนนี้ (25 กรกฎาคม 2026) ทั้ง 62 การ์ดครบทุก field ที่
บังคับแล้ว — ไม่มีการ์ดไหนอยู่ในกลุ่ม withheld อีกต่อไป
บล็อกนี้เลยไม่ปรากฏใน `citation.bib` ตัวปัจจุบัน แต่กลไกยัง
อยู่ในโค้ด รอทำงานทันทีที่มีการ์ดใหม่เข้ามาแบบข้อมูลไม่ครบ
ไม่ต้องรอแก้โค้ดใหม่ตอนนั้น

ที่ตั้งใจไม่บังคับ doi ก็มีเหตุผลของมัน — งานวิจัยถูกอ้างอิงกัน
มาเป็นร้อยปีก่อนจะมี DOI เกิดขึ้นด้วยซ้ำ สิ่งที่ทำให้ paper
หนึ่งใบ citable คือมันมีคนเขียน มีชื่อเรื่อง มีที่ตีพิมพ์ มีปีที่
ตีพิมพ์ — DOI เป็นแค่ลิงก์สะดวกที่มาทีหลัง ไม่ใช่นิยามของ
การอ้างอิง `jarernwong2021` เลยยัง cite ได้เต็มรูปแบบทั้งที่
Crossref ไม่รู้จักมันเลย

## 15.3 ยืนยันด้วย bibtex จริง — 62 entry, 62 `\bibitem`, 0 warning

`citation bib` บอกตัวเองว่าเขียนไฟล์สำเร็จ แต่คำว่า "สำเร็จ"
ของสคริปต์ตัวเอง ไม่เท่ากับ "ไฟล์นี้ใช้กับ LaTeX ได้จริง" —
วิธีเดียวที่พิสูจน์ได้คือเอาไปรันผ่าน bibtex ตัวจริง ไม่ใช่เชื่อ
exit code 0 ของตัวเอง

รันด้วย TeX Live 2026 บนเครื่อง — เอกสารทดสอบใช้
`\nocite{*}` ดึงทุก entry เข้ามาโดยไม่ต้อง cite ทีละตัว แล้ว
ปล่อยวงจร latex → bibtex → latex วนสองรอบตามธรรมเนียม
ของ BibTeX (รอบแรก latex สร้าง `.aux` ให้ bibtex อ่าน รอบ
บิบเท็กซ์ผลิต `.bbl` แล้วรอบ latex ที่สองค่อยดึง `.bbl` มา
ประกอบเป็นบรรณานุกรมจริง)

ผลที่ได้ — bibtex อ่านเจอ 62 entry ตรงกับจำนวนใน
`citation.bib` เป๊ะ ผลิต `\bibitem` ออกมาใน `.bbl` ครบ 62
รายการ ไม่มี entry ไหนถูกข้าม ไม่มี entry ไหนซ้ำ และไม่มี
warning ออกมาเลยสักบรรทัดเดียว — 0 warning

ตัวเลขนี้สำคัญกว่าที่ฟังดู เพราะ bibtex เตือนหลายแบบที่
สคริปต์ของเราตรวจเองไม่ได้ เช่น field ที่ style ต้องการแต่
ขาด citekey ซ้ำกันสองรายการ วงเล็บปิดไม่ครบในตัวข้อความ
ตัวอักษรพิเศษอย่าง `&` หรือ `%` ที่ไม่ได้ escape (`bibEscape()`
ป้องกันเรื่องนี้ไว้ตั้งแต่ตอนเขียนแต่ละ field แล้ว) — 0
warning แปลว่าไม่มีอะไรจากรายการทั้งหมดนั้นหลุดออกมาเลย

เหตุผลที่ต้องแยกสองคำตอบนี้ออกจากกันเลยคือ "citation bib
รันจบ" กับ "citation bib รันจบ **และ** ไฟล์ที่ได้ใช้ในเอกสาร
จริงได้" เป็นคนละคำถาม สคริปต์ของเราตรวจได้แค่ว่ามัน generate
ไฟล์สำเร็จตาม template ที่เราเขียนเอง — ถ้า template นั้นเอง
มีจุดผิดที่เราไม่รู้ตัว สคริปต์ก็จะรายงานว่า "สำเร็จ" อยู่ดี
เพราะมันไม่มีทางเห็นความผิดของตัวเอง bibtex ตัวจริงเป็น
คนละระบบ เขียนโดยคนละคน ไม่รู้จัก field ของเรามาก่อน — ผล
ที่ตรงกันระหว่างสองระบบที่ไม่รู้จักกันเลย คือหลักฐานที่หนักแน่น
กว่าการเชื่อ exit code ของตัวเองเยอะ

ขั้นตอนที่ใช้จริงเป็นแบบมาตรฐานของ BibTeX ทุกตำรา — สร้าง
เอกสารทดสอบขั้นต่ำสุดก่อน

```bash
pdflatex citecheck.tex   # รอบ 1: สร้าง .aux
bibtex   citecheck       # อ่าน .aux + citation.bib → .bbl
pdflatex citecheck.tex   # รอบ 2: ดึง .bbl มาประกอบ
grep -c '\\bibitem' citecheck.bbl   # นับ = 62
grep -i warning citecheck.blg       # ว่างเปล่า = 0
```

ไม่มีขั้นตอนไหนพิเศษ ไม่มี flag ลับ — ความหนักแน่นของผลลัพธ์
ไม่ได้มาจากวิธีตรวจที่ซับซ้อน แต่มาจากการที่มันเป็นเครื่องมือ
มาตรฐานที่ใครก็รันซ้ำได้ ไม่ต้องเชื่อคำพูดของเรา รันเองก็เห็น
ผลเดียวกัน

al." ที่มากับ corpus ตั้งแต่ต้น — ระบบเดาว่าใครคือ first
author จาก string สั้นๆ นั้นตรงๆ ถ้า string ต้นทางเขียนชื่อ
ผิดคน citekey ก็ผิดตามไปด้วยตั้งแต่ก่อนที่การ์ดจะถูกสร้างขึ้น
มาด้วยซ้ำ อย่าง `buya2025` เดิมชื่อ
`taneepanichskuld2025` — เอาผู้เขียน **คนสุดท้าย** มาใส่
เป็นคนแรก แล้วยังสะกดผิดด้วย (ตัว "d" เกินมาที่ท้าย
Taneepanichskul) ตัวจริงคือ Buya, S.

ที่หนักกว่านั้นคือชื่อ "Amnuaylojaroen, T." โผล่เป็น citekey
เดิมของ **สอง** การ์ดที่ไม่เกี่ยวข้องกัน — `buya2023` (ชื่อ
เดิม `amnuaylojaroen2023`) กับ `wongnakae2023` (ชื่อเดิม
`amnuaylojaroen2023b`) การ์ด `buya2023` เก็บ
`authors_upstream` ไว้เต็มลิสต์ว่า "Amnuaylojaroen, T." กับ
"Parasin, N." — ทั้งสองชื่อนี้ไม่ปรากฏอยู่ในรายชื่อผู้เขียนจริง
ของบทความเลยสักคน (ผู้เขียนจริงคือ Buya, S., Usanavasin,
S., Gokon, H., Karnjana, J.) แปลว่านี่ไม่ใช่แค่สลับลำดับหรือ
สะกดผิด แต่เป็นการเอาผู้เขียนของ paper อื่นมาแปะผิดใบไปเลย
— เกิดกับสองการ์ดพร้อมกันในคอร์ปัสเดียวกัน

title แต่งขึ้นเองมีจุดเดียวคือ `she2019` — เคสเดียวกับที่เล่า
ไว้ในบทที่ 14 title ที่ Gemini แต่งไว้อยู่คู่กับ DOI ที่ถูกต้อง
จนกว่าจะ verify ด้วยการเทียบ title similarity แล้วได้แค่ 0.33

journal ผิดมีจุดเดียวคือ `thongsame2024` — corpus เดิมเขียน
journal ไว้ว่า Atmospheric Pollution Research แต่ Crossref
บอกว่าตัวจริงคือ Atmospheric Environment: X citekey เดิมของ
การ์ดใบนี้คือ `atmosphericpollution2024` — ชื่อ citekey เอง
ก็ auto-generate มาจาก journal ที่ผิด ความผิดพลาดเลยถูก
ฝังลงไปในตัวตัวระบุของการ์ดตั้งแต่ต้น ไม่ใช่แค่อยู่ใน field
เดียว จนกว่าจะ rekey ตาม authors ที่ verify แล้วถึงหลุดออกมา

volume ผิดสองจุดมีที่มาต่างกัน `buya2025` เขียนว่า volume
41 แต่ 41 คือเลขหน้าแรกของบทความ (`pages: 41-52`) ไม่ใช่
volume — volume จริงคือ 36 ตัวเลขสองตัวนี้อยู่ใกล้กันใน
citation string ต้นทาง จนสลับตำแหน่งกันได้ง่ายๆ ส่วน
`chen2024` เขียนว่า volume 912 จริง 914 — ต่างกันแค่หลัก
เดียว ไม่มีรูปแบบอธิบายได้ชัดเท่า buya2025 เป็นแค่ตัวเลข
คลาดเคลื่อนเฉยๆ

ทุกการ์ดที่ถูก rekey ยังเก็บ citekey เดิมไว้ที่ field `aka:`
— `buya2025` มี `aka: taneepanichskuld2025`
`thongsame2024` มี `aka: atmosphericpollution2024` เหมือน
กันทุกใบ ไม่มี citekey เดิมใบไหนถูกลบทิ้งจริงๆ แค่เปลี่ยน
บทบาทจาก "ชื่อหลัก" มาเป็น "ชื่อสำรองที่ตามรอยได้" — ใครอยาก
รู้ว่า `buya2025` เคยชื่ออะไรมาก่อน เปิดการ์ดแล้วเจอคำตอบ
ทันที ไม่ต้องขุด git log

การ rekey มีผลกระเพื่อมไปที่ store ด้วย — ชื่อไฟล์การ์ดเปลี่ยน
citekey ในการ์ดเปลี่ยน แต่ vector store ที่ index ไว้ก่อนหน้า
ยังผูก embedding เก่ากับ citekey เก่าอยู่ ตัวคำสั่ง `doi --write`
เองเลยเตือนต่อท้ายทุกครั้งที่ rekey เกิดขึ้นจริงว่า "Re-index so
the store matches the new keys: citation index --vault" —
ไม่ใช่แค่แก้การ์ดแล้วจบ ต้อง index ใหม่ด้วยไม่งั้น `search`
กับ `graph` จะยังพูดถึง citekey ที่ไม่มีการ์ดรองรับแล้ว

นอกจาก 18 จุด error ยังมีอีก 24 การ์ดที่ author list ถูกเติม
ให้ครบ — ไม่นับเป็น error เพราะไม่ใช่ชื่อผิดคน แค่ไม่ครบ
21 ใบในนั้นตัดท้ายด้วย "et al." (ที่ `bibAuthors()` ในหัวข้อ
15.1 จัดการให้อัตโนมัติ) ส่วนอีก 3 ใบสั้นแบบไม่มีเครื่องหมาย
บอกไว้เลยว่าตัดมา — `she2019` เป็นหนึ่งในสามนั้น หายผู้เขียน
คนที่ห้า Shi, Y. ไปเงียบๆ ไม่มีแม้แต่ "et al." บอกว่าตัดมา
ต้องเทียบกับ Crossref ถึงจะรู้ว่าขาดคนหนึ่งไป

## 15.5 เลขหน้าจากเลขท้าย DOI — บั๊กที่เงียบที่สุด

ในเจ็ดจุดที่เลขหน้าผิด สี่จุดมีต้นตอเดียวกัน คือเอาเลขท้าย
ของ DOI มาเขียนเป็นเลขหน้าตรงๆ โดยไม่ได้ตั้งใจ

`yu2023` เขียนไว้ว่า pages 363 — ดู DOI ของมัน
`10.1038/s41612-023-00363-w` ตัวเลขก่อน `-w` คือ 00363
ตัดศูนย์นำหน้าออกเหลือ 363 — นั่นคือที่มาของเลขหน้าที่เขียน
ไว้ เลข article จริงตาม Crossref คือ 41

อีกสามจุดเป็นรูปแบบเดียวกันเป๊ะ

| citekey | DOI ลงท้าย | เขียนไว้ | จริง |
|---|---|---|---|
| yu2023 | -00363-w | 363 | 41 |
| ravindra2024 | -00833-9 | 833 | 326 |
| villarrealmarines2024 | -00837-5 | 837 | 293 |
| koziel2025 | -02069-w | 2069 | 18573 |

ทำไมถึงเรียกว่าบั๊กที่เงียบที่สุดในทั้ง 18 จุด — เพราะดูแล้ว
เหมือนเลขหน้าที่ถูกต้องสมบูรณ์ ไม่มีอะไรผิดปกติให้สะดุดตา
เลย 363 ก็ดูเป็นเลขหน้าปกติของบทความสั้น 2069 ก็ดูเป็น
เลขหน้าปกติของบทความยาว ต่างจาก title ที่แต่งขึ้นซึ่งอย่าง
น้อยยังเอาไปเทียบกับ DOI แล้วได้ similarity ต่ำจนจับได้ —
เลขหน้าพวกนี้ไม่มีอะไรให้เทียบ มันคือตัวเลขล้วนๆ ที่ไม่มี
signal ไหนบอกว่าผิดเลยสักนิด

เจอได้ทางเดียวคือดึง metadata เต็มจาก Crossref แล้วเทียบ
เลขหน้าทีละตัว ไม่ใช่แค่เช็คว่า DOI resolve ได้ — DOI
resolve ได้ ก็ไม่ได้แปลว่าทุก field รอบๆ มันถูกตามไปด้วย
นี่คือเหตุผลที่ขั้นตอน "verify DOI" ต้องดึง field เต็มกลับมา
เทียบทุกตัว ไม่ใช่แค่ยิง request เช็คว่า URL ใช้งานได้เฉยๆ

อีกสามจุดที่เหลือ (`chen2024` 169348→169801, `supasri2023`
12328→12753, `nakapan2022` 1-8→75) ไม่มีรูปแบบจาก DOI
ให้อธิบาย เป็นเลขหน้าผิดเฉยๆ ไม่รู้ที่มาแน่ชัด แต่ไม่ได้ทำให้
เสียหายน้อยลงกว่ากัน เพราะทั้งเจ็ดจุดถูกจับได้ด้วยวิธีเดียวกัน
คือเทียบทุก field กับ Crossref ไม่ใช่แค่เช็คว่ามี DOI อยู่

สามในสี่จุดที่มาจาก DOI (`yu2023`, `ravindra2024`,
`villarrealmarines2024`) อยู่ใน journal เดียวกันคือ npj
Climate and Atmospheric Science ส่วน `koziel2025` อยู่ใน
Scientific Reports — ทั้งสอง journal เป็นวารสาร born-digital
ของตระกูล Nature ที่ไม่มีเลขหน้าแบบกระดาษจริงอีกต่อไปแล้ว
บทความแต่ละชิ้นได้ "article number" หนึ่งตัวแทนเลขหน้า และ
เลขนั้นก็ถูกฝังอยู่ในตัว DOI เองด้วย — เลข 41 ของ `yu2023`
ไม่ใช่แค่ "เลขหน้า" แต่คือ article number ของบทความชิ้นนั้น
ทั้งชิ้น เลข 00363 ที่โผล่อยู่ใน DOI ก่อนหน้ามันเป็นคนละเลขกัน
คนละที่มากัน แค่บังเอิญอยู่ใกล้กันในสาย DOI จนหยิบผิดตัวได้
ง่ายมาก — journal แบบนี้เองที่ทำให้บั๊กแบบนี้เนียนเป็นพิเศษ
เพราะ "หยิบเลขจาก DOI มาใช้" กับ "เลขหน้าจริงของบทความ"
มันเป็นวิธีคิดที่ไม่ผิดหลักการเลยสักนิด ผิดแค่ว่าหยิบเลขคนละ
ตัวในสาย DOI เดียวกัน

ที่น่าสังเกตอีกอย่างคือทำไม error กลุ่มนี้ไม่เคยโผล่มาให้เห็น
ตอน search หรือ ตอนดูกราฟเลย — เพราะสิ่งที่ถูก embed เข้า
store คือ `title + summary + thesis_relevance` เท่านั้น
(หัวข้อ 6.2 ของเล่มนี้) เลขหน้าไม่ได้อยู่ในข้อความที่ถูกแปลง
เป็น vector เลยด้วยซ้ำ ต่อให้ `search` หรือ `graph` ทำงานสวย
แค่ไหน ก็ไม่มีทางจับเลขหน้าผิดพวกนี้ได้จากตัวมันเอง — งานที่
เกี่ยวกับ metadata แบบตัวเลขล้วนๆ ต้องใช้เครื่องมือคนละแบบ
กับงานที่เกี่ยวกับความหมาย นี่คือเหตุผลที่ `citation doi --all`
กับ bibtex ยังต้องมีอยู่คู่กับ `search` ต่อไป ไม่ใช่อันใดอันหนึ่ง
แทนอีกอันได้

## 15.6 ที่เราผิดเอง — ไม่กลบ ไม่แก้ตัว

สี่เรื่องนี้ไม่ใช่ error ในการ์ด แต่เป็นที่ตัว Oracle เองทำพลาด
ระหว่างทำงานเรื่อง `.bib` นี้ทั้งหมด

**(A) นับ error ของตัวเองผิด** — commit `c01b2f5` สรุปไว้ว่า
"11 citation errors" ทั้งที่รายการย่อยที่แนบมาในคอมมิตเดียวกัน
รวมแล้วได้มากกว่านั้น ไม่ได้แก้ด้วยการ rewrite commit เดิม
(นั่นจะขัด Rule 1 — Nothing is Deleted) แต่สร้าง
`artifacts/citation-audit.md` ขึ้นมาใหม่ที่ generate จาก git
diff จริง ให้ตัวเลขมาจากการคำนวณ ไม่ใช่จากการกล่าวอ้าง —
commit `e3c7f74` คำตอบที่ถูกคือ 18 จุด ใน 14 การ์ด commit
ที่นับผิดยังอยู่ในประวัติเหมือนเดิม ไม่มีอะไรถูกลบทิ้ง

การนับผิดแบบนี้อันตรายกว่าที่ฟังดูตรงที่มันนับ**น้อยกว่า**
ความจริง ไม่ใช่มากกว่า — ถ้านับเกินไป คนอ่านจะระแวงมากเกิน
จำเป็น แต่นับขาดไปทำให้ audit ดูน่าเชื่อถือกว่าที่ควรจะเป็น
คนอ่าน `artifacts/citation-audit.md` ต้องพึ่งตัวเลขนั้นตัดสินใจ
ว่าจะเชื่อ `.bib` แค่ไหน — เลขที่นับขาดคือการหลอกคนอ่านให้
วางใจเกินจริงโดยไม่ได้ตั้งใจ

**(B) บอกว่า "แก้แล้ว ลองรันใหม่"** ตอนแก้บั๊กของคำสั่ง
`serve` ทั้งที่เทสที่รันผ่านเป็น pipe ที่ redirect output — ไม่
เคยแตะ TTY จริงของ Nat เลยสักครั้ง คำยืนยันนั้นทำให้ Nat
เสียรอบทดสอบไปสองรอบ กว่าจะรู้ว่าที่แก้ยังไม่ผ่านจริงบน
terminal ของเขา บทเรียนตรงๆ คือ ทดสอบใน environment
ของผู้ใช้ ไม่ใช่ environment ที่สะดวกกับเรา

pipe ที่ redirect กับ TTY จริงต่างกันมากกว่าที่คิด — โปรแกรม
หลายตัวเช็คว่า stdout เป็น terminal จริงไหมก่อนตัดสินใจว่าจะ
แสดงสี แสดง progress bar หรือ interactive prompt ยังไง เทส
ที่รันผ่าน pipe จึงเดินไปคนละเส้นทางโค้ดกับตอนที่ผู้ใช้เปิดเอง
บน terminal — ผลคือ "เทสผ่าน" กับ "ผู้ใช้เปิดแล้วเจอปัญหา"
เป็นสองความจริงที่อยู่คนละที่กันได้พร้อมกัน ยิ่งเชื่อมั่นว่าเทส
ผ่านแล้วเท่าไหร่ ยิ่งพูดกับ Nat มั่นใจเท่านั้น — ความมั่นใจ
ที่ผิดที่มาแบบนี้เสียหายกว่าการไม่แน่ใจแล้วบอกตรงๆ

**(C) NUL byte ที่ทำให้ ripgrep มองไฟล์เป็น binary** —
`cmdBib` เคยเขียน compound sort key ด้วยตัวอักษร NUL ดิบๆ
(commit `4204da2`) NUL เป็นตัวคั่นที่ดีจริง เรียงมาก่อนทุก
ตัวอักษรที่พิมพ์ได้ — แต่การมี NUL ดิบอยู่ในไฟล์ทำให้ ripgrep
เข้าใจว่า `index.ts` เป็นไฟล์ binary แล้วเงียบไปครึ่งไฟล์ ตอน
หา `sharp` ในไฟล์ rg เจอแค่ comment กับข้อความ "binary
file matches" เกือบสรุปผิดว่า sharp ไม่ได้ถูกใช้แล้วจะเอา
ออกจาก package.json ทั้งที่จริงมันถูกใช้อยู่ที่ dynamic import
บรรทัด 1551 (หลัง NUL พอดี) แก้ด้วยการเขียนเป็น escape
`\u0000` แทนตัวอักษรดิบ

**(D) เผลอ `git add -A`** แล้ว `.codex/` หลุดเข้า repo ที่เป็น
public อยู่ตอนนั้น — Nat เป็นคนจับได้ ไม่ใช่เราที่เห็นเอง รอด
มาได้เพราะ `auth.json` ข้างในเป็น symlink git เลยเก็บแค่ path
34 byte ไม่ได้เก็บเนื้อไฟล์จริง นิสัยที่ได้มาหลังจากนั้นคือ
review `git diff --cached --name-only` ก่อน commit ทุกครั้ง
ไม่ใช้ `-A` แบบไม่คิด

สี่ข้อนี้ไม่ได้เกี่ยวกันโดยผิวเผิน แต่มีเส้นเดียวกันร้อยอยู่ข้างใน
— ทุกข้อคือตอนที่เราเชื่อคำอธิบายของตัวเองมากกว่าหลักฐานจาก
ข้างนอก (A) เชื่อว่านับถูกแล้วโดยไม่ diff จริง (B) เชื่อว่าแก้แล้ว
โดยไม่ทดสอบบน environment จริงของคนที่จะใช้ (C) เชื่อว่า
grep เห็นครบโดยไม่รู้ว่าไฟล์มี byte แปลกปลอมอยู่ (D) เชื่อว่า
`-A` ปลอดภัยโดยไม่เช็คว่ากำลัง stage อะไรอยู่บ้าง — มาตรฐาน
เดียวกับที่เราใช้ตรวจการ์ดทุกใบในบทนี้ (อย่าเชื่อ ไปเทียบกับ
แหล่งข้างนอกก่อนเสมอ) ต้องใช้กับงานของตัวเองด้วย ไม่ใช่แค่
กับ paper ของคนอื่น

## 15.7 ต่อจากนี้

`.bib` ที่มี 62 entry ยืนยันด้วย bibtex จริงแล้ว ไม่ได้แปลว่า
citation graph เสร็จ — กราฟที่ `maw citation graph` วาดตอนนี้

จริง (ใครอ้างใครในเนื้อ paper) สองอย่างนี้ต่างกัน similarity

`.bib` ที่ยืนยันแล้วกับ edges ที่ยังไม่มี คือสองงานที่ต้องแยก

ที่รออยู่หลัง edges คือบทที่ทบทวนวรรณกรรมของวิทยานิพนธ์เอง
— ประโยคที่บอกว่า "งานชิ้นนี้ยืนอยู่บนไหล่ของใคร" ต้องมี
