# บทที่ 7: Index แบบ Local — ollama บนเครื่องเรา

corpus 62 ใบ ยังไม่ตีพิมพ์ — `thesis_relevance` ที่เขียนกำกับแต่ละใบ
ก็ยังไม่ตีพิมพ์เหมือนกัน นี่คือย่อหน้าเดียวที่ต้องจำจากบทนี้ ถ้าจำ
อย่างอื่นไม่ได้เลยก็ยังพอ **ของที่ยังไม่ตีพิมพ์ ไม่ควรออกจากเครื่อง**
— แล้ว index ก็เป็นจุดแรกที่ตัดสินใจเรื่องนี้ ก่อนจะไปพูดถึงว่า
search เร็วแค่ไหน หรือ batch ควรตั้งเท่าไหร่

บทที่แล้วเราอธิบายว่า embed คืออะไร — ข้อความกลายเป็นเวกเตอร์ 1024
มิติ แล้ว cosine similarity เทียบความใกล้กันของสองความหมายได้ยังไง
บทนี้ลงมือทำจริง บนเครื่อง m5 (Apple M5 Max, arm64, 18 cores, 128 GB
unified memory) ด้วย backend ตัวแรกในลำดับการเลือกอัตโนมัติ คือ
ollama ที่รันอยู่บนเครื่องเราเอง ไม่ผ่านเน็ตสักครั้งเดียว

## 7.1 ทำไม local เป็น default

`thesis_relevance` ในแต่ละการ์ด ไม่ใช่แค่บทคัดย่อของ paper คัดลอกมา
— มันคือการตีความของเราเองว่า paper ใบนี้ค้ำ claim ไหนในวิทยานิพนธ์
บ้าง พูดอีกแบบคือมันคือ argument ที่ยังไม่เผยแพร่ ถ้าข้อความนี้หลุด
ออกไปก่อนตีพิมพ์ นั่นเท่ากับ argument ทั้งเล่มหลุดไปก่อนเวลาของมัน

ยังไม่นับว่า title กับ summary ของ paper บางใบ ก็มาจากงานที่ยังเป็น
preprint หรือยังอยู่ในกระบวนการ review — การส่งข้อความพวกนี้ออกไปให้
บริการนอกเครื่องประมวลผล ก็เท่ากับส่งข้อมูลของคนอื่นออกไปด้วย ไม่ใช่
แค่ของ ณัฐ คนเดียว

เพราะงี้ citation ถึงเลือก backend ตามลำดับนี้ ไม่ใช่สุ่มเลือก และไม่
ใช่เลือกตัวที่เร็วที่สุดก่อน:

| ลำดับ | backend | ต้องมีอะไร | ออกเน็ตไหม |
|---|---|---|---|
| 1 | ollama (local) | pull bge-m3 + ollama serve | ไม่ออก ← default |
| 2 | Cloudflare worker `:18787` | wrangler login เดิม | ออก ผ่าน worker |
| 3 | Cloudflare REST | `CF_ACCOUNT_ID` + `CF_API_TOKEN` | ออก ตรง REST |

ระบบไล่เช็คจากบนลงล่าง เจอ ollama ที่ pull `bge-m3` แล้วและรันอยู่
ก็หยุดตรงนั้นทันที ไม่ไปแตะ backend ที่ 2 หรือ 3 เลย — ไม่ต้องมี
token ไม่ต้องมี account ไม่ต้องเปิด wrangler ไม่ต้องต่อเน็ตสักครั้ง
ข้อความของเราไม่มีวันออกจากพอร์ต localhost ถ้า ollama พร้อมอยู่แล้ว

อยากบังคับ backend ใดบ้าง โดยไม่ให้ระบบไล่เดาเอง ก็สั่งตรงด้วย env
var ตัวนี้:

```bash
CITATION_EMBED=ollama   ./bin/citation index --vault
CITATION_EMBED=worker   ./bin/citation index --vault
CITATION_EMBED=cf-rest  ./bin/citation index --vault
```

แต่ถ้าไม่ตั้งอะไรเลย ระบบก็เดินตามลำดับในตารางข้างบนเอง — พอ ollama
พร้อม มันก็เลือก ollama เองโดยไม่ต้องบอกอะไรเพิ่ม นี่คือเหตุผลที่บท
ที่ 10 (cloud) เขียนไว้ว่าเมฆเป็น "ตัวสำรอง ไม่ใช่ default" — เครื่อง
เราเองต้องมาก่อนเสมอ ไม่ใช่เพราะเมฆแย่ แต่เพราะข้อมูลที่ยังไม่
ตีพิมพ์ควรเลือกทางที่ปลอดภัยที่สุดก่อน แล้วค่อยเปิดทางอื่นเมื่อจำเป็น
จริงๆ (เครื่องไม่มี GPU หรือ ollama ล่ม)

หลักการข้อ 3 ของเรา "External Brain ไม่ใช่ Command" ก็อยู่ตรงนี้
เหมือนกัน — เราถือ corpus ถือ key ถือ graph ให้ แต่ตัวเลือกว่าข้อมูล
จะออกไปที่ไหนบ้าง เป็นของ ณัฐ ระบบแค่ทำให้ตัวเลือกที่ปลอดภัยที่สุด
เป็นค่าเริ่มต้น ไม่ใช่ตัวเลือกเดียว

## 7.2 ollama pull bge-m3 — 1.2 GB ครั้งเดียว

ของที่ต้องมีก่อน index ได้ครั้งแรก คือตัว model เอง ดึงมาครั้งเดียว
แล้วอยู่บนดิสก์ตลอดไป ไม่ต้องดึงซ้ำทุกครั้งที่ index หลังจากนี้:

```bash
ollama pull bge-m3
```

ครั้งแรกที่ pull บน m5 ใช้พื้นที่ดาวน์โหลดประมาณ 1.2 GB — เป็นค่าที่
วัดจากการ pull จริงครั้งแรก ไม่ใช่เลขจากเอกสารของ ollama เอง หลัง
pull เสร็จ model จะอยู่ใน local model store ของ ollama รอเรียกใช้
ครั้งต่อไปไม่ต้องโหลดผ่านเน็ตอีก

ต้องมี ollama รันอยู่เบื้องหลังด้วย ถึงจะรับ request embed ได้จริง:

```bash
ollama serve
```

ปกติ ollama บน macOS ติดตั้งมาพร้อม background service อยู่แล้ว ก็ไม่
ต้องเปิดคำสั่งนี้เอง มันรันตัวเองตั้งแต่ล็อกอินเครื่อง แต่ถ้า install
แบบ manual หรือรันบน CI ที่ไม่มี service manager ก็ต้องสั่งรันเองตรงๆ
แบบนี้ก่อนสั่ง index ทุกครั้ง

bge-m3 คือ model ตัวเดียวที่ citation ใช้ตอนนี้ ชื่อเต็มมาจากตระกูล
BAAI General Embedding — ตัว M3 หมายถึงรองรับได้หลายภาษา หลายขนาด
ข้อความ (สั้นยันยาว) และหลายรูปแบบการค้น ในแง่การใช้งานจริงของเรา
สิ่งที่สำคัญที่สุดคือมัน multilingual — ไทยกับอังกฤษอยู่ใน vector
space เดียวกัน พิมพ์คำถามเป็นไทย ก็ค้นเจอ paper ที่เขียนเป็นอังกฤษ
ล้วนได้ ไม่ต้องแปลคำถามก่อนค้นเอง

model นี้ 1024 มิติ — แปลว่า title + summary + thesis_relevance ของ
แต่ละ paper ถูกบีบให้เหลือแค่ตัวเลข 1024 ตัว ข้อความที่ถูก embed ต่อ
1 paper คือสามฟิลด์นี้ต่อกัน ไม่ใช่ทั้งไฟล์การ์ด ฟิลด์อย่าง `doi`
`volume` `pages` ไม่ถูก embed ด้วย — เติม `doi` เข้าไปทีหลังเฉยๆ ก็ไม่
ต้อง index ใหม่ทั้งชุด (บทที่ 6 อธิบายรายละเอียดเรื่องนี้ไว้แล้ว
บทนี้แค่ทวนสั้นๆ พอให้เข้าใจว่ากำลัง embed อะไรอยู่)

ถ้าสั่งด้วย `--vault` ด้วย vault note จาก `ψ/memory/{learnings,
retrospectives,resonance}` และ `ψ/writing/research` ก็ถูก embed ไป
พร้อมกัน ติด tag `kind: note` ไว้แยกจาก paper — ทำให้ search เจอทั้ง
paper และความคิดของเราเองในผลลัพธ์เดียวกัน ไม่ต้องเปิดสองระบบค้นคน
ละที่

## 7.3 รันจริง: 75 รายการ 8.4 วินาที

รันคำสั่งนี้บน m5 พร้อม `--vault`:

```bash
./bin/citation index --vault
```

สิ่งที่เกิดขึ้นข้างในคือ ระบบอ่านการ์ดทุกใบใน `ψ/papers/` อ่าน note
ทุกไฟล์ตามพาธที่บอกไว้ข้างบน ต่อข้อความตามกฎของแต่ละประเภท (paper
เอา title+summary+thesis_relevance / note เอาเนื้อหาของมันเอง) แล้ว
ส่งไป embed เป็นชุดๆ ผ่าน ollama ก่อนเขียนผลลัพธ์ลง store

corpus ตอนนี้มี 62 paper + 13 note รวม 75 รายการ ใช้เวลา **8.4
วินาที** ทั้งชุด — เงื่อนไขของตัวเลขนี้คือ model ต้อง warm อยู่ใน GPU
แล้วตอนเริ่ม (ครั้งแรกหลังเครื่องว่างนาน ollama จะโหลด model เข้า
VRAM ก่อน ถึงจะเริ่ม embed ได้ ใช้เวลาเพิ่มอีกนิดหน่อยจากตัวเลขนี้)
คิดเฉลี่ยคร่าวๆ ก็ตกวินาทีละราวๆ 9 รายการ — เร็วพอที่จะสั่ง index
ใหม่ทั้งชุดได้บ่อยๆ โดยไม่รู้สึกเสียเวลา

| รายการ | ค่าที่วัดจริงบน m5 |
|---|---|
| จำนวนที่ index | 75 (62 paper + 13 note) |
| เวลา index --vault | 8.4 วินาที |
| เวลา search 1 ครั้ง | 0.221 วินาที |
| ขนาด store ทั้งโฟลเดอร์ | 452 KB |
| ขนาด `vectors.f32` | 300 KB |
| bge-m3 ใน VRAM | 634 MB · ctx 8192 · 100% GPU |

search หนึ่งครั้งคือ embed คำถามที่พิมพ์เข้าไปก่อน แล้วเทียบ cosine
กับทั้ง 75 แถวแบบ brute-force — ไม่มี ANN index ไม่มี native
dependency ใดๆ เขียนล้วนด้วย TypeScript ตรงๆ แล้วยังจบใน 0.221
วินาที เพราะ 75 แถวมันเล็กเกินกว่าจะต้องใช้โครงสร้างข้อมูลซับซ้อน
อะไรเลย เทียบตรงๆ ทีละแถวก็เร็วพอแล้ว

output จริงของ search หน้าตาแบบนี้:

```
[0.7913] 📄 paper \cite{mahajan2025}
  (low-cost-sensor-calibration)
  Mahajan & Helbing (2025)
[0.8702] 📝 note (ψ/writing/research)
  Environmental prediction models for PM2.5
```

📄 คือ paper 📝 คือ note — ตัวเลขในวงเล็บเหลี่ยมข้างหน้าคือ cosine
similarity ยิ่งใกล้ 1 ยิ่งใกล้เคียงกับคำถามมาก สองผลลัพธ์ตัวอย่างนี้
มาจากคนละแหล่งกัน แต่โผล่ในรายการเดียวกันได้ เพราะทั้งคู่ถูก embed
ด้วย model เดียวกัน อยู่ใน vector space เดียวกันเป๊ะ

ส่วน store บนดิสก์ ก็ไม่ใช่ database ตัวไหนเลย เป็นไฟล์ธรรมดา 3 ไฟล์
เท่านั้น — `vectors.f32` (75 × 1024 float32 เรียงต่อกันเป็นก้อนไบนารี
เดียว) `meta.jsonl` (metadata ของแต่ละแถว หนึ่งบรรทัดต่อหนึ่งรายการ)
กับ `manifest.json` (จำชื่อ model ที่ใช้ index ไว้) — vector จาก
model ต่างกันเทียบกันไม่ได้เลย สลับ model เมื่อไหร่ต้อง index ใหม่
ทั้งชุดเสมอ manifest มีไว้กันตรงนี้

ลบโฟลเดอร์ store ทิ้งแล้ว index ใหม่ได้เลยเมื่อไหร่ก็ได้ เพราะมันเป็น
derived data ทั้งหมด ไม่ใช่ของต้นฉบับ ของต้นฉบับจริงๆ อยู่ที่การ์ด
ใน `ψ/papers/` เท่านั้น — store แค่เป็นดัชนีชั่วคราวที่สร้างใหม่ได้
ตลอด

## 7.4 batch 16 — และเคสยิงทีเดียวหมดแล้วพัง

embed ไม่ได้ส่งทีละ paper ทีละครั้ง — ส่งเป็นชุดๆ ชุดละ 16 คุมด้วย
env var ตัวนี้:

```bash
CF_EMBED_BATCH=16   # ค่า default
```

เหตุผลที่ต้องมี batch เลย ไม่ใช่แค่เรื่อง performance อย่างเดียว —
มันคือเรื่องความอยู่รอดของ request ด้วย ตอนที่ corpus ยังมีแค่ 56
paper เฉยๆ (ยังไม่รวม vault note) การยิง embed ทีเดียวทั้งชุดยังผ่าน
อยู่ได้ แต่พอเพิ่ม note เข้ามาจนจำนวนรวมทะลุ 65 รายการขึ้นไป การยิง
ทีเดียวหมดก็เริ่มพัง — worker ตอบกลับมาด้วย error 500 ตรงๆ ไม่ใช่
timeout ค่อยๆ ช้าลง แต่คือพังทั้งก้อนเลย

จำนวนที่เพิ่มขึ้นจาก 56 ไป 65 ไม่ได้เยอะมากในสายตาคนดู แต่ในแง่ของ
payload หนึ่งก้อนที่ส่งไปพร้อมกัน มันคือข้อความยาวขึ้น จำนวนแถวมากขึ้น
รวมกันแล้วพอถึงจุดหนึ่งก็ใหญ่เกินกว่าฝั่ง backend จะรับไหวในคำขอ
เดียว — ไม่ว่าจะเป็นเพราะ payload size limit หรือ timeout ของฝั่ง
worker เอง ผลลัพธ์ที่เราเห็นก็คือ error 500 เหมือนกัน

ทางแก้คือหั่นเป็นชุดละ 16 แล้วส่งต่อกันไปเรื่อยๆ ทีละชุด รอผลลัพธ์
ของชุดก่อนกลับมาก่อน ค่อยส่งชุดถัดไป — 75 รายการตอนนี้ก็คือ 5 รอบ
(16 × 4 บวกอีก 11) แทนที่จะเป็น 1 รอบยักษ์เดียว ระบบทำแบบนี้ให้
อัตโนมัติอยู่แล้วเป็นค่าเริ่มต้น ไม่ต้องสั่งเองทุกครั้ง

แต่ถ้าเครื่องที่ใช้มี RAM น้อย หรือ backend ที่ต่ออยู่ตั้ง limit ไว้
ต่ำกว่า 16 แถวต่อคำขอ ก็ลด batch ให้เล็กลงได้ตรงๆ:

```bash
CF_EMBED_BATCH=8  ./bin/citation index --vault
```

batch เล็กลง แปลว่ารอบการส่งเยอะขึ้น ช้าลงนิดหน่อยโดยรวม แต่แต่ละ
request ที่ส่งออกไปก็เบาลงตามไปด้วย — เหมาะกับเครื่องที่ RAM จำกัด
หรือ backend ฝั่งไหนก็ตามที่ตั้ง limit ต่ำกว่าค่า default ไว้ ปรับได้
ทันทีโดยไม่ต้องแก้โค้ดสักบรรทัดเดียว แค่ตั้ง env var ก่อนรันคำสั่ง

บทเรียนจากเคสนี้ตรงๆ คือ: อย่ายิงทีเดียวหมด ไม่ว่า corpus จะดูเล็ก
แค่ไหนก็ตาม — 65 รายการก็ยังเรียกว่าเล็กอยู่ดีเมื่อเทียบกับ corpus
งานวิจัยจริงๆ ทั่วไป แต่ก็ยังพังได้ถ้ายิงทีเดียวหมด การหั่นเป็น batch
เล็กๆ ไม่ได้แพงอะไร แต่ป้องกันปัญหานี้ได้เกือบทั้งหมด

## 7.5 debug: no embedding backend reachable

ข้อความนี้โผล่มาตอนระบบไล่ครบทั้ง 3 backend ในตารางข้อ 7.1 แล้วไม่
เจอตัวไหนที่ใช้ได้จริงสักตัวเลย — ส่วนใหญ่กรณีที่เจอในเครื่องเรา คือ
ollama ยังไม่ได้รันอยู่ หรือรันอยู่แต่ยังไม่ได้ pull `bge-m3` เข้ามา

เช็คทีละขั้น เริ่มจากถามว่า ollama รันอยู่จริงไหมก่อนเลย:

```bash
curl -s http://localhost:11434/api/tags
```

ถ้า connection refused กลับมา คือ ollama ไม่ได้รันอยู่เลย — สั่ง
`ollama serve` ก่อน (หรือเปิด ollama app ถ้าใช้ macOS แบบติดตั้งปกติ)
ถ้า connect ติดแต่ list ของ model ที่ได้กลับมาว่างเปล่า หรือไม่มี
`bge-m3` โผล่อยู่ในนั้นเลย ก็แปลว่ายังไม่เคย pull มาก่อน pull เพิ่ม
ตรงๆ:

```bash
ollama pull bge-m3
```

พอ ollama พร้อมแล้วทั้งสองจุดนี้ ก็เช็คต่อว่า model ขึ้น GPU จริงไหม
ด้วย `/api/ps`:

```bash
curl -s http://localhost:11434/api/ps
```

ดูสอง field คือ `size` กับ `size_vram` — ถ้าเท่ากันเป๊ะ แปลว่า model
resident อยู่ทั้งก้อนบน GPU (100% ไม่มี CPU fallback เลย) นี่คือวิธี
ยืนยันแบบเดียวที่เชื่อถือได้จริง ไม่ใช่เดาเอาจากความรู้สึกว่าเครื่อง
เร็วหรือช้า ตัวเลขบอกตรงๆ กว่าความรู้สึกเสมอ

ollama unload model เองหลังไม่ได้ใช้งานประมาณ 5 นาที (เช็คได้จาก
field `expires_at` ใน `/api/ps` เหมือนกัน) — ถ้า index รอบแรกของวัน
ช้ากว่ารอบถัดไปนิดหน่อย ก็เพราะ model เพิ่งถูก unload ไปแล้วต้อง warm
กลับเข้า VRAM ใหม่ ไม่ใช่อาการพังอะไร แค่รอบแรกเสียเวลา warm-up ไป
เล็กน้อยเท่านั้นเอง

ถ้าเช็คครบทุกจุดข้างบนแล้วยังเจอ `no embedding backend reachable`
อยู่ดี ก็ลองบังคับ backend ตรงๆ ด้วย `CITATION_EMBED=ollama` ก่อน
แล้วดู error message ที่ชัดเจนกว่าเดิม — บางทีปัญหาไม่ได้อยู่ที่
ollama เลยสักนิด แต่อยู่ที่ระบบไปลองอีกสอง backend ก่อน แล้วเงียบ
error ของแต่ละตัวทิ้งไป จนเหลือแต่ข้อความรวมที่ไม่บอกอะไรมาก การบังคับ
backend ตรงๆ ช่วยตัดตัวแปรออกไปทีละตัว

ถ้าอยากเทียบกับ backend ที่ 2 (Cloudflare worker) ตอนดีบัก ก็เปิดขึ้น
มาคู่กันได้ ด้วย wrangler ที่ล็อกอินไว้อยู่แล้ว ไม่ต้องสร้าง token
ใหม่:

```bash
cd ~/.maw/plugins/cf-embed/worker
wrangler dev --port 18787
```

แต่นี่เป็นทางเลือกตอนดีบักหรือตอนเครื่องไม่มี GPU จริงๆ เท่านั้น —
ถ้า ollama ใช้ได้ปกติ ก็ไม่มีเหตุผลต้องเปิด worker คู่ขนานไปด้วย
เพราะมันแปลว่าข้อความบางส่วนได้ออกเน็ตไปโดยไม่จำเป็น

สิ่งที่ทำได้โดยไม่ต้องมีเน็ตเลยสักนิด ครบเลยคือ `index` `search`
`serve` `graph` `bib` `cards` `status` — ทุกตัวนี้อยู่บนเครื่องล้วนๆ
ตั้งแต่ต้นจนจบ ที่ต้องมีเน็ตจริงๆ มีแค่คำสั่งเดียว คือ `doi` ที่ยิงไป
`api.crossref.org` เพื่อยืนยัน DOI ของแต่ละ paper — และถ้าต่อเน็ตผ่าน
tethering ที่ควอต้าจำกัด ก็ยังยิงทีละใบได้เสมอ ด้วย `citation doi
<citekey>` ไม่ต้องยิงทั้งชุดพร้อมกัน

## ปิดท้ายด้วยคำถามที่ยังไม่ได้ตอบ

ทั้งหมดที่วัดในบทนี้ วัดบนเครื่องที่มี GPU พร้อมใช้งานอยู่แล้ว — m5
คือ Apple Silicon ที่ตัว unified memory ทำให้ CPU กับ GPU ใช้ RAM ก้อน
เดียวกัน ไม่ต้องคัดลอกข้อมูลข้ามไปมาเหมือน discrete GPU ทั่วไป (เรื่อง
นี้บทที่ 9 จะขยายให้เต็มๆ)

แล้วถ้าเครื่องไม่มี GPU เลยล่ะ — index 8.4 วินาทีของ 75 รายการ จะ
กลายเป็นกี่วินาทีบนเครื่องที่ต้องใช้ CPU ล้วนอย่างเดียว เรา **ยังไม่
ได้วัด** ตัวเลขนั้นตรงๆ สักครั้งเดียว ทั้งบนเครื่องที่ปิด GPU ทดสอบ
และบนเครื่อง Intel/AMD ทั่วไปที่ไม่มี Apple Silicon เลย

บทที่ 8 จะไม่เดาตัวเลขนั้นให้ แต่จะสอนวิธีจับเวลาเอง สอนวิธีเช็คด้วย
`size_vram` เทียบ `size` ว่าตกไปที่ CPU จริงหรือเปล่า และสอนว่าเมื่อ
ไหร่ที่ corpus ขนาดเท่านี้ CPU ล้วนก็ยังพอไหว โดยไม่ต้องเชื่อตัวเลข
ไหนที่ใครบอกมาโดยไม่มีใครวัดจริงสักครั้ง
