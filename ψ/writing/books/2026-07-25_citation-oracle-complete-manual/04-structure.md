# บทที่ 4: โครงสร้าง — ของอยู่ไหน อะไรคือของจริง

บทที่แล้วบอกว่าของเสริมอะไรขาดได้ บทนี้พาไปดูของที่ขาดไม่ได้ —
โครงสร้างของ repo เอง แล้วตอบคำถามที่สำคัญที่สุดข้อเดียว:
ถ้า `.bib` ผิด `.citation.bib` ผิด หรือ search ตอบมั่ว จะไปแก้ที่ไหน

คำตอบสั้น ๆ ก่อนอธิบายยาว — แก้ที่การ์ด ไม่ใช่ที่ไหนอื่น
การ์ดใน `ψ/papers/` คือความจริงหนึ่งเดียวของ paper ทุกใบ ส่วน JSONL
เป็นแค่ประตูตอนนำเข้าครั้งแรก store ก็เป็นแค่ผลลัพธ์ที่ derive มาจาก
การ์ดอีกที ลบทิ้งเมื่อไหร่ก็สร้างใหม่ได้ ไม่มีอะไรหาย

## 4.1 แผนที่ทั้ง repo

repo นี้ไม่มี database ไม่มี server ถาวร มีแค่ folder กับไฟล์ markdown
เป็นหลัก ลองดูจริงบนเครื่อง m5:

```bash
$ ls ψ
active/   inbox/    memory/   papers/
archive/  lab/      outbox/   writing/
learn/

$ ls artifacts
citation-audit.md      citation-network.svg
citation-network.html  citation.bib
citation-network.png   literature_corpus.jsonl

$ ls bin
citation

$ ls .claude/skills
gemini-deep-research/  research-harvest/
paper-card/            research-ingest/
```

สี่ที่ที่ต้องรู้จัก:

| ที่ | เก็บอะไร |
|---|---|
| `ψ/papers/` | การ์ด paper 62 ใบ — **source of truth** |
| `ψ/lab/citation/` | โค้ด plugin (`src/index.ts`, `package.json`) |
| `artifacts/` | ผลผลิต — JSONL นำเข้า, `.bib`, กราฟ PNG/SVG/HTML |
| `bin/citation` | ทางเข้าแบบไม่ต้องมี maw |

`ψ/lab/citation/` คือที่โค้ดอยู่ ไม่ใช่ที่ข้อมูลอยู่ — แยกกันชัดเจน
ข้อมูล (การ์ด) อยู่ใน `ψ/papers/` โค้ด (plugin) อยู่ใน `ψ/lab/citation/`
คนละที่ คนละบทบาท จะย้าย engine ไปเขียนใหม่วันไหนก็ได้ การ์ดไม่ขยับ

`.claude/skills/` ไม่ได้อยู่ในเส้นทาง การ์ด → embed → search เลย —
เป็นคนละชั้น เอาไว้ตอน**หา**เนื้อหาใหม่มาป้อนเข้าคอร์ปัส ไม่ใช่ตอน
จัดการของที่มีอยู่แล้ว สี่ตัวแบ่งงานกันชัด: `gemini-deep-research`
เขียน brief/prompt ส่งให้ research tool ข้างนอกไปหาให้ `research-ingest`
รับรายงานที่ได้กลับมา ตรวจ DOI ทุกตัวกับ Crossref ก่อนเสมอ แล้วค่อย
สร้างการ์ดใหม่ + index `research-harvest` ทำงานคนละจุด — เอารายงาน
ที่ ingest ไว้แล้วมาแปลงเป็นตาราง/คิวตรวจ/ช่องว่างที่ต้อง research
ต่อ ส่วน `paper-card` ใช้ตอนมี paper เดี่ยว ๆ ใบเดียว (DOI, APA,
BibTeX) จะเพิ่มเข้าการ์ด ไม่ต้องผ่านทั้ง pipeline research

### สองทางเข้า หนึ่ง implementation

`./bin/citation` กับ `maw citation` ไม่ใช่คนละเครื่องมือ — เรียก
handler เดียวกันที่ export ออกมาจากปลั๊กอิน ไม่มี dispatch สองชุด
ให้ต้องคอย sync กัน:

```bash
./bin/citation status      # ไม่มี maw ก็ใช้ได้ ต้องมีแค่ bun
maw citation status        # เหมือนกันทุกอย่าง สำหรับคนมี maw
```

ต่างกันแค่ตอน**หา repo root** — เพราะสองทางเข้าไม่รู้ว่าตัวเองรัน
จากไหน ต้องเดาให้ถูกก่อนถึงจะไปเปิด `ψ/papers/` ได้ ลำดับที่ใช้:

1. `CITATION_ROOT` — ถ้าตั้ง env นี้เอง ใช้ตัวนี้เลย ไม่เดาต่อ
2. `MAW_HOME` — รันผ่าน maw พฤติกรรมเดิมไม่เปลี่ยน
3. ไล่ขึ้นจาก**ตำแหน่ง script** หา `CLAUDE.md` + `ψ/` คู่กัน
4. ไล่ขึ้นจาก**cwd** ปัจจุบัน หา `CLAUDE.md` + `ψ/` คู่กัน
5. `git rev-parse --show-toplevel` — ถ้ายืนอยู่ใน repo git ก็ยังหาได้
6. cwd ตรง ๆ — ทางสุดท้ายจริง ๆ

ข้อ 3 คือเหตุผลที่ `./bin/citation status` รันจาก `/tmp` ยังได้ผล
(commit `051014b`) — เพราะมันไม่ได้ดูว่า**เรา**ยืนอยู่ไหน มันดูว่า
**ตัวสคริปต์**อยู่ไหน แล้วไล่ขึ้นจากตรงนั้น ปกติสคริปต์อยู่ใน repo
เสมอ ต่อให้ terminal ย้ายไปไหนก็ตาม

ทำไมต้องใส่ใจเรื่องนี้ขนาดนี้ — เพราะ root ผิดแล้ว `status` ไม่ error
มันแค่รายงาน "0 paper card" เงียบ ๆ เหมือนข้อมูลหายไปทั้งชุด `status`
เลยพิมพ์บอกไว้บรรทัดแรกเสมอว่าเจอ root ด้วยกฎไหน — บนเครื่อง m5 ตอน
รันจริงมันขึ้นว่า `repo root: /opt/Code/github.com/Soul-Brews-Studio/`
`phd-citation-oracle (walk up from the script)` เห็นวงเล็บท้ายบรรทัด
แล้วรู้ทันทีว่าใช้กฎไหน ไม่ต้องเดา

## 4.2 ψ/papers/ — การ์ดคือของจริง

62 การ์ด หนึ่งไฟล์ต่อหนึ่ง paper กฎเดียวที่ต้องจำ:

> **ชื่อไฟล์ = citekey = คีย์ที่ใช้ใน `\cite{}`**

ไฟล์ `mahajan2025.md` มี `citekey: mahajan2025` ข้างใน แล้วในเล่ม
วิทยานิพนธ์ก็เขียน `\cite{mahajan2025}` ตรง ๆ ไม่มีชั้นแปลระหว่างกลาง
ไม่มี mapping table แยกไว้ที่ไหนอีก — ชื่อไฟล์บอกทุกอย่าง

README ของ `ψ/papers/` เองก็เขียนไว้ตรง ๆ ตั้งแต่บรรทัดแรก:

> "ที่นี่คือ source of truth ไม่ใช่ `artifacts/literature_corpus.jsonl`
> — JSONL เป็นแค่ช่องทาง import ตอนเริ่ม ถ้าจะแก้อะไรให้แก้ card"

พอ import มาแล้ว JSONL หมดหน้าที่ตัวเองในทันที มันเป็นแค่ท่อ ไม่ใช่
ถังเก็บ ใครแก้ paper ที่ JSONL หลังจากนี้ก็ไม่มีผลอะไรกับการ์ดที่มี
อยู่แล้ว (เว้นแต่จะสั่ง `cards` ให้ regenerate ใหม่ — เรื่องนั้นอยู่
หัวข้อ 4.4)

62 การ์ดไม่ได้กระจายเท่ากัน แต่ละใบผูกกับ 1 ใน 6 taproot topic
(field `topic` ในหัวข้อ 4.3) — ตัวเลขจริงตอนนี้:

| topic | จำนวนการ์ด |
|---|---:|
| `satellite-pm25-products` | 16 |
| `low-cost-sensor-calibration` | 14 |
| `thailand-burning-season` | 11 |
| `health-policy` | 9 |
| `reference-monitoring-bam` | 6 |
| `multi-source-fusion-qa` | 6 |

รวม 62 พอดี — ตัวเลขนี้คือสิ่งที่ทำให้กราฟใน `serve`/`graph` (บทที่ 5)
ลงสีได้ 6 กลุ่ม ไม่ใช่กลุ่มเดียวก้อนเดียวไม่มีความหมาย

ใน `ψ/papers/` มีไฟล์ที่**ไม่ใช่**การ์ดอยู่สองไฟล์ ต้องรู้จักแยก:

| ไฟล์ | คืออะไร | แก้มือได้ไหม |
|---|---|---|
| `<citekey>.md` | การ์ด — 1 ไฟล์ = 1 paper | ได้ นี่คือของจริง |
| `INDEX.md` | สารบัญ generate อัตโนมัติ | **ห้าม** — เดี๋ยวถูกทับ |
| `README.md` | คู่มือการเพิ่ม/แก้การ์ดด้วยมือ | ได้ แต่ไม่ใช่ข้อมูล |

ตัว index ตอน embed เองก็รู้เรื่องนี้ — มันข้าม `INDEX.md` กับ
`README.md` ออกจากรายการ paper โดยเจตนา (มีคอมเมนต์ในโค้ดบอกไว้ว่า
เคยมีบั๊กที่ `README.md` หลุดเข้าไป index เป็น paper "uncategorized"
หนึ่งใบ เจอแล้วก็แก้ ไม่ปล่อยไว้)

## 4.3 frontmatter 20 field

ทุกการ์ดขึ้นต้นด้วย YAML frontmatter — ระหว่าง `---` สองอัน ก่อนถึง
body markdown ครบชุดมี 20 field เอาการ์ด `mahajan2025.md` ตัวจริงมา
ดู (บรรทัด `title:` ยาวเกิน ตัดขึ้นบรรทัดใหม่เพื่อพอดีหน้ากระดาษ —
ในไฟล์จริงอยู่บรรทัดเดียว):

```yaml
citekey: mahajan2025
id: "2.1.4"
title: >-
  Dynamic calibration of low-cost PM2.5 sensors using
  trust-based consensus mechanisms
short_title: "Trust-Based Dynamic Calibration"
authors:
  - "Mahajan, S."
  - "Helbing, D."
year: "2025"
journal: "npj Climate and Atmospheric Science"
quartile: "Q1"
impact_factor: "9.0"
volume: "8"
issue: "1"
pages: "257"
doi: "10.1038/s41612-025-01145-2"
topic: "low-cost-sensor-calibration"
status: ok
verified: "crossref 2026-07-25"
tags: [paper, low-cost-sensor-calibration]
kind: paper
```

การ์ดใบนี้ไม่มี `aka:` กับ `authors_upstream:` — สองตัวนั้นเป็น
field ที่ 19-20 มีเฉพาะการ์ดที่เคยถูก Crossref แก้ citekey หรือแก้
รายชื่อผู้เขียน (ดูตัวอย่างจริงในหัวข้อ 4.6)

ทีนี้ไล่ทีละตัวว่าคืออะไร บังคับไหม แล้วเวลา `index` ไปแล้ว มันถูก
**embed เป็น vector** ด้วยหรือเปล่า — นี่คือจุดที่คนมักเข้าใจผิด
เพราะคิดว่าใส่ frontmatter ครบแล้ว search จะฉลาดขึ้น ทั้งที่จริง ๆ
ตัว embed อ่านแค่บางส่วนเท่านั้น:

| # | field | คืออะไร | บังคับ | embed? |
|---|---|---|---|---|
| 1 | `citekey` | คีย์ citation ต้องตรงชื่อไฟล์ | บังคับ | ไม่ |
| 2 | `id` | เลข section ใช้เรียง `INDEX.md` | บังคับ | ไม่ |
| 3 | `title` | ชื่อ paper เต็ม | บังคับ | ทางอ้อม |
| 4 | `short_title` | ชื่อสั้นโชว์บนกราฟ | แนะนำ | ใช่ |
| 5 | `authors` | รายชื่อผู้เขียน | บังคับ | ใช่ |
| 6 | `year` | ปีตีพิมพ์ | บังคับ | ใช่ |
| 7 | `journal` | ชื่อวารสาร | บังคับ | ไม่ |
| 8 | `quartile` | Q1–Q4 | บังคับ | ไม่ |
| 9 | `impact_factor` | IF ของวารสาร | บังคับ | ไม่ |
| 10 | `volume` | เล่มที่ | บังคับ | ไม่ |
| 11 | `issue` | ฉบับที่ | optional | ไม่ |
| 12 | `pages` | เลขหน้า | บังคับ | ไม่ |
| 13 | `doi` | DOI จาก Crossref | optional | ไม่ |
| 14 | `topic` | 1 ใน 6 topic เดิม | บังคับ | ไม่ |
| 15 | `status` | `ok` \| `needs-authors` | บังคับ | ไม่ |
| 16 | `verified` | แหล่งยืนยัน + วันที่ | optional | ไม่ |
| 17 | `tags` | `[paper, topic]` ใช้ filter | บังคับ | ไม่ |
| 18 | `kind` | `paper` — ห้ามลบ | บังคับ | ไม่ |
| 19 | `aka` | citekey เดิมก่อน rename | optional | ไม่ |
| 20 | `authors_upstream` | ผู้เขียนเดิมก่อนแก้ | optional | ไม่ |

แถวที่ 3-6 เขียนว่า "ทางอ้อม" กับ "ใช่" เพราะข้อความที่ยิงเข้า
embedder จริง ๆ ไม่ใช่ frontmatter ดิบ ๆ แต่เป็น**label**ที่ประกอบขึ้น
จาก `authors` ตัวแรก + `year` + `short_title` (หรือ `title` ถ้าไม่มี
`short_title`) ต่อด้วยเนื้อความสองก้อนจาก body คือ **Key findings**
กับ **Thesis relevance** แล้วปิดท้ายด้วยทุกอย่างใต้ `## Notes`

พูดง่าย ๆ — สิ่งที่ทำให้ search "ฉลาด" ไม่ใช่ metadata การตีพิมพ์
(journal, quartile, volume, pages, doi) แต่เป็นเนื้อหาสามก้อน:
label สั้น ๆ, ที่เจออะไรมา, แล้วมันเกี่ยวกับ thesis ยังไง field
พวก journal/doi/pages ยังคงสำคัญมาก — แค่สำคัญตอนออก `.bib` กับ
โชว์ผลลัพธ์ ไม่ใช่ตอนคำนวณ cosine similarity

field optional สองตัวในตารางมีสภาพต่างกันในทางปฏิบัติ — `issue`
เว้นว่างได้แบบเงียบ ๆ ไม่กระทบอะไร (การ์ด `jin2022` เว้นไว้เพราะ
วารสารนั้นไม่มีเลขฉบับให้ใส่) ส่วน `doi` ตอนนี้กรอกครบแล้ว 61 จาก
62 ใบ เหลือ `jarernwong2021` ใบเดียวที่ยังว่าง เพราะอยู่ใน *Chemical
Engineering Transactions* ซึ่ง Crossref ไม่มีข้อมูลให้สืบ — ปล่อย
ว่างไว้ดีกว่าใส่เลขที่เดาขึ้นมาเอง (Crossref ไม่มั่นใจ ก็ไม่เดาแทน)

`topic` เป็นอีกตัวที่คนมักเดาผิดว่าถูก embed — จริง ๆ ไม่ใช่ มันถูก
ใช้ลงสี node บนกราฟ กับใช้ gate ว่าแก้แล้วต้อง index ใหม่หรือเปล่า
เท่านั้น (ต้องเป็น 1 ใน 6 topic เดิมด้วย ไม่งั้นสีบนกราฟจะเพี้ยน)
ส่วน `kind: paper` ก็สำคัญคนละแบบ — field นี้ไม่มีผลต่อความหมาย
เลย แต่ถ้าลบทิ้ง ตอน index จะแยก paper ออกจาก vault note ไม่ได้

เอาการ์ด `mahajan2025.md` ตัวเดิมมาไล่ดูจริง ๆ ว่า embed แล้วข้อความ
ที่ยิงเข้า `bge-m3` หน้าตาเป็นยังไง — สามก้อนถูกต่อกันด้วยบรรทัดว่าง
โดยไม่มี metadata การตีพิมพ์ปนอยู่เลยสักตัว:

```text
Mahajan & Helbing (2025) -- Trust-Based Dynamic Calibration

4-indicator trust framework (accuracy, stability,
responsiveness, consensus). MAE reductions up to 68% for
poor sensors, 35-38% for reliable ones.

HIGHEST CONCEPTUAL ALIGNMENT -- trust-scoring parallels
DustBoy's A-F confidence grading. Nature-family validation
of the confidence scoring concept.
```

บรรทัดแรกมาจาก `authors` + `year` + `short_title` ประกอบกันเอง
(ฟังก์ชันเดียวกับที่ขึ้นหัวเรื่อง `#` ในไฟล์) สองก้อนล่างมาจาก body
ตรง ๆ — journal, quartile, impact factor, DOI ไม่มีตัวไหนอยู่ในนี้
เลยสักคำ นี่คือเหตุผลที่บทที่ 6 จะบอกว่า "embedding ไม่ใช่ keyword
search" — ถามหา "npj Climate" จะไม่เจอ paper นี้จาก journal name
แต่ถามหา "trust framework calibration" มีโอกาสเจอสูงมาก เพราะคำ
พวกนี้อยู่ในข้อความที่ถูก embed จริง ๆ

## 4.4 ## Notes ไม่หาย — แล้วอะไรรอดเพิ่มเวลา verified แล้ว

body ของทุกการ์ดมีสามก้อนแบบตายตัว ตามด้วย `## Notes`:

```markdown
**Key findings** — เจออะไร ใส่เลขจริงให้ครบ
**Thesis relevance** — เกี่ยวกับงานเรายังไง
**Full citation** — reference เต็มแบบ APA

## Notes

โน้ตของเราเอง
```

parser จับสามก้อนบนด้วย pattern `**label** —` ตรง ๆ เว้นวรรคหรือ
สลับ format นิดเดียวก็จับไม่เจอ — เพราะงั้นเวลาแก้การ์ดด้วยมือ ต้อง
คงรูปแบบนี้ไว้

จุดที่ต้องระวังคือ parser ตัวนี้**ไม่ error ตอนจับไม่เจอ** มันแค่คืน
สตริงว่างกลับมา หมายความว่าถ้าพิมพ์ `**Key findings**` ผิดเป็น
`**Key Finding**` (ตัว s หาย) หรือลืมใส่เครื่องหมาย `—` ต่อท้าย
เนื้อความ**Key findings**ในกรณีนั้นจะเป็นสตริงว่างตอนไป embed —
การ์ดใบนั้นจะยังอยู่ใน `status` เหมือนเดิม ยัง `index` ผ่านเหมือน
เดิม แต่ search จะหามันไม่เจอ เพราะข้อความที่ยิงเข้า embedder ขาด
เนื้อหาไปครึ่งหนึ่งโดยไม่มีใครบอก — เป็นบั๊กเงียบแบบเดียวกับที่
บทที่แล้วเล่าเรื่อง NUL byte ไว้ คือพังแบบไม่ error ต้องไปเช็คผลลัพธ์
search เองถึงจะรู้

คำสั่ง `cards` เอาไว้ regenerate การ์ดทั้งชุดใหม่จาก JSONL ใช้ตอน
JSONL อัปเดต หรือ import เพิ่ม แต่การ regenerate แบบไม่ระวังจะทับ
งานแก้มือทิ้งหมด เพราะงั้นมันมีกฎว่าอะไร**รอด**เสมอ แล้วอะไรรอด
**เพิ่ม**เมื่อการ์ดผ่านการ verify แล้ว:

| รอดเสมอ ไม่ว่าอะไร | รอดเพิ่ม ถ้ามี `verified:` |
|---|---|
| ทุกอย่างใต้ `## Notes` | `authors` |
| `doi:` ที่เคยเติมไว้ | `title` |
| `aka:` | `journal` |
| `authors_upstream:` | `volume` |
| | `issue` |
| | `pages` |

เหตุผลของคอลัมน์ขวา — JSONL ต้นทางคือที่มาของข้อมูลผิดตั้งแต่แรก
(มีบทเรียนละเอียดที่หัวข้อ 4.6) ถ้าปล่อยให้ `cards` ทับ field พวกนี้
ทุกครั้งที่ regenerate เท่ากับ**revert งาน verify ทิ้งทั้งหมด**
โดยไม่ตั้งใจ — เพราะงั้นพอการ์ดมี `verified:` ห้อยอยู่ ตัว `cards`
จะรู้ว่า "ห้ามแตะ field พวกนี้อีก มันถูกต้องแล้ว"

field อื่นที่**ไม่**อยู่ในสองคอลัมน์นี้ — `id` `short_title`
`quartile` `impact_factor` `topic` `status` `tags` `kind` กับ body
สามก้อนแรก (`Key findings` `Thesis relevance` `Full citation`) —
จะถูกทับด้วยของจาก JSONL ทุกครั้งที่ regenerate ถ้าการ์ดใบนั้นยัง
ไม่ verified ถ้าจะแก้อะไรให้ถาวรแล้วไม่อยู่ในรายการที่รอด ต้องไปแก้
ที่ JSONL เองด้วย หรือเลิกใช้ `cards` แล้วแก้การ์ดตรง ๆ อย่างเดียว

## 4.5 store — ไฟล์ธรรมดา 3 ไฟล์ ไม่มี database

`index` เอาการ์ดไป embed แล้วเก็บผลไว้ที่ store ไม่ใช้ database เลย
ใช้ไฟล์ธรรมดาสามไฟล์:

| ไฟล์ | เก็บอะไร |
|---|---|
| `vectors.f32` | Float32 เรียงต่อกัน N × 1024 มิติ |
| `meta.jsonl` | 1 บรรทัด = 1 แถว (id/kind/citekey/title/topic) |
| `manifest.json` | `{ model, dim, count, updated }` |

บนเครื่อง m5 ตอนนี้ standalone store อยู่ที่ `<repo>/.citation/store`
เนื้อหา `manifest.json` จริง:

```json
{
  "model": "ollama:bge-m3",
  "dim": 1024,
  "count": 75,
  "updated": "2026-07-25T11:30:39.102Z"
}
```

75 แถว = 62 paper + 13 vault note (retro/lesson/research ที่ index
ด้วย `--vault`) รวมกันหนักประมาณ 300 KB — เบากว่าไฟล์รูปหนึ่งใบ

`manifest.json` จำชื่อ model ไว้เพราะเหตุผลเดียว — vector จาก model
ต่างกัน**เทียบกันไม่ได้** ตัวเลข 1024 มิติจาก `bge-m3` ไม่ได้อยู่ใน
พื้นที่เดียวกับ vector จาก model อื่น สลับ model เมื่อไหร่ต้อง
`index` ใหม่ทั้งชุด ไม่มีทางไล่แปลงทีละแถว

ผ่าน maw ที่เก็บจะย้ายไปที่ `$MAW_HOME/citation-data/store` แทน —
ที่ตั้งต่างกัน แต่รูปแบบไฟล์เหมือนกันเป๊ะ ทั้งคู่ gitignore ลบทิ้ง
ได้ตลอด แล้ว `index --vault` สร้างใหม่ให้ครบ เพราะเป็น derived data
ล้วน ๆ ไม่มีอะไรอยู่ใน store ที่ไม่มีอยู่ในการ์ดอยู่แล้ว

search เองก็ไม่ซับซ้อน — brute-force cosine ล้วน ๆ ใน TypeScript
ไม่มี ANN index ไม่มี index structure พิเศษ 75 แถวใช้เวลาประมาณ
0.2 วินาที รวมเวลา embed คำค้นด้วยแล้ว corpus ขนาดนี้ยังไม่ต้อง
คิดเรื่อง scale — เอาไว้ตอน corpus โตถึงหลักหมื่นแถวค่อยว่ากัน

## 4.6 aka: กับ authors_upstream: — ทำไมไม่มีอะไรถูกลบ

ตอนรัน `citation doi` ครั้งแรกเพื่อถาม Crossref หา DOI ให้ครบ มันเจอ
มากกว่าที่ตั้งใจ — เจอว่า corpus ต้นทางผิด 18 จุด ใน 14 การ์ด บางใบ
ผิดหนักถึงขั้นใส่ชื่อผู้เขียนคนแรกผิดคนไปเลย

ตัวอย่างจริง — การ์ด `jin2022.md` เดิมชื่อไฟล์ `li2022.md` แล้วใส่
ผู้เขียนเป็น Li, R. / Hu, Y. / Li, H. / Zhang, Y. แต่ Crossref ยืนยัน
ว่า paper นี้ผู้เขียนจริงคือ Jin, C. เป็นคนแรก — citekey เดิมผิด
คนทั้งใบ ต้อง rename จาก `li2022` เป็น `jin2022`

คำถามคือ — แล้วชื่อเดิม ผู้เขียนเดิม หายไปไหน คำตอบคือไม่หายเลย
สักตัว การ์ดใบเดียวกันนี้เก็บทั้งสองเวอร์ชันไว้:

```yaml
citekey: jin2022
aka: li2022
authors_upstream:
  - "Li, R."
  - "Hu, Y."
  - "Li, H."
  - "Zhang, Y."
```

`aka:` เก็บ citekey เดิมก่อน rename `authors_upstream:` เก็บรายชื่อ
ผู้เขียนที่ JSONL เคยอ้างไว้ผิด สองตัวนี้ทำงานคู่กันเป็นกฎ **Nothing
is Deleted** ตัวจริง — ไม่ใช่แค่คำขวัญ แต่เป็น mechanism สองชั้น:

ชั้นแรก — ป้องกัน**การ์ดผี** ทุกครั้งที่ `cards` regenerate ใหม่จาก
JSONL มันจะอ่าน `aka:` กลับ แล้วรู้ว่า citekey `li2022` ที่เคยมีใน
JSONL ถูก rename ไปเป็น `jin2022` แล้ว จะไม่สร้าง `li2022.md` ขึ้นมา
ซ้ำอีกใบข้าง ๆ `jin2022.md` ถ้าไม่มี `aka:` ทุกรอบ regenerate จะได้
การ์ดผีตัวใหม่โผล่มาเรื่อย ๆ ตามจำนวนครั้งที่รัน

ชั้นสอง — เก็บ**หลักฐานของความผิดพลาด**ไว้ ไม่ใช่แค่ลบของผิดแล้ว
เขียนของถูกทับเงียบ ๆ authors_upstream บอกตรง ๆ ว่า "เคยเชื่อว่าคือ
คนนี้" แล้ว `authors:` ตัวบนบอกว่า "จริง ๆ คือคนนี้" — ทั้งสองอยู่ใน
ไฟล์เดียวกัน ใครมาอ่านทีหลังเห็นทั้งสองด้าน ไม่ใช่แค่เห็นเวอร์ชัน
ที่ถูกแล้วเหมือนไม่เคยผิดมาก่อน

นี่คือหลักการข้อ 1 ของเราเอง — "Nothing is Deleted" — paper ที่ดู
เหมือนไม่เกี่ยวก็ยังอยู่ในคอร์ปัสพร้อมเหตุผลว่าทำไมไม่เกี่ยว citekey
ที่แก้แล้วก็ยังอยู่ใน `aka:` พร้อมเหตุผลว่าทำไมถึงแก้ ความผิดพลาด
ไม่ใช่สิ่งที่ต้องซ่อน มันเป็นส่วนหนึ่งของ argument — บอกว่าเรา
ตรวจสอบจริง ไม่ใช่แค่ก็อปมาแปะ

รายการเต็มทั้ง 18 จุด แยกประเภท (ชื่อผู้เขียนผิดคน 7 · title แต่งขึ้น
1 · เลขหน้าผีจากเลขท้าย DOI 7 · journal ผิด 1 · volume สลับกับเลข
หน้า 2) อยู่ที่ `artifacts/citation-audit.md` — เก็บไว้เป็นบันทึกแยก
อีกชั้น ไม่ได้พึ่งแค่ `aka:`/`authors_upstream:` ในการ์ดอย่างเดียว

ต้องพูดตรงนี้ให้ชัด — `aka:` กับ `authors_upstream:` **ไม่ได้**คุ้ม
ครองทุกการแก้ มันคุ้มครองเฉพาะกรณีที่ citekey เปลี่ยนหรือรายชื่อ
ผู้เขียนเปลี่ยนเท่านั้น การ์ด `she2019` เป็นตัวอย่างที่ตรงข้ามกัน —
JSONL ต้นทางใส่ title ที่**แต่งขึ้นเอง** (DOI ถูกต้อง แต่ไม่มีใคร
เอา title ไปเทียบกับสิ่งที่ DOI นั้นชี้จริง) พอ Crossref แก้ title
ให้ citekey ไม่ต้องเปลี่ยน ไม่มีอะไรต้อง `aka:` การ์ดใบนี้เลยไม่มี
field ทั้งสองตัวอยู่เลย — ร่องรอยของ title เดิมที่ผิดอยู่ที่
`citation-audit.md` กับ git history เท่านั้น ไม่ได้อยู่ในไฟล์

กลับกัน การ์ด `yu2023` ก็สอนอีกมุม — เดิมชื่อไฟล์ `npjclimate2023`
(ตั้งจากชื่อ journal เพราะยังไม่รู้ผู้เขียน) แก้ไปเป็น `yu2023` ตาม
ผู้เขียนคนแรก ทั้งที่**ผู้เขียนไม่เคยผิด** ผิดแค่เลขหน้า — 363 ซึ่ง
มาจากเลขท้าย DOI (`...-00363-w`) ทั้งที่เลขบทความจริงคือ 41 การ์ด
ใบนี้มี `aka: npjclimate2023` แต่ไม่มี `authors_upstream:` เพราะ
citekey เปลี่ยน แต่ authors ไม่เคยเปลี่ยน — สองตัวนี้จึงเป็นอิสระ
จากกัน ไม่ได้ผูกมาด้วยกันเสมอไป

สรุปให้จำง่าย — `aka:` ตามการเปลี่ยน**ชื่อไฟล์** `authors_upstream:`
ตามการเปลี่ยน**เนื้อหา authors** ส่วนการแก้ field อื่น (title,
pages, journal, volume) ที่ไม่กระทบทั้งสองอย่างนี้ ไม่มี field
พิเศษมารองรับ — ต้องพึ่ง `citation-audit.md` กับ `git log` เอา
ถึงจะเห็นว่าใบไหนเคยผิดอะไรมาก่อน นี่คือเหตุผลที่ "Nothing is
Deleted" ในบทนี้ไม่ได้แปลว่า field เดียวเก็บทุกอย่าง — มันแปลว่า
**มีที่เก็บอยู่เสมอ** แค่คนละชั้นกันตามแต่ว่าอะไรเปลี่ยน

โครงสร้างที่วางไว้ในบทนี้ทั้งหมด — การ์ดเป็นความจริง, frontmatter
ตัวไหน embed ตัวไหนไม่, กฎรอด/ไม่รอด, store สามไฟล์ธรรมดา — มีไว้
เพื่อให้ 8 คำสั่งที่จะเจอในบทถัดไปทำงานถูกที่ ถูกเวลา ไม่ต้องเดา

บทที่ 5 พาไปเรียงคำสั่งทั้ง 8 ตัวตามลำดับที่ใช้จริง เริ่มจากตัวที่
ต้องรันก่อนเสมอ — `status` — เพราะโครงสร้างที่เพิ่งอธิบายไปทั้งหมด
คือสิ่งที่ `status` กำลังรายงานให้ฟังอยู่ทุกครั้งที่เรียกมัน
