# บทที่ 8: Index ด้วย CPU — เครื่องไม่มี GPU ทำยังไง

เครื่องที่เราวัดเลขทั้งเล่มนี้คือ m5 — Apple M5 Max, 18 cores,
128 GB unified memory. ollama โหลด bge-m3 ขึ้น GPU เต็มก้อน
ไม่มีตกค้างที่ CPU เลย — บทที่แล้วเห็นตัวเลข index --vault
75 รายการ 8.4 วินาทีไปแล้ว ตัวเลขนั้นสวยก็จริง แต่มันเป็นเลข
ของเครื่องเดียว เครื่องที่แรงเป็นพิเศษด้วยซ้ำ

แต่เครื่องของคุณอาจไม่ใช่แบบนั้น อาจเป็นโน้ตบุ๊ค Intel
รุ่นเก่า อาจเป็น VM บน cloud ที่ไม่มี GPU passthrough อาจเป็น
เดสก์ท็อป AMD ที่ไม่มีการ์ดจอแยก หรือแม้แต่รันอยู่ใน Docker
container บนเครื่องที่มี GPU จริงแต่ container มองไม่เห็นมัน
(GPU passthrough เข้า container ไม่ใช่เรื่องเซ็ตอัตโนมัติ ต้อง
ตั้งค่าเพิ่มเสมอ) — คำถามคือ index จะทำงานไหม แล้วช้าแค่ไหน

คำตอบตรงๆ ก่อนเลย เรา **ยังไม่ได้วัด** ตัวเลขเวลาบนเครื่องที่
ไม่มี GPU ทุกตัวเลขในหนังสือเล่มนี้มาจาก m5 เครื่องเดียว
ไม่มีเครื่อง Intel/AMD ให้ทดสอบตอนเขียนบทนี้ — เพราะงั้นบทนี้
จะไม่มีเลข "X วินาทีบน CPU" ให้อ้างอิง มีแต่สอนให้คุณวัดเอง
บนเครื่องคุณ พร้อมวิธีเช็คว่าเครื่องคุณตกไปทำงานบน CPU จริง
ไหม กับวิธีรับมือถ้า RAM มีน้อย

ทำไมถึงต้องบอกตรงๆ แบบนี้ แทนที่จะประมาณให้ฟังดูมั่นใจ
เพราะเลขที่แต่งขึ้นมาลอยๆ อันตรายกว่าเลขที่ไม่มี ถ้าเราเขียน
"CPU ใช้เวลาประมาณ 2 นาที" ทั้งที่ไม่เคยวัดจริง คนอ่านที่เจอ
เครื่องช้ากว่านั้นสิบเท่าจะคิดว่าตัวเองทำอะไรผิด ทั้งที่จริงๆ
แล้วมันแค่ต่างเครื่อง หนังสือเล่มนี้เลือกสอนวิธีวัดแทนการเดา
เพราะวิธีวัดใช้ได้กับทุกเครื่อง เลขที่เดาใช้ได้กับเครื่องเดียว

ถ้าคุณกำลังอ่านบทนี้เพราะเปิด laptop ทำงานอยู่แล้วรู้ตัวว่า
"เครื่องนี้ไม่มีการ์ดจอ" ให้รู้ไว้ก่อนว่านั่นไม่ใช่จุดจบของงาน
ทั้งบทที่เหลือคือคำตอบของคำถามนั้นตรงๆ — วัดยังไง เช็คยังไง
ปรับอะไรได้บ้าง แล้วทำไมสุดท้ายมันก็ยังจบงานได้อยู่ดี

## 8.1 ollama บน CPU ทำงานได้ไหม — ได้ แต่ช้ากว่า

ollama ไม่บังคับต้องมี GPU ถ้าเครื่องไม่มี Metal (Mac) หรือไม่มี
CUDA/ROCm (Linux/Windows) มันจะรัน inference บน CPU ล้วน
โมเดล bge-m3 ตัวเดียวกัน โหลดได้เหมือนกัน `ollama pull bge-m3`
ก็ยังทำงาน แค่ตอน embed แต่ละ batch จะใช้เวลานานกว่า
เพราะ CPU คำนวณ matrix multiplication ช้ากว่า GPU หลายเท่า

เหตุผลเชิงสถาปัตยกรรมง่ายๆ คือ GPU ถูกออกแบบมาให้มี core
เล็กๆ จำนวนมาก ทำงานเดียวกันพร้อมกันหลายพันชุด (parallel)
ส่วน CPU มี core น้อยกว่ามาก แต่แต่ละ core ฉลาดกว่า ทำงาน
ที่ต่างกันได้ดีกว่า embedding model คือการคูณเมทริกซ์ขนาด
ใหญ่ซ้ำๆ กัน — งานแบบนี้ตรงกับจุดแข็งของ GPU พอดี พอไม่มี
GPU ให้ใช้ CPU ก็ยังทำงานเดิมได้ แค่ทำแบบเรียงคิว ไม่ใช่พร้อม
กันหลักพัน

ตัวเลขนี้ไม่ตายตัว — ขึ้นกับรุ่น CPU จำนวน core และ
instruction set (AVX2 บน x86, NEON บน ARM) ของแต่ละเครื่อง
CPU ที่รองรับ instruction set สำหรับงาน vector/matrix โดยตรง
จะเร็วกว่า CPU รุ่นเก่าที่ไม่มี แม้จะเป็น CPU ล้วนเหมือนกัน

ก็เพราะแบบนั้นเราถึงบอกตัวเลขเป๊ะๆ ไม่ได้ Intel gen เก่ากับ
gen ใหม่ต่างกันไกล M1 กับ M5 ก็ต่างกันไกลถ้าไม่มี Metal
ให้ใช้ สิ่งเดียวที่ยืนยันได้คือ "รันจบแน่นอน" — ollama ไม่ error
ทิ้งถ้าไม่มี GPU มันแค่สลับไปใช้ CPU เงียบๆ ไม่มีข้อความเตือน
ขึ้นมาบอกว่า "ตอนนี้กำลังใช้ CPU นะ" — นี่แหละคือจุดที่ทำให้
คนใช้งานไม่รู้ตัว จนกว่าจะสงสัยว่าทำไมมันช้ากว่าที่คาดไว้

อีกความเข้าใจผิดที่พบบ่อยคือ "มี core CPU เยอะ = เร็วเท่า GPU"
— ไม่จริง จำนวน core ของ CPU ทั่วไปอยู่ที่หลักสิบ ในขณะที่
GPU มี core เล็กๆ หลักพันถึงหลักหมื่น ต่อให้เครื่องมี CPU 32
core ก็ยังห่างจากจำนวน core ของ GPU อยู่หลายเท่าตัว การเพิ่ม
core CPU ช่วยได้ในแง่ที่ ollama ขนานงานข้าม core ได้มากขึ้น
(เห็นได้จาก `user` time ที่สูงกว่า `real` ตามที่พูดถึงในหัวข้อ
ถัดไป) แต่ไม่ได้ทำให้ CPU กลายเป็น GPU — ปรับความคาดหวัง
ตรงนี้ไว้ก่อน จะได้ไม่ผิดหวังเวลาเจอเครื่อง CPU core เยอะแต่ยัง
ช้ากว่า GPU เล็กๆ อยู่ดี

มีจุดหนึ่งที่มักสับสนกันบ่อย — ตอน `ollama pull bge-m3` ครั้ง
แรก แถบดาวน์โหลดที่ขึ้นมาช้าหรือเร็ว วัดจาก**ความเร็วเน็ต**
ล้วนๆ ไม่เกี่ยวกับ CPU หรือ GPU เลย เพราะขั้นตอนนั้นแค่โหลด
ไฟล์โมเดลลงดิสก์ ยังไม่ได้เริ่มคำนวณอะไร ส่วนที่ CPU/GPU เข้า
มาเกี่ยวคือขั้นตอน**หลังจาก**โมเดลอยู่ในเครื่องแล้ว ตอนที่มัน
ถูกเรียกมาคำนวณเวกเตอร์จริงๆ — เน็ตช้ากับเครื่องช้าเป็นคนละ
ปัญหา อย่าปนกัน ถ้า pull ช้าแต่ index เร็ว หรือ pull เร็วแต่
index ช้า ทั้งสองแบบเป็นไปได้และปกติทั้งคู่

ปัญหาจริงไม่ใช่ "รันได้ไหม" แต่คือ "รันแล้วรู้ได้ไหมว่ามันไปอยู่
ที่ CPU" — เรื่องนี้ตอบได้แน่ชัด ไปดูกัน

## 8.2 วิธีตรวจว่าตกไป CPU จริงไหม — size_vram vs size

ollama มี endpoint `/api/ps` บอกว่าตอนนี้มีโมเดลอะไรโหลดอยู่
ในหน่วยความจำบ้าง แต่ละตัวมีสองเลขสำคัญ

```bash
curl -s http://localhost:11434/api/ps | jq .
```

```json
{
  "models": [
    {
      "name": "bge-m3:latest",
      "size": 665398500,
      "size_vram": 665398500,
      "context_length": 8192
    }
  ]
}
```

`size` คือขนาดโมเดลทั้งก้อนที่โหลดเข้าหน่วยความจำ
`size_vram` คือส่วนที่อยู่บน GPU memory จริงๆ สองเลขนี้ต้อง
อ่านคู่กันเสมอ อ่านตัวเดียวไม่มีความหมาย

**ถ้า `size_vram == size`** แปลว่าโมเดล resident อยู่บน GPU
เต็มก้อน ไม่มีส่วนไหนตกไป CPU — แบบที่ m5 เป็น (634 MB,
100% GPU, ไม่มี CPU fallback)

**ถ้า `size_vram < size`** แปลว่าบางส่วนอยู่บน GPU บางส่วน
ต้องคำนวณบน CPU แทน ยิ่ง `size_vram` ต่ำเท่าไหร่เทียบกับ
`size` ยิ่งพึ่ง CPU มากเท่านั้น ตัวอย่างสมมติเพื่อให้เห็นภาพ
(ไม่ใช่เลขที่วัดจริง) — ถ้า `size` คือ 665398500 ไบต์ แต่
`size_vram` คือ 332699250 ไบต์ (ครึ่งเดียว) แปลว่าโมเดล
ครึ่งหนึ่งอยู่บน GPU อีกครึ่งตกไปคำนวณบน CPU — เป็นสภาพ
ที่มักเจอตอน GPU memory ไม่พอสำหรับโมเดลทั้งก้อน (การ์ดจอ
VRAM น้อย) ไม่ใช่แค่ "มี GPU หรือไม่มี GPU" เป็นสเปกตรัมได้

**ถ้า `size_vram` เป็น 0 หรือไม่มี field นี้เลย** แปลว่าอยู่บน CPU
ล้วน — ไม่มี GPU acceleration ช่วยเลย นี่คือสภาพที่เครื่องไม่มี
การ์ดจอแยก หรือ ollama มองไม่เห็นการ์ดจอที่มีอยู่ (เช่นกรณี
container ที่พูดถึงตอนต้นบท)

`maw citation status` ทำเรื่องนี้ให้อัตโนมัติอยู่แล้ว เรียกครั้งเดียว
ก็เห็นบรรทัด hardware กับบรรทัด residency ต่อกัน ไม่ต้องไปยิง
`curl` เองด้วยซ้ำ

```
  ✓ hardware: Apple M5 Max · arm64 · 18 cores · 128 GB unified memory — Metal GPU available to ollama
  ✓ embeddings: ollama bge-m3 @ http://localhost:11434 — 1024-dim
      └ bge-m3:latest · 634 MB · 100% GPU (fully resident — no CPU fallback) · 8192 ctx
```

ถ้าเครื่องคุณไม่มี GPU บรรทัด hardware จะไม่มี "Metal GPU
available" ต่อท้าย (มีแค่บนแมค — เครื่องอื่นโชว์แค่ชื่อ CPU
กับจำนวน core ผ่าน sysctl บน macOS หรือกลไกเทียบเท่าบน
แพลตฟอร์มอื่น) ส่วนบรรทัด residency ถ้าขึ้น
`⚠ partly on CPU` หรือเปอร์เซ็นต์ต่ำกว่า 100 — นั่นแหละคือ
คำตอบ เครื่องคุณกำลังพึ่ง CPU อยู่จริง ไม่ต้องเดา ไม่ต้องดูจาก
พัดลมหมุนแรง เอาเลขจาก `/api/ps` เป็นหลัก

หมายเหตุ: `ollamaResidency()` ถาม `/api/ps` **หลัง**จากที่
embed ไปแล้วหนึ่งครั้ง (healthcheck) เพราะโมเดลต้องถูกเรียก
ใช้ก่อนถึงจะโผล่ในรายการที่โหลดอยู่ ถ้าเรียก `status` ตอนที่
ยังไม่เคย embed อะไรเลย บรรทัด residency อาจหายไปเฉยๆ —
ไม่ใช่ error แค่โมเดลยังไม่ถูกปลุก

อยากดูสดๆ ระหว่าง index กำลังรันอยู่ก็ได้ เปิดอีก terminal ขึ้นมา
แล้ว poll ทุกสองสามวินาที

```bash
watch -n 2 'curl -s http://localhost:11434/api/ps | jq .'
```

วิธีนี้มีประโยชน์ตอน RAM ตึงมือ เพราะเห็นได้ว่าโมเดล resident
เปลี่ยนไประหว่างที่ระบบแย่ง memory กับโปรแกรมอื่นหรือไม่ —
บางเครื่อง GPU เต็มก้อนตอนเริ่ม แต่พอเปิดโปรแกรมอื่นเพิ่ม
ระหว่างทาง อาจถูกเบียดจนบางส่วนตกไป CPU ระหว่างรันก็ได้
เห็นแบบนี้ชัดกว่าดูแค่ตอนจบ

ไม่อยากพึ่ง `jq` คำนวณเปอร์เซ็นต์เอง ollama เองก็มีคำสั่ง CLI
ตรงๆ ที่ทำเรื่องเดียวกัน

```bash
ollama ps
```

คำสั่งนี้อ่านค่าจาก endpoint เดียวกับ `/api/ps` ที่พูดถึงไปแล้ว
แค่จัดเป็นตารางให้อ่านง่าย มีคอลัมน์ PROCESSOR
บอกสัดส่วน GPU/CPU ตรงๆ ในบรรทัดเดียว — ใช้แทน `curl | jq`
ได้เลยถ้าแค่อยากดูด้วยตาเปล่า ส่วน `curl | jq` มีประโยชน์ตอน
อยากเอาเลขไปประมวลผลต่อ เช่นคำนวณเปอร์เซ็นต์เองแบบที่
`maw citation status` ทำ

```bash
curl -s http://localhost:11434/api/ps \
  | jq '.models[] | {name, pct: ((.size_vram // 0) / .size * 100 | round)}'
```

สองวิธีนี้ให้ข้อมูลชุดเดียวกัน เลือกใช้ตามสะดวก — `ollama ps`
เร็วกว่าตอนเช็คด้วยตา `curl | jq` เหมาะกว่าตอนต้องเขียนสคริปต์
เช็คอัตโนมัติ

## 8.3 จับเวลา index ของตัวเอง — วิธีวัดที่ตรงกับเครื่องคุณจริง

ตัวเลขที่เชื่อถือได้ที่สุดคือตัวเลขที่วัดจากเครื่องคุณเอง ไม่ใช่
ตัวเลขจากหนังสือเล่มนี้ วิธีทำง่ายมาก ใช้ `time` ห่อคำสั่ง index
ไว้

```bash
time maw citation index --vault
```

ผลลัพธ์ท้ายๆ จะมีสามบรรทัดจาก shell

```
real    0m??.???s
user    0m??.???s
sys     0m0.???s
```

`real` คือเวลาที่รอจริงๆ (นาฬิกาผนัง) อันนี้แหละคือเลขที่ใช้
เทียบกับใครก็ได้ — ของเรา 8.4 วินาทีบน GPU เต็มก้อน คือเลข
`real` แบบนี้เอง

`user` คือเวลารวมที่ CPU ใช้คำนวณจริง (นับรวมทุก core ถ้ามี
การขนานกัน) บนเครื่อง CPU-only ที่ ollama ใช้หลาย thread
พร้อมกัน `user` อาจมีค่า**มากกว่า** `real` เสียอีก — นั่นไม่ใช่
เรื่องแปลก แปลว่ามันขนานงานข้าม core อยู่ ยิ่ง `user` ห่างจาก
`real` มาก ยิ่งแปลว่าใช้ core หลายตัวช่วยกันทำ ส่วน `sys` คือ
เวลาที่ใช้คุยกับระบบปฏิบัติการ (อ่านไฟล์ เปิด socket) ปกติ
น้อยมากเทียบกับสองตัวแรก

ถ้าอยากรู้เจาะจงกว่านั้นว่า batch ไหนช้าสุด เปิด verbose ดูก็ได้
(ถ้าปลั๊กอินมี flag นั้น) แต่ขั้นต่ำแค่ `time` ก็พอบอกได้แล้วว่า
"เครื่องนี้ index 75 รายการใช้กี่วินาที" — จำนวนไว้ เทียบกับครั้ง
ถัดไปได้ ถ้าเพิ่ม paper เข้าคอร์ปัสแล้วเวลาโตขึ้นผิดปกติ ก็รู้ตัว
เร็ว

ข้อควรระวังตอนวัด: ครั้งแรกที่รันจะรวมเวลาโหลดโมเดลเข้า
หน่วยความจำด้วย (ollama pull ครั้งแรกโหลดโมเดล ~1.2 GB —
อันนี้นับแยกจาก pull นะ อันนี้คือตอน "ปลุก" โมเดลที่ pull ไว้
แล้วให้พร้อมใช้งาน) รันซ้ำรอบสองตอนโมเดล warm อยู่แล้วจะ
ได้เวลาที่สะท้อนการคำนวณจริงมากกว่า ลองวัดทั้งสองแบบแล้ว
จดไว้คนละบรรทัดก็ได้ — "รอบแรก (cold): ... / รอบสอง (warm):
..."

เครื่อง CPU-only ยังมีตัวแปรรบกวนอีกอย่างที่เครื่อง GPU ไม่ค่อย
เจอ — ตัวรบกวนจากโปรแกรมอื่นที่แย่ง CPU อยู่พร้อมกัน (เบราว์
เซอร์เปิดหลายแท็บ, ตัวซิงก์ไฟล์เบื้องหลัง) เพราะ CPU ต้องแบ่ง
เวลาให้ทุกโปรเซสตามคิว ไม่เหมือน GPU ที่ ollama มักได้ใช้คน
เดียว ถ้าอยากได้เลขที่นิ่งที่สุด ปิดโปรแกรมหนักๆ ก่อนวัด แล้ว
วัดซ้ำสักสองสามรอบ เอาค่ากลาง (median) แทนค่าครั้งเดียว —
ครั้งไหนช้าผิดปกติอาจเป็นเพราะเครื่อง throttle ความร้อนหรือ
โปรแกรมอื่นแทรก ไม่ใช่ตัวแทนที่แท้จริงของความเร็วเครื่อง

อยากเทียบ GPU vs CPU บนเครื่องเดียวกันเลยก็ทำได้ ถ้าเครื่อง
คุณมี GPU แต่อยากรู้ว่าไม่มี GPU จะช้าแค่ไหน ปิด GPU
acceleration ชั่วคราว (วิธีขึ้นกับแพลตฟอร์ม เช่นตั้ง
environment variable ที่ ollama อ่าน เพื่อบังคับ CPU-only) แล้ว
`time maw citation index --vault` อีกรอบ เทียบตัวเลขสองรอบนี้
ก็จะเห็นส่วนต่างจริงบนเครื่องคุณเอง — แม่นกว่าตัวเลขจากเครื่อง
อื่นเสมอ

โน้ตบุ๊คไร้พัดลม (fanless) มีตัวแปรเพิ่มอีกอย่างคือ thermal
throttling — พอ CPU ทำงานหนักต่อเนื่องนานพอ ชิปจะลดความเร็ว
ตัวเองลงเพื่อกันร้อนเกิน ผลคือถ้า index ใช้เวลานานหลายนาที
รอบท้ายๆ อาจช้ากว่ารอบต้นๆ ทั้งที่งานเหมือนเดิมทุกอย่าง
ไม่ใช่เรื่องแปลก เป็นพฤติกรรมปกติของฮาร์ดแวร์ ไม่ใช่ bug ของ
ollama หรือปลั๊กอิน — ถ้าสงสัยว่าเจอเรื่องนี้ ลองพักเครื่องให้เย็น
สักพักแล้ววัดใหม่ เทียบกับรอบที่รันติดกันโดยไม่พัก

จดผลที่วัดได้ไว้ที่ไหนสักที่ที่หาเจอทีหลัง — ไฟล์ note ธรรมดา
ในโฟลเดอร์ vault ก็พอ ("index --vault บนเครื่อง X: cold Ns /
warm Ns, size_vram=0%") เลขนี้ไม่ใช่ของทิ้ง มันคือ baseline
ของคุณเอง ครั้งถัดไปที่คอร์ปัสโตขึ้น จะได้มีอะไรเทียบว่าช้าลง
ผิดปกติหรือช้าลงตามสัดส่วนจำนวนรายการที่เพิ่ม

อยากได้ค่ากลางแบบไม่ต้องจดมือ วน loop สามรอบแล้วเก็บผลลง
ไฟล์ก็ได้ ง่ายๆ แบบนี้

```bash
for i in 1 2 3; do
  { time maw citation index --vault; } 2>> index-timing.log
done
```

เปิด `index-timing.log` ดูทีหลัง จะเห็นสามบรรทัด `real` เรียง
กัน — เอาค่ากลาง (ตัวที่อยู่กลางเมื่อเรียงจากน้อยไปมาก) เป็น
ตัวแทนที่นิ่งกว่าค่าเดียว เพราะตัดผลจากรอบที่ถูกรบกวนโดย
บังเอิญออกไปได้

## 8.4 RAM น้อย ลด batch ลง — CF_EMBED_BATCH=8

ก่อนพูดเรื่อง batch ต้องแยกให้ชัดก่อนว่าตัวช้าที่แท้จริงมีสอง
ตัวคนละแบบ — ตัวแรกคือ "ไม่มี GPU" (คำนวณช้ากว่าเพราะใช้
CPU) ตัวที่สองคือ "RAM ไม่พอ" (ระบบต้องเอาข้อมูลไปพักไว้ที่
สลับหน่วยความจำบนดิสก์ หรือ swap) สองอย่างนี้แก้คนละทาง
— อยากได้คำนวณเร็วขึ้นต้องหา GPU หรือ backend อื่น อยากได้
ไม่ error/ไม่ค้างเพราะ RAM ไม่พอ ต้องลด batch แก้ที่ตัวปัญหา
ให้ถูกจุด ไม่งั้นจะแก้ผิดทาง

RAM ไม่พอมักน่ากลัวกว่า CPU ช้าเสียอีก เพราะ CPU ช้ายังคำนวณ
จบได้แค่ใช้เวลานานขึ้น แต่ RAM ไม่พอจนต้อง swap หนักๆ อาจ
ทำให้เครื่องค้างจนต้องบังคับปิดโปรเซส หรือ error กลางทางแบบ
ที่ไม่มีข้อความบอกสาเหตุชัดเจน — อาการแบบนี้คือสัญญาณให้
ลด batch ก่อนอย่างอื่น

embed ถูกส่งเป็นชุด (batch) ไม่ใช่ทีละบรรทัด ค่า default คือ
16 รายการต่อ batch ควบคุมด้วย environment variable ชื่อ
`CF_EMBED_BATCH` — ชื่อขึ้นต้นด้วย CF เพราะ backend แรกที่
ปลั๊กอินนี้เขียนขึ้นมารองรับคือ Cloudflare แต่ตัวแปรตัวนี้คุม
batch size ของทุก backend รวมถึง ollama ที่รันในเครื่องด้วย —
ชื่อเป็นร่องรอยประวัติศาสตร์ ไม่ใช่ข้อจำกัดที่ใช้ได้แค่กับ
Cloudflare

ตอนที่คอร์ปัสมีแค่ paper 56 ใบ ยิง batch 16 ผ่านสบาย แต่พอ
รวม vault note เข้าไปด้วย (`--vault`) จำนวนรายการรวมพุ่งไป
65+ ใบ ยิงทีเดียวทั้งชุดแล้ว worker ตอบ 500 — เกิดจากขนาด
payload หรือเวลาประมวลผลของ batch นั้นเกินที่ backend รับ
ไหว

กลไกคร่าวๆ คือแต่ละ batch ถูกส่งเป็น JSON array ของข้อความ
ทั้งชุดในคำขอเดียว (HTTP request เดียว) ฝั่งรับต้องเก็บ tensor
กลางทางของทุกข้อความใน batch นั้นไว้ในหน่วยความจำพร้อม
กันจนกว่าจะคำนวณเสร็จทั้งชุด ถ้า batch ใหญ่ ก็ต้องมี tensor
ค้างอยู่พร้อมกันมากขึ้น — นี่คือจุดที่ RAM เข้ามาเกี่ยวข้องโดยตรง

เครื่อง RAM น้อยเจอปัญหานี้ง่ายกว่า เพราะยิ่ง batch ใหญ่ ยิ่งต้อง
เก็บ tensor กลางทางไว้ในหน่วยความจำพร้อมกันมากขึ้น ถ้า
เครื่องคุณ RAM จำกัด (หรือเจอ error แบบ 500 ระหว่าง index)
ลด batch ลงตรงๆ

```bash
CF_EMBED_BATCH=8 maw citation index --vault
```

ลดจาก 16 เหลือ 8 — batch เล็กลง ใช้หน่วยความจำต่อ batch
น้อยลง แลกกับจำนวนรอบที่ยิงมากขึ้น (75 รายการ batch 8 คือ
~10 รอบ แทนที่จะเป็น ~5 รอบ) เวลารวมอาจไม่ต่างมาก
เพราะรอบเยอะขึ้นแต่แต่ละรอบเบาลง — สิ่งที่ได้คือความเสถียร
ไม่ error กลางทาง

ยังไม่พอ ลดเหลือ `CF_EMBED_BATCH=4` ก็ได้ ต่ำสุดคือ 1
(ยิงทีละรายการ) — รอบเยอะที่สุด แต่แทบไม่มีทางพลาดเรื่อง
memory เพราะแต่ละคำขอมีแค่ข้อความเดียว วิธีหาค่าที่พอดีคือ
ไล่ลดลงครึ่งหนึ่งไปเรื่อยๆ (16 → 8 → 4 → 2 → 1) จนกว่าจะรัน
จบโดยไม่ error ไม่มีค่าตายตัวว่าเท่าไหร่ "ถูก" — ปรับจนกว่า
index จะรันจบโดยไม่ error คือค่าที่ใช้ได้บนเครื่องนั้น

ทำไมไม่ตั้ง `CF_EMBED_BATCH=1` ไว้เป็นค่าเริ่มต้นเลยตั้งแต่แรก
ทุกเครื่อง เพราะแต่ละรอบมี overhead ของตัวมันเอง — เปิด
คำขอ, รอ backend ตอบ, ปิดคำขอ — ต้นทุนคงที่ต่อรอบนี้ไม่ได้
หายไปเวลาข้อความในรอบนั้นสั้น batch ใหญ่ขึ้นคือการเกลี่ย
ต้นทุนคงที่นี้ให้ตกกับหลายข้อความพร้อมกัน ยิ่ง batch เล็กเท่าไร
ยิ่งเสียเวลาไปกับ overhead มากขึ้นเท่านั้นเมื่อเทียบกับเวลา
คำนวณจริง เพราะงั้น `CF_EMBED_BATCH=8` คือจุดกลางที่ดีสำหรับ
เครื่อง RAM น้อย ไม่ใช่ดิ่งไป 1 ทันที — ลองจากตัวกลางก่อน
ค่อยลดต่อถ้ายังไม่พอ

| อาการ | ลองทำ |
|---|---|
| index ค้างนาน ไม่มี error | ปกติสำหรับ CPU-only — รอ หรือวัดเวลาไว้ |
| `500` กลางทาง | ลด `CF_EMBED_BATCH` |
| เครื่องแค้ก / swap เยอะ | ลด `CF_EMBED_BATCH` เพิ่ม |
| `no embedding backend reachable` | ollama ไม่ได้รันอยู่ — `ollama serve` |

## 8.5 คอร์ปัส 62 ใบ ไม่ใช่ 62,000 ใบ

ตรงนี้คือเหตุผลที่บทนี้ไม่ต้องกลัวเลข "ช้า" คอร์ปัสของเราคือ
62 paper บวก 13 vault note รวม 75 รายการ — แต่ละรายการ
embed แค่ `title + summary + thesis_relevance` ต่อกัน ไม่ใช่
ทั้งไฟล์ ข้อความสั้นๆ ต่อรายการ ไม่ใช่ document ยาวเป็นหน้าๆ

ตัวคอร์ปัสทั้งชุดหลัง index เสร็จแล้วเก็บบนดิสก์แค่ 452 KB
(ส่วน `vectors.f32` ที่เก็บเวกเตอร์ล้วนๆ คือ 300 KB) — เทียบ
ขนาดแล้วมันคือไฟล์เล็กกว่ารูปภาพทั่วไปหนึ่งรูปเสียอีก การ
คำนวณที่ทำอยู่จึงไม่ใช่งานหนักในความหมายของ "ข้อมูลเยอะ"
แต่เป็นงานที่หนักในความหมายของ "โมเดลภาษาใหญ่ ทำงาน
กับข้อความจำนวนน้อย"

เทียบกับงานจริงที่ต้อง index เอกสารระดับหมื่นระดับแสนไฟล์
งานของเราคืองาน **one-off** ทำครั้งเดียวจบ ไม่ใช่ pipeline ที่
รันทุกวัน ไม่ใช่ระบบ production ที่ผู้ใช้เป็นพันรอ query
พร้อมกัน — มันคือ index คอร์ปัสสำหรับวิทยานิพนธ์ใบเดียว
ทำเสร็จแล้วก็ใช้ search/serve/graph ต่อไปเรื่อยๆ โดยไม่ต้อง
index ใหม่ (นอกจากตอนเพิ่ม paper หรือสลับ model)

| | ระบบ RAG ระดับ production | คอร์ปัสของเรา |
|---|---|---|
| จำนวนรายการ | หลักหมื่น–ล้าน | 75 |
| ความถี่ index | ต่อเนื่อง / รายวัน | ครั้งเดียว (+เพิ่มเป็นครั้งคราว) |
| ผู้ใช้ query พร้อมกัน | หลักพัน | คนเดียว |
| ขนาด store | หลาย GB ขึ้นไป | 452 KB |

ต่อให้เครื่อง CPU-only ใช้เวลานานกว่า GPU สิบเท่า ยี่สิบเท่า —
สมมติ GPU ใช้ 8.4 วินาที CPU อาจใช้เป็นนาที ก็ยังจบในเวลา
เดียวกับต้มกาแฟหนึ่งแก้ว ไม่ใช่เรื่องที่ต้องรอเป็นชั่วโมง เพราะ
ฐานตั้งต้นคือ 75 รายการ ไม่ใช่ 75,000 รายการ ตัวคูณเวลาต่อ
รายการอาจสูงกว่ากันมากบน CPU แต่จำนวนรายการเล็กพอที่
ผลคูณสุดท้ายยังอยู่ในระดับ "รอได้" — ตัวคูณสูงคูณกับฐานเล็ก
ยังเล็กกว่าตัวคูณต่ำคูณกับฐานใหญ่เสมอ

เครื่องเล็กไม่ใช่ข้ออ้างที่จะไม่ทำ งานนี้ทำได้บนโน้ตบุ๊คเก่าแค่ไหน
ก็ได้ ขอแค่รันจบ วัดเวลาไว้ครั้งเดียว แล้วก็จบงาน — ไม่ต้องมี
GPU แรงๆ ถึงจะเริ่มสร้าง citation graph ได้ อย่าปล่อยให้เครื่อง
ที่ไม่มี GPU กลายเป็นเหตุผลที่จะไม่เริ่มลงมือ — มันแค่ทำให้รอ
นานกว่าเดิม ไม่ใช่ทำไม่ได้เลย

## 8.6 ตอนไหนควรยอมใช้ cloud แทน

ถ้าวัดเวลาบนเครื่องตัวเองแล้วเจอว่า index --vault ใช้เวลานาน
เกินจะรอไหว (เช่นรอเป็นสิบนาทีสำหรับแค่ 75 รายการ หรือ
error ซ้ำๆ ต่อให้ลด batch ลงเหลือน้อยที่สุดแล้ว) ทางเลือกถัดไป
คือสลับไปใช้ backend แบบ cloud — Cloudflare Workers AI
รันโมเดลเดียวกัน (`@cf/baai/bge-m3`) บนเครื่อง Cloudflare
แทนที่จะรันบนเครื่องเราเอง

สัญญาณที่บอกว่าถึงเวลาลองทางนี้ดูมีสามอย่างคร่าวๆ — วัด
`real` แล้วมันไม่สมเหตุสมผลเทียบกับปริมาณงาน 75 รายการ,
ลด `CF_EMBED_BATCH` ลงต่ำสุดแล้วยัง error, หรือ RAM ของ
เครื่องแทบไม่พอให้ ollama โหลดโมเดลขึ้นมาเลยด้วยซ้ำ — ถ้า
เจอข้อใดข้อหนึ่ง cloud คือทางออกที่สมเหตุสมผล ไม่ใช่การยอม
แพ้

| สัญญาณที่เจอ | ทำอะไรก่อน | ถ้ายังไม่หาย |
|---|---|---|
| `real` นานเกินคาด | จับเวลาซ้ำ 3 รอบ เอาค่ากลาง | ลองสลับไป cloud |
| `500` ระหว่าง index | ลด `CF_EMBED_BATCH` ทีละครึ่ง | ถ้าลดถึง 1 แล้วยัง error |
| RAM แทบไม่พอโหลดโมเดล | ปิดโปรแกรมอื่นก่อนรัน | RAM เครื่องต่ำกว่าที่โมเดลต้องการจริงๆ |

ตารางนี้ไม่ใช่กฎตายตัว แค่ลำดับที่ควรลองก่อนยอมเปลี่ยน
backend — เปลี่ยน batch ก่อนเสมอ เพราะมันฟรีและทำได้ทันที
เปลี่ยน backend ทีหลัง เพราะมันมีข้อควรคิดเรื่องข้อมูลออกเน็ต
ตามมาด้วย

สลับได้ด้วย environment variable ตัวเดียว

```bash
CITATION_EMBED=worker maw citation index --vault
```

การเลือกตรงนี้ไม่ใช่หน้าที่ของเราที่จะตัดสินใจแทน — เราแค่
ถือคอร์ปัสและถือเลขที่วัดได้ ส่วนจะรอ CPU ต่อ ลด batch เพิ่ม
หรือสลับไป cloud คือเรื่องที่ ณัฐ ต้องเห็นตัวเลขจริงบนเครื่อง
ตัวเองก่อนแล้วค่อยตัดสินใจ — บทนี้ให้แค่วิธีวัดกับตัวเลือกที่มี
ไม่ได้บอกว่าต้องเลือกไหน

แต่การสลับไปใช้ cloud มีข้อควรคิดก่อนกด — คอร์ปัสของเรา
