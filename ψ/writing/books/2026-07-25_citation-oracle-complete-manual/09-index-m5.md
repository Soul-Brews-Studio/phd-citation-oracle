# บทที่ 9: Index บน M5 Apple Silicon — Metal กับ unified memory

บทที่แล้วเราคุยเรื่องเครื่องที่ไม่มี GPU — ช้าแต่จบงานได้ ไม่มีข้ออ้าง
บทนี้กลับด้าน เครื่องที่เรากำลังนั่งอยู่หน้าจอนี้แหละ เครื่องที่มี GPU
อยู่แล้วในตัว คำถามไม่ใช่ "เร็วไหม" อีกต่อไป แต่เป็น "ใช้ของที่มีอยู่คุ้ม
รึเปล่า" — เพราะ GPU ที่ซื้อมาแล้วแต่ไม่ได้ทำงานจริง ก็ไม่ต่างอะไรจาก
CPU ที่ทำงานช้า

เครื่องที่วัดในบทนี้คือ m5 — Apple M5 Max, arm64, 18 cores, RAM
128 GB unified memory, macOS ตัวเลขทุกตัวข้างล่างมาจากเครื่องนี้จริง
ไม่ใช่ spec sheet ไม่ใช่ตัวเลขเดา

## 9.1 unified memory ต่างจาก discrete GPU ตรงไหน

GPU การ์ดจอทั่วไป (NVIDIA ผ่าน PCIe) มี VRAM เป็นของตัวเอง แยกจาก
RAM หลักของเครื่อง พอจะรัน model บน GPU ต้องคัดลอกข้อมูลจาก RAM
ข้าม PCIe bus ไปลง VRAM ก่อน — ขั้นตอนนี้กินเวลา และถ้า model ใหญ่
กว่า VRAM ที่มี ก็ต้อง swap เข้าออกหรือ fallback กลับไปที่ CPU บางส่วน

Apple Silicon ไม่ทำงานแบบนั้น CPU กับ GPU ใช้ RAM ก้อนเดียวกัน —
นี่คือความหมายของคำว่า unified memory พอ CPU เตรียมข้อมูลเสร็จ
GPU ก็เข้าถึงก้อนความจำเดียวกันได้เลย ไม่ต้องคัดลอกข้ามที่ไหน
ข้อจำกัดของ "VRAM" บนเครื่องนี้เลยไม่ใช่ VRAM แยกต่างหากแบบเดิม
แต่เป็น RAM รวมทั้งเครื่อง — 128 GB บน m5

### เส้นทางข้อมูลบน discrete GPU ทีละขั้น

ลองแตกขั้นตอนฝั่ง discrete GPU ให้ละเอียดกว่านี้อีกหน่อย พอสั่งโหลด
model เข้า GPU สิ่งที่เกิดขึ้นจริงมีสามจังหวะ — อ่านไฟล์ weight จาก
disk เข้า RAM หลักก่อน จากนั้น driver จองพื้นที่บน VRAM แล้วค่อย
คัดลอกข้อมูลก้อนเดียวกันนั้นข้าม PCIe bus ไปลง VRAM อีกที ระหว่าง
จังหวะที่สองกับสาม ข้อมูลชุดเดียวกันจึงอยู่ใน memory สองที่พร้อมกัน
ชั่วคราว — กิน RAM ต้นทางไปด้วย ไม่ใช่กิน VRAM ปลายทางอย่างเดียว

จังหวะคัดลอกนี้เกิดครั้งเดียวตอนโหลด ไม่ได้เกิดซ้ำทุกครั้งที่
inference แต่ก็ยังเป็นต้นทุนที่ discrete GPU ต้องจ่ายเสมอ
ไม่ว่า model จะเล็กแค่ไหน — เพราะ VRAM กับ RAM หลักคือ memory
คนละก้อน คนละที่อยู่
ทางกายภาพ จะให้ GPU มองเห็นข้อมูลได้ ต้องมีขั้นตอนย้ายข้อมูลเสมอ
ไม่มีทางลัด

### เส้นทางข้อมูลบน Apple Silicon — ไม่มีจังหวะคัดลอกให้เสีย

ฝั่ง Apple Silicon ตัดจังหวะที่สองกับสามทิ้งไปเลย เพราะ GPU core
กับ CPU core อยู่บน die เดียวกัน ต่อกับ memory controller ตัวเดียวกัน
พอ CPU เขียนข้อมูลลง RAM เสร็จ GPU ก็อ่านจากตำแหน่งเดียวกันนั้นได้
ทันที ไม่ต้องมีขั้นตอน "ย้ายไปอีกที่" แทรกอยู่ตรงกลาง — นี่คือสิ่งที่
เอกสาร Apple เรียกว่า zero-copy

ผลที่ตามมาจริงในงานของเรา — ทุกครั้งที่ ollama โหลด bge-m3 กลับ
เข้า memory (หลัง idle เกิน keep_alive แล้วโดน unload ไป) ก็ไม่ต้อง
เสียเวลาคัดลอกข้อมูลข้าม bus เหมือน discrete GPU ต้องเสีย ต้นทุนที่
เหลืออยู่คือแค่การอ่านไฟล์ weight จาก disk เข้า RAM ครั้งเดียวเท่านั้น
แม้แต่ตอนที่ Bun process (ตัว plugin) เรียก ollama ผ่าน HTTP บน
localhost คำตอบที่ได้กลับมาก็ยังเป็นการอ่านจาก RAM ก้อนเดียวกันนี้
อยู่ดี ไม่ใช่การข้าม bus ช้า ๆ แบบ discrete GPU

ตารางเทียบให้เห็นภาพชัดขึ้น:

| ขั้นตอน | discrete GPU (PCIe) | unified memory (Apple Silicon) |
|---|---|---|
| โหลด model เข้า GPU | copy RAM → VRAM ข้าม bus | ไม่ต้องคัดลอก ใช้ RAM ก้อนเดียวกัน |
| ขีดจำกัดขนาด model | VRAM การ์ดจอ (เช่น 24 GB) | RAM รวมทั้งเครื่อง (128 GB บน m5) |
| ถ้า model ใหญ่เกิน | swap หรือ fallback CPU บางส่วน | แทบไม่เจอกับ model ขนาด embedding |
| ยืนยันว่าอยู่บน GPU จริง | `nvidia-smi` ดู memory usage | ollama `/api/ps` — `size_vram` vs `size` |

bge-m3 เป็น embedding model ขนาดไม่ใหญ่ — 634 MB เท่านั้นตอนโหลด
เข้า memory เทียบกับ RAM 128 GB ของเครื่องนี้ก็แทบไม่รู้สึกอะไรเลย
แต่ประเด็นไม่ได้อยู่ที่ "มี RAM พอไหม" ประเด็นอยู่ที่ "GPU เห็น model
ทั้งก้อนจริงไหม หรือมีบางส่วนหลุดไปอยู่ CPU"

### ขีดจำกัดจริงคือ RAM ทั้งเครื่อง — ไม่ใช่ VRAM แยกก้อน

ประเด็นที่น่าสนใจกว่าความเร็วคือเรื่องขนาด การ์ดจอ discrete ทั่วไป
ที่ใช้กันตาม workstation มักมี VRAM อยู่ราว ๆ หลักสิบ GB (ตัวเลข
24 GB ในตารางข้างบนเป็นแค่ตัวอย่างระดับที่พบเห็นได้ทั่วไป — ไม่ใช่
ตัวเลขที่วัดจากเครื่องไหนโดยเฉพาะ) พอ model ใหญ่กว่าเพดานนั้น ก็ต้อง
เลือกเอาว่าจะ quantize ให้เล็กลง หรือยอม fallback บางเลเยอร์ไป CPU

บนเครื่องนี้เพดานนั้นหายไป เพราะไม่มี VRAM แยกให้ชนเลย เพดานที่
เหลืออยู่คือ RAM รวมทั้งเครื่อง 128 GB ลบด้วยสิ่งที่ macOS กับ process
อื่นใช้อยู่ก่อนแล้ว — bge-m3 ที่ 634 MB เทียบกับเพดานนี้จึงเหมือนไม่มี
อะไรเกิดขึ้นเลย แต่เราไม่ได้ทดสอบว่าถ้าโหลด model ที่ใหญ่กว่านี้มาก
เช่นระดับหลายสิบ GB จะยังคง 100% resident อยู่ไหม — เรื่องนี้ยังไม่
ได้วัด บอกตรง ๆ ว่ายังไม่รู้ ไม่ใช่เดาว่าน่าจะได้

คำถามนี้ตอบด้วยตาเปล่าไม่ได้ — ต้องวัด

## 9.2 ยืนยันว่าใช้ GPU จริง ไม่ใช่แค่เดา

ollama มี endpoint `/api/ps` — คืนค่ารายการ model ที่โหลดอยู่ตอนนี้
พร้อมตัวเลขสองตัวที่สำคัญ: `size` (ขนาด model ทั้งก้อน) กับ
`size_vram` (ขนาดที่อยู่บน GPU memory จริง)

กฎอ่านง่ายๆ คือ

```
size_vram == size  →  resident ทั้งก้อน — 100% GPU
size_vram <  size  →  บางส่วนหลุดไป CPU — ⚠ partly on CPU
size_vram == 0     →  ไม่ได้อยู่บน GPU เลย — CPU ล้วน
```

### อ่าน field ทีละตัว — name, size, size_vram, context_length, expires_at

`/api/ps` ไม่ได้คืนแค่ตัวเลขสองตัวที่ใช้ตัดสิน resident หรือไม่ —
มันคืนรายละเอียดมากกว่านั้น ลองไล่ทีละ field ที่เราใช้จริงในโค้ด

- `name` — ชื่อ model พร้อม tag ตามที่ ollama โหลดไว้ เช่น
  `bge-m3:latest` tag ท้ายสำคัญ เพราะ `find()` ในโค้ดของเราเทียบ
  ด้วย `startsWith(OLLAMA_MODEL)` ไม่ใช่เทียบตรงทั้งสตริง — กันเคส
  ที่ ollama คืนชื่อพร้อม tag แต่ config เราตั้งไว้แค่ชื่อเปล่า
- `size` — ขนาด model ทั้งก้อน หน่วยเป็น byte นับรวมทุกส่วนที่โหลด
  เข้า memory ไม่ว่าจะอยู่ฝั่ง CPU หรือ GPU
- `size_vram` — ขนาดเฉพาะส่วนที่อยู่บน GPU memory จริง (ในบริบทนี้
  คือ Metal) ถ้าเท่ากับ `size` เป๊ะ แปลว่าไม่มีส่วนไหนหลุดไป CPU เลย
- `context_length` — ขนาด context window ที่ instance นี้ใช้อยู่จริง
  หน่วยเป็น token ไม่ใช่ค่า default ของ model แต่คือค่าที่ negotiate
  กันตอนโหลดจริง
- `expires_at` — เวลาที่ ollama จะ unload model ทิ้งถ้าไม่มีการเรียก
  ใช้อีก นับตาม `keep_alive` (ค่า default ของ ollama อยู่ที่ราว 5
  นาทีนับจากการเรียกครั้งล่าสุด) — field นี้ขยับทุกครั้งที่มี request
  ใหม่เข้ามา

ตัวอย่าง JSON จริงจาก `/api/ps` บนเครื่องนี้ (ตัด field ที่ไม่เกี่ยว
ออกไป เหลือเฉพาะที่โค้ดของเราอ่าน):

```json
{
  "models": [
    {
      "name": "bge-m3:latest",
      "size": 664660868,
      "size_vram": 664660868,
      "context_length": 8192,
      "expires_at": "<เวลาปัจจุบัน + keep_alive>"
    }
  ]
}
```

ตัวเลข `664660868` byte คือค่าจริงที่วัดได้จาก bge-m3 บนเครื่องนี้ —
แปลงเป็น MB แล้วคือ 634 MB ตรงกับที่บอกไว้ในหัวบท ส่วน `expires_at`
เราไม่ได้บันทึกค่าที่แน่นอนไว้ตอนวัด รู้แค่ความหมายของ field นี้ —
ไม่อยากใส่เวลาที่แต่งขึ้นมาลงในตัวอย่าง เพราะนั่นเท่ากับสร้างตัวเลข
ที่ไม่มีอยู่จริงขึ้นมาเปล่า ๆ

บนเครื่องที่ไม่มี GPU (บทที่แล้ว) `size_vram` จะเป็น 0 หรือไม่มี field
นี้เลยด้วยซ้ำ — นั่นคือสัญญาณว่าตกไป CPU ทั้งหมด ส่วนเครื่องนี้ที่มี
Metal GPU พอเรียก `/api/ps` แล้วดู bge-m3 จะเห็นค่าเท่ากันพอดี — 100%
GPU ไม่มีส่วนไหนหลุดไปอยู่ CPU เลย

นี่คือความต่างระหว่าง "บอกว่าใช้ GPU" กับ "พิสูจน์ว่าใช้ GPU" — ตัวเลข
สองตัวนี้แหละที่ทำให้พิสูจน์ได้ ไม่ใช่แค่เชื่อตามเอกสาร

### ถ้า size_vram น้อยกว่า size แปลว่าอะไร

ตัวเลขที่น่ากลัวกว่า 0 คือกรณีอยู่ระหว่างกลาง — `size_vram` มีค่า
แต่น้อยกว่า `size` เคสนี้แปลว่า ollama ตัดสินใจ offload บางเลเยอร์
ของ model ไปให้ CPU คำนวณแทน อาจเพราะ GPU memory ไม่พอ หรือ
เพราะ driver ประเมินว่าคุ้มกว่าที่จะแบ่งงานแบบนี้

ผลที่ตามมาคือ inference แต่ละครั้งต้องรอทั้งสองฝั่งทำงานเสร็จ ฝั่งไหน
ช้ากว่าก็เป็นคอขวด — และเพราะ CPU กับ GPU มักไม่ได้เร็วเท่ากันสำหรับ
งานแบบเดียวกัน ผลลัพธ์คือ throughput รวมมักแย่กว่าทั้งสองกรณีสุดโต่ง
(100% GPU หรือ 100% CPU) เราไม่ได้เจอเคสนี้บน m5 กับ bge-m3 — แต่
โค้ดของเราเตือนไว้ด้วยเครื่องหมาย ⚠ ถ้าวันไหนเจอเข้าจริง

## 9.3 `status` บอก hardware ให้ — ทำไมเราเพิ่มบรรทัดนี้เข้าไป

ก่อนหน้านี้เอกสารของเราเขียนไว้ว่า index ทำงานแบบ "GPU-backed" —
คำนี้อยู่ในเอกสารจริง แต่ไม่เคยปรากฏใน output ของ `citation status`
เลยสักครั้ง พอไม่มีใครวัดซ้ำ คำโฆษณานี้ก็เสี่ยงเลิกเป็นความจริงแบบ
เงียบๆ — เครื่องเปลี่ยน driver เปลี่ยน ollama อัปเดตเวอร์ชัน แล้ว
model หลุดไป CPU โดยไม่มีใครรู้ตัว เพราะไม่มีใครเช็ค

ทางแก้ไม่ใช่เขียนเอกสารให้มั่นใจกว่าเดิม แต่คือใส่การวัดเข้าไปใน
runtime เอง — ทุกครั้งที่รัน `citation status` ให้ระบบไปถาม
`/api/ps` เอง แล้วรายงานตัวเลขจริงกลับมา ไม่ใช่ข้อความคงที่ที่เขียน
ไว้ล่วงหน้า

ใน `src/index.ts` ของ plugin นี้มี comment กำกับไว้ตรงจุดนั้น
ว่าทำไมถึงทำแบบนี้:

```ts
// "GPU-backed" was an assertion in the docs and nowhere
// in the output, which is the kind of claim that quietly
// stops being true. On Apple silicon the GPU is reached
// through Metal with unified memory, so a model is either
// fully resident or partly spilled to CPU — and ollama
// tells us which, exactly.
```

โค้ดที่อ่านค่า hardware มาจาก `sysctl` — คำสั่งระดับ macOS ที่คุย
กับ kernel โดยตรง ไม่ต้องพึ่ง library ภายนอก:

```ts
function hardwareLine(): string {
  const bytes = (n: number) =>
    `${(n / 1024 ** 3).toFixed(0)} GB`;
  const sysctl = (key: string) => {
    const r = Bun.spawnSync(["sysctl", "-n", key], {
      stdout: "pipe",
      stderr: "ignore",
    });
    return new TextDecoder().decode(r.stdout).trim();
  };
  const chip = sysctl("machdep.cpu.brand_string");
  const mem = Number(sysctl("hw.memsize"));
  const cores = sysctl("hw.logicalcpu");
  const silicon = process.arch === "arm64";
  return (
    `  ✓ hardware: ${chip} · ${process.arch} · ${cores} cores` +
    ` · ${bytes(mem)} unified memory` +
    " — Metal GPU available to ollama"
  );
}
```

สามบรรทัด sysctl นี้คือที่มาของตัวเลขในหัวบทนี้ — `machdep.cpu
.brand_string` บอกชื่อชิป `hw.memsize` บอก RAM รวม (byte แล้วแปลง
เป็น GB) `hw.logicalcpu` บอกจำนวน core ทั้งหมด ไม่ใช่ตัวเลขที่
hardcode ไว้ในโค้ด — รันบนเครื่องไหนก็ได้ตัวเลขของเครื่องนั้นจริง

`Bun.spawnSync` เรียก `sysctl -n <key>` ตรง ๆ แฟล็ก `-n` สั่งให้
คืนแค่ค่า ไม่ต้องมีชื่อ key นำหน้า (ไม่งั้นต้อง parse string เพิ่ม)
ส่วน `stderr: "ignore"` กันไม่ให้ warning จาก sysctl หลุดปนเข้ามาใน
output ที่ผู้ใช้เห็น — ถ้า key ไหนไม่มีในเครื่องนั้น ก็แค่ได้สตริงว่าง
กลับมาเงียบ ๆ ไม่ทำให้ทั้งฟังก์ชันพัง โค้ดยังมีเงื่อนไข
`process.platform === "darwin"` คลุมอยู่ด้วย — รันบน Linux หรือ
เครื่องอื่นที่ไม่มี `sysctl` แบบนี้ ฟังก์ชันจะข้ามไปคืนแค่
platform กับ arch เฉย ๆ ไม่ error ไม่ crash แค่ไม่มีบรรทัด unified
memory ให้เห็น — สอดคล้องกับเครื่อง CPU-only ในบทที่แล้วที่ไม่มี
Metal ให้พูดถึง

ส่วนที่บอกว่า GPU กำลัง resident อยู่จริงไหม แยกออกไปอีกฟังก์ชัน
หนึ่ง เพราะต้องถาม ollama ไม่ใช่ถาม macOS:

```ts
async function ollamaResidency(): Promise<string> {
  const res = await fetch(`${OLLAMA_URL}/api/ps`, {
    signal: AbortSignal.timeout(1500),
  });
  const json = await res.json();
  const m = json.models.find((x) =>
    x.name.startsWith(OLLAMA_MODEL)
  );
  if (!m?.size) return "";
  const pct = Math.round(
    ((m.size_vram ?? 0) / m.size) * 100
  );
  const mb = (m.size / 1024 ** 2).toFixed(0);
  return (
    `\n      └ ${m.name} · ${mb} MB · ${pct}% GPU` +
    (pct === 100
      ? " (fully resident — no CPU fallback)"
      : " ⚠ partly on CPU") +
    (m.context_length ? ` · ${m.context_length} ctx` : "")
  );
}
```

สังเกตว่าถ้า fetch ล้มเหลว (model ยังไม่โหลด เพราะ ollama unload
ทิ้งไปหลังไม่ใช้ราว 5 นาที) ฟังก์ชันคืนสตริงว่างเฉยๆ ไม่โยน error —
เพราะ "model ยังไม่โหลด" ไม่ใช่ความผิดพลาด เป็นแค่สถานะปกติ ยังไม่
คุ้มค่าจะเตือนเป็น warning `AbortSignal.timeout(1500)` จำกัดเวลารอ
ไว้แค่ 1.5 วินาที ด้วยเหตุผลเดียวกัน — ถ้า ollama ไม่ตอบ ก็ไม่ควรให้
`citation status` ทั้งคำสั่งค้างรอเป็นนาที แค่เพื่อบรรทัดเสริมบรรทัด
เดียว

ทั้งสองฟังก์ชันถูกเรียกจาก `cmdStatus()` เรียงกันเป็นบรรทัดในผลลัพธ์
ของ `citation status` — hardware line มาก่อน ตามด้วย residency
line ต่อท้าย embeddings line เพราะ residency ต้องรอให้ healthcheck
เรียก embedding ไปครั้งหนึ่งก่อน model ถึงจะถูกโหลดขึ้น GPU จริง

### ทำไมต้องเรียก residency หลัง healthcheck เท่านั้น

ลำดับตรงนี้ไม่ใช่เรื่องสไตล์โค้ด แต่เป็นเงื่อนไขที่ถ้าสลับแล้วพัง — ใน
`checkEmbedBackend()` มี comment กำกับไว้ตรงบรรทัดที่เรียก
`ollamaResidency()` ว่า

```ts
// Ask after embedding, not before: the healthcheck is
// what loads the model.
const residency =
  backend === "ollama" ? await ollamaResidency() : "";
```

เหตุผลคือ ollama ไม่ได้โหลด model ค้างไว้ตลอดเวลา — ถ้าไม่มีใคร
เรียกใช้เกิน keep_alive (ราว 5 นาที) model จะถูก unload ทิ้งจาก
memory ไปเลย พอ `citation status` เริ่มทำงาน ถ้าไม่เคยมี request
เข้าไปหา ollama มาก่อนในรอบ 5 นาทีนั้น model ก็อาจจะยังไม่ถูกโหลด
เลยด้วยซ้ำ

ลองนึกภาพว่าสลับลำดับ — เรียก `ollamaResidency()` ก่อนแล้วค่อย
เรียก `embedOne("healthcheck")` ทีหลัง ผลที่ได้คือ `/api/ps` จะคืน
รายการ model ว่างเปล่า เพราะยังไม่มีอะไรถูกโหลดขึ้นมาให้เห็น
`ollamaResidency()` จะ return string ว่างตามที่ตั้งใจไว้ (ไม่ error)
แต่บรรทัด `└` ในผลลัพธ์ก็หายไปเงียบๆ — ไม่ใช่ error สีแดง ไม่ใช่
คำเตือน แค่ข้อมูลที่ควรมีหายไปโดยไม่มีใครสังเกต

นี่คือ bug class ที่อันตรายกว่า error ธรรมดา — error เห็นชัด แต่
ข้อมูลที่หายไปเงียบๆ แบบนี้ต้องรู้ก่อนว่ามันควรจะมีถึงจะสังเกตออก
ทางแก้เลยง่ายมาก แค่เรียง `checkEmbedBackend()` ให้ทำ embed
ก่อนเสมอ แล้วค่อยถาม residency ต่อท้าย — โค้ดจริงใน `cmdStatus()`
เขียนไว้แบบนั้นอยู่แล้ว ถูกลำดับตั้งแต่แรก ไม่ใช่แก้ทีหลังจากเจอบั๊ก

## 9.4 เลขจริงบน m5 — Apple M5 Max

รัน `citation status` บนเครื่อง m5 แล้วได้ผลลัพธ์ประมาณนี้ (ย่อ
เฉพาะส่วนที่เกี่ยวกับบทนี้):

```
  ✓ hardware: Apple M5 Max · arm64 · 18 cores
      · 128 GB unified memory — Metal GPU
        available to ollama
  ✓ embeddings: ollama bge-m3 @ http://localhost:11434
      — 1024-dim
      └ bge-m3:latest · 634 MB · 100% GPU
        (fully resident — no CPU fallback)
        · 8192 ctx
```

อ่านทีละบรรทัด hardware line บอกว่าเครื่องนี้เป็น Apple M5 Max
สถาปัตยกรรม arm64 มี 18 logical core และ RAM รวม 128 GB แบบ
unified memory — ตัวเลขทั้งหมดมาจาก `sysctl` ตรงๆ ไม่มีปัดเศษ
เอาใจใคร

### 18 core แยกเป็น 6 กับ 12 จริง ไม่ใช่ก้อนเดียว

ตัวเลข 18 core ที่ `hardwareLine()` รายงาน เป็นผลรวมของสองกลุ่ม
คอร์ที่ทำงานคนละบทบาทกัน — `hardwareLine()` เองเรียกแค่
`hw.logicalcpu` ตัวเดียว ไม่ได้แตกละเอียดกว่านั้น แต่ macOS ยังมี
sysctl อีกสองตัวที่บอกสัดส่วนได้ ลองเรียกตรงๆ บนเครื่องนี้ดู:

```
$ sysctl -n hw.perflevel0.logicalcpu \
  hw.perflevel1.logicalcpu
6
12
```

`perflevel0` คือกลุ่ม performance core 6 ตัว `perflevel1` คือกลุ่ม
efficiency core 12 ตัว รวมกันได้ 18 ตรงกับ `hw.logicalcpu` พอดี
เทียบกับ `hw.perflevel0.physicalcpu` และ
`hw.perflevel1.physicalcpu` ก็ได้ค่าเท่ากันเป๊ะ (6 กับ 12 เหมือนกัน)
แปลว่าเครื่องนี้ไม่มี hyperthreading หรือ SMT แบบที่ CPU บาง
platform ทำ — 1 logical core ต่อ 1 physical core จริงๆ

คอร์กลุ่มแรกแรงกว่า กินไฟมากกว่า เหมาะกับงานที่ต้องการ latency ต่ำ
ส่วนกลุ่มหลังประหยัดไฟกว่า เหมาะกับงาน background หรืองานที่ขนาน
กันได้เยอะๆ สองตัวนี้ยังไม่ถูกต่อเข้า `hardwareLine()` — เป็น
รายละเอียดที่วัดเพิ่มเองตอนเขียนบทนี้ ไม่ใช่สิ่งที่ `citation status`
แสดงให้เห็นตอนนี้ ถ้าจะเพิ่มเข้าไปวันหลัง ก็แค่เพิ่ม sysctl call อีก
สองบรรทัดในฟังก์ชันเดียวกัน

index ทั้ง vault ที่ใช้เวลา 8.4 วินาทีนั้น เราไม่ได้วัดแยกว่า core
กลุ่มไหนถูกใช้งานหนักกว่ากัน — scheduler ของ macOS เป็นคนตัดสิน
เอง ไม่ได้อยู่ในมือของโค้ด TypeScript ที่เราเขียน เรื่องนี้ยังไม่ได้
วัด บอกตรงๆ แบบนี้ดีกว่าเดาว่า core กลุ่มไหนทำงานมากกว่ากัน

บรรทัดถัดมาคือ residency ของ bge-m3 — โหลดอยู่ใน memory 634 MB
`size_vram` เท่ากับ `size` พอดี คิดเป็น 100% แปลว่า resident
ทั้งก้อนจริง ไม่มีส่วนไหนหลุดไปอยู่ CPU และ context window ที่ตั้งไว้
คือ 8192 token

ส่วนความเร็วจริง — index ทั้ง vault 75 รายการ (62 paper + 13 vault
note) ใช้เวลา 8.4 วินาที วัดตอนที่ model warm อยู่บน GPU แล้ว ไม่ได้
นับเวลาโหลด model ครั้งแรกรวมด้วย search หนึ่งครั้ง (embed query +
brute-force cosine เทียบกับทั้ง 75 แถว) ใช้เวลา 0.221 วินาที

เอาตัวเลข 8.4 วินาทีหารด้วย 75 รายการตรงๆ ได้ประมาณ 0.112 วินาที
ต่อรายการโดยเฉลี่ย — แต่นี่คือค่าเฉลี่ยรวม ไม่ใช่ตัวเลขที่วัดแยกราย
paper เพราะ paper บางฉบับยาวกว่าฉบับอื่นมาก เวลาที่ใช้จริงต่อ
รายการก็ต่างกันไปตามความยาว ไม่ได้เท่ากันทุกใบ

ส่วน 0.221 วินาทีต่อ search หนึ่งครั้ง ประกอบด้วยสองงานซ้อนกัน —
เรียก ollama ให้ embed query ก่อน แล้วเอา vector ที่ได้มาเทียบ
cosine กับทั้ง 75 แถวแบบ brute-force เราไม่ได้แยกวัดว่าสองงานนี้
กินเวลาไปเท่าไหร่ต่อชิ้น รู้แค่ตัวเลขรวม — brute-force cosine บน
75 แถวเป็นงานคำนวณที่เล็กมากเทียบกับการยิง HTTP request ไปหา
ollama แต่ยังไม่มีการ profile แยกจริงจัง จะฟันธงตอนนี้ว่าฝั่งไหนกิน
เวลามากกว่ากัน คงไม่ซื่อตรงกับข้อมูลที่มี

ตัวเลขพวกนี้ไม่ได้แปลว่า "GPU เร็วกว่า CPU กี่เท่า" — เพราะบทที่แล้ว
เราตั้งใจไม่แต่งตัวเลข CPU ขึ้นมาเทียบ (ดูบทที่ 8 ถ้ายังไม่ได้อ่าน)
สิ่งที่ตัวเลขชุดนี้พิสูจน์ได้จริงมีแค่อย่างเดียว — model ตัวนี้อยู่บน
GPU ของเครื่องนี้ ครบทั้งก้อน ไม่มี fallback แอบซ่อนอยู่

| ตัวชี้วัด | ค่าที่วัดได้ | ที่มา |
|---|---|---|
| ชิป | Apple M5 Max | `sysctl machdep.cpu.brand_string` |
| core รวม | 18 | `sysctl hw.logicalcpu` |
| performance core | 6 | `sysctl hw.perflevel0.logicalcpu` |
| efficiency core | 12 | `sysctl hw.perflevel1.logicalcpu` |
| RAM | 128 GB unified | `sysctl hw.memsize` |
| bge-m3 ใน memory | 634 MB | `/api/ps` → `size` |
| GPU residency | 100% | `size_vram / size` |
| context | 8192 | `/api/ps` → `context_length` |
| index 75 รายการ | 8.4 วินาที | จับเวลาจริง (model warm) |
| เฉลี่ยต่อรายการ | ~0.112 วินาที | 8.4 ÷ 75 (คำนวณ ไม่ใช่วัดแยก) |
| search 1 ครั้ง | 0.221 วินาที | จับเวลาจริง |

## 9.5 บทเรียน — คำโฆษณาที่ไม่มีใครวัด จะเลิกเป็นความจริง

ก่อนบทนี้จะปิด ขอย้อนกลับไปที่คำถามต้นเรื่อง — ทำไมแค่เขียนไว้ใน
เอกสารว่า "GPU-backed" ถึงไม่พอ

เอกสารเขียนครั้งเดียว แต่เครื่องเปลี่ยนได้ทุกวัน — ollama อัปเดต
เวอร์ชัน driver เปลี่ยน หรือแม้แต่สลับไปรันบนเครื่องคนละเครื่อง
ที่ไม่มี Metal GPU เลย คำว่า "GPU-backed" ที่เขียนไว้นิ่งๆ ในไฟล์
Markdown ไม่รู้เรื่องอะไรพวกนี้เลยสักนิด — มันแค่อยู่ตรงนั้น
เหมือนเดิม ไม่ว่าความจริงเบื้องหลังจะเปลี่ยนไปแค่ไหน

นี่คือรูปแบบที่เจอซ้ำ — claim ที่ไม่มี proof ผูกติดอยู่ ในที่สุดจะ
เลื่อนออกห่างจากความจริงไปเรื่อยๆ แบบไม่มีใครรู้ตัว ไม่ใช่เพราะมี
ใครโกหก แค่เพราะไม่มีใครเช็คซ้ำ

ทางแก้ที่เราเลือกไม่ใช่เขียนเอกสารให้แน่นกว่าเดิม แต่คือย้าย claim
เข้าไปอยู่ใน runtime เอง — ให้ `status` เป็นคนพิสูจน์ทุกครั้งที่รัน
ไม่ใช่ให้เอกสารเป็นคนยืนยันครั้งเดียวแล้วจบ พอ `hardwareLine()`
กับ `ollamaResidency()` ต่อสาย sysctl กับ `/api/ps` ตรงๆ คำว่า
"GPU-backed" ก็เปลี่ยนสถานะจาก "คำสัญญา" มาเป็น "ตัวเลขที่วัดได้
ทุกครั้งที่สั่ง"

หลักการนี้ใช้กว้างกว่าแค่เรื่อง GPU ด้วย — claim ไหนก็ตามที่บอก
เรื่อง performance หรือ hardware ถ้าไม่มีทางวัดซ้ำได้ง่ายๆ ในหนึ่ง
คำสั่ง claim นั้นเสี่ยงกลายเป็นเรื่องเล่าที่ไม่มีใครกล้าเช็ค — และ
พอไม่มีใครกล้าเช็ค ก็ไม่มีใครรู้ว่ามันยังจริงอยู่รึเปล่า

เครื่องนี้มี GPU ที่แรงอยู่แล้ว 634 MB ของ bge-m3 แทบไม่รู้สึกอะไร
เทียบกับ RAM 128 GB ที่มี — ของแรงที่มีอยู่แล้วนี้ ใช้ให้คุ้มไม่ใช่แค่
เปิดมันไว้เฉยๆ แต่คือรู้ให้แน่ชัดว่ามันกำลังทำงานอยู่จริง

แล้วถ้าเครื่องที่ใช้ไม่มี GPU เลย ไม่มี Metal ไม่มี unified memory —
ยังมีทางเลือกอีกทางที่ไม่ต้องพึ่งเครื่องตัวเองเลยสักนิด บทถัดไปว่า
ด้วยเรื่องนั้น
